# Trace cloud misconfigurations into controlled consequences

**BugVault should hunt cloud misconfiguration as “misconfiguration → boundary failure → controlled effect,” not as a count of failed posture checks.** Start with resource ownership and a precise operation, compare owner and lower-trust contexts, then follow every evidenced, authorized identity or consumer transition until a meaningful synthetic consequence is established. The four selected resources supply complementary inputs: Prowler supplies configuration observations, CloudGoat supplies authored dependency chains, HackTricks Cloud supplies cross-provider hypotheses, and AWS documentation supplies primary authorization semantics. AWS is the first implementation lane; Azure and GCP receive complete planning branches here, with provider-specific semantics and defaults awaiting primary-source validation. BugVault's recorded baseline is **674 passing tests, 25 skills and no cloud executor**; those tests were not rerun for this report. This delivery is research synthesis and an engineering proposal, not implementation, campaign approval, cloud testing or a finding. ([Local baseline](../Handover.md#2-current-status-honest); [Prowler](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/README.md); [CloudGoat](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/README.md); [Cloud methodology](https://cloud.hacktricks.wiki/en/pentesting-cloud/pentesting-cloud-methodology.html#basic-methodology); [AWS evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html))

### Prowler observations are useful precisely when their limitations remain visible

Prowler's pinned README advertises AWS/Azure/GCP assessment coverage, but periodically updated check counts are not independently enumerated coverage or feature parity. Its output separates a check definition from resource results; normalized fields include identity/scope, resource, time, version, verdict and other metadata. CSV and OCSF are suitable **candidate import formats**, not already supported BugVault adapters. OCSF lifecycle status must not be mistaken for the check verdict: “New” does not mean FAIL, and suppression is separate from the original result. Preserve PASS, FAIL, MANUAL, mute/lifecycle status, scanner severity and BugVault judgment independently. ([Provider table](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/README.md#prowler-at-a-glance); [finding model](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/prowler/lib/outputs/finding.py); [report formats](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/docs/user-guide/cli/tutorials/reporting.mdx); [mute semantics](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/docs/user-guide/cli/tutorials/mutelist.mdx))

Three inspected behaviors explain why a failed check is not a vulnerability. The Azure blob check tests an account-level allowance rather than anonymous retrieval of a particular blob. The GCP storage check emits MANUAL when IAM cannot be read. The AWS escalation helper explicitly excludes important resource, condition, SCP and transitive-path reasoning. In addition, AWS quick inventory is tag-coverage-limited, and finding UIDs use resource names among other fields; neither inventory completeness nor immutable resource identity follows from their presence. **Design:** retain collection denominators, errors, policy visibility and exact resource scope before prioritizing any result. ([Azure check](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/prowler/providers/azure/services/storage/storage_blob_public_access_level_is_disabled/storage_blob_public_access_level_is_disabled.py); [GCP check](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/prowler/providers/gcp/services/cloudstorage/cloudstorage_bucket_public_access/cloudstorage_bucket_public_access.py); [IAM helper limits](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/prowler/providers/aws/services/iam/lib/privilege_escalation.py#L6-L15); [inventory](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/docs/user-guide/cli/tutorials/quick-inventory.mdx); [UID](https://github.com/prowler-cloud/prowler/blob/a5fd2d7eda90e9d59e0c4bfc0c74284b47529694/prowler/lib/outputs/finding.py#L575-L598))

The AWS additions policy includes `securityhub:BatchImportFindings`; the Azure custom role includes key/configuration retrieval actions. Optional fixers mutate configuration and can incur cost, while optional secret validation sends discovered credentials to provider APIs. Model-declared redaction is not general DLP. An approved future scan therefore needs a reviewed collector/action map, not merely selected check names, output filters or a mutelist. No fixer, automatic credential validation, key retrieval or full-account permission expansion belongs in the initial integration. ## Three execution contexts turn hints into testable boundaries

### One permission envelope enables deep work without inventing authority

**“No limitations” means no arbitrary technical-depth ceiling, not removal of written authorization, program/provider policy, scope, budgets, owned-resource constraints or evidence stop rules.** A standing plan can approve reversible writes, disposable deployments, identity exchange and inert execution in advance; it need not ask for a new exception at each already-approved step. Its envelope must name the rules source/hash/date and approver; provider policy review; exact provider/partition/accounts/tenants/subscriptions/projects/regions/resources/prefixes and exclusions; supplied test principals; provider operations plus HTTP methods and sensitive response classes; approved execution channel; attempt/rate/concurrency/time/byte/resource/cost caps; receiver and evidence-disclosure permissions; and cleanup owner/deadline/recovery. New discoveries do not enlarge it. No real-user testing, production credential harvesting, persistence, production lateral movement, log disabling, stress, or harmful data modification is required: assess those consequences through policies and synthetic effects. Stop the affected run on scope/principal drift, throttling/challenge/lockout, unexpected 5xx/degradation, credential/private-data spill, unknown write outcome, lost attribution, cap exhaustion or failed cleanup; charge uncertain attempts, retain evidence and require reviewed reconciliation before resume. Never change transport, identity, region or model to evade the stop. This preserves the existing [scope policy](../.claude/skills/scope-policy/SKILL.md) and [execution boundary](../AGENTS.md#execution-and-evidence).

The dedicated visible browser through Burp remains the default interactive path; current project documentation records preparation, not connected control or verified HTTPS capture. Native HTTP uses `python3 -m recon send` only within its approved capabilities. **Cloud SDKs/CLIs do not inherit its URL/method/egress/rate/budget enforcement**, and Burp/scanners are not integrated into that enforcement either. Any future cloud connector needs a separate approval/design with action/resource checks, signing and credential custody, redirects/retries/pagination/token-service destinations and accounting. Without it, the deliverable is an explicit operator-owned sandbox/lab handoff or owner artifact request, never an alternate network route. This plan changes neither model routing nor selected provider/model and does not distribute private captures to new model providers. ([Current transport and limits](../recon/README.md#skill-triggers-and-the-request-executor); [Burp boundary](../recon/README.md#explicit-method-grants-and-shared-burp-mcp); [browser status](../Handover.md#dedicated-visible-browser-prepared-connection-pending))

### A stored-signal census answers where and when to hunt

**Design:** open cloud work on onboarding, a newly captured cloud reference, policy/IAM/network/deployment change, new controlled role/tenant, federation/CI trigger change, newly exposed artifact, incident/billing anomaly, resolved collection error, stale resource/consumer, or source/check-version change. Onboarding builds the baseline; deployment and identity events reopen affected facets rather than rerunning everything blindly. Scheduled review uses a freshness window appropriate to the resource and engagement, not an invented universal seven-day truth. Keep old results as history. Prowler version-specific corrections and AWS analyzer propagation windows are concrete reasons to preserve time and source versions. ([Prowler changes](https://github.com/prowler-cloud/prowler/releases/tag/5.50.0); [Analyzer timing](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html))

### Outside-in and inside-out work meet at one exact hypothesis

**Design:** outside-in follows stored reference → ownership → current endpoint/resource → expected restriction → owner-seeded baseline → candidate contrast → actual consumer or identity edge. Inside-out follows owner hierarchy → collection gaps → policy/resource/runtime graph → lowest controlled principal → reachable operation → exact canary contrast → terminal effect. Join the two only through matching resource, principal, revision and time, never same-host or same-cloud coincidence. The hypothesis sentence is: **“Principal/session P can perform operation A on resource/version R through path T, contrary to intended boundary B under context C.”**

Queue by readiness, actual trust consumption and consequence, not just severity. Keep separate fields for **source confidence** (unverified hint, bound snapshot, observed operation, controlled replay), **potential severity** (consequence if all premises hold), **demonstrated impact**, and **effort/cost/disruption**. Highest-value initial hunts are intended-private marker exposure or delegated-scope defects; usable identity/trust/role-passing transitions; and mutable artifacts consumed by stronger workloads. A wildcard with a known deny ranks below a concrete canary boundary; an intended-public website remains a non-finding. No default mass namespace guessing is proposed.

## Exact operations expose more than generic cloud checklists

### Effective permission needs a principal/session/action/resource/context/policy-version tuple

**Design:** evaluate `provider + hierarchy + principal ID/type + session issuer/constraints + operation + all authorized resources/versions + network path + request context + policy/config versions + time`. Represent alternative allow routes as OR and necessary dependencies as AND; preserve each applicable deny as a veto. Distinguish policy-derived possibility, observed authentication, accepted operation and persisted/data-plane effect. Unsupported conditions or missing inherited/session documents yield **unknown**, not implicit permission. Scanner/simulator/analyzer disagreement remains separate source-qualified claims until a controlled counterfactual or provider clarification resolves it.

For AWS, an applicable explicit deny remains controlling, but **“all policies are intersected” is wrong**. The documented same-account treatment differs for identity grants, direct user-ARN resource grants, role-ARN grants, direct role-session grants and wildcard-principal/`aws:PrincipalArn` forms. Direct session grants have important implicit-deny exceptions; that is not permission to transplant those rules into cross-account access. Preserve the original statement form, immutable principal ID, issuing role and session separately. An account-root principal normally delegates to an account, not only its root user; `aws:PrincipalArn` for an assumed role is the role ARN. ([Detailed evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html); [principal forms](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html); [PrincipalArn](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-principalarn))

Ordinary cross-account resource access needs both sides' authorization. SCPs constrain applicable member-account principals; RCPs constrain supported member-account resources, including relevant outside access, with documented exceptions. Evaluate inheritance and current action/resource support, not an old launch-era list. Separate direct service principals, service roles, service-linked roles and forward access sessions; an endpoint policy is an additional path control, not identity authorization. `PassRole` requires a compatible service/configuration path and trust and has no standalone API/CloudTrail event; inspect the actual create/update operation. An explicit deny that defeats the **same principal/action/resource/context** is a real defeating control, not an invitation to evade it; a separately authorized service-mediated identity transition is a different operation requiring its own proof. ([Cross-account](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html); [SCP](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html); [RCP](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps.html); [FAS](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md); [endpoint policy](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-access.html); [PassRole](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_passrole.html))

For Azure, the **proposed review facets**, not a certified evaluation algorithm, are Entra identity/consent versus Azure resource RBAC; control-plane Actions versus data-plane DataActions; assignment scope/inheritance, conditions, deny assignments, Azure Policy effects and authentication mechanism; managed identity audience; and the actual Key Vault RBAC versus access-policy mode. For GCP they are organization/folder/project/resource inheritance, allow/deny/conditions, principal sets and group visibility, organization policy/service perimeter, service account impersonation versus direct federated grants, workload mode and applicable OAuth scopes. Do not project AWS boundaries/SCP/session exceptions onto either provider. Their primary documentation and deployed-state checks are **pending before provider-specific implementation**. ### Current defaults are invalidation inputs, not target observations

AWS documents private creation defaults and Bucket owner enforced for new S3 buckets, but existing buckets require actual snapshots. Effective BPA now includes organization policy as well as applicable account/bucket/access-point controls. `BlockPublicPolicy` rejects new applicable public policies; it does not itself retroactively neutralize every old policy. `IgnorePublicAcls` and disabled ACLs can make persisted public ACLs ineffective. Encryption at rest is not a privacy deny: S3's new-upload SSE-S3 baseline dates to 2023, and SSE-KMS object access still requires its specific authorization path. These facts invalidate stale “public ACL therefore exposed” or “unencrypted by default” reasoning without assuming any target is secure. ([BPA options](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html#access-control-block-public-access-options); [Object Ownership](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html); [SSE-KMS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html))

Current AWS documentation describes KMS grants with service-principal/SourceArn fields and additional AWS RAM key-policy paths; the model must not freeze an older schema or assume every key has only one possible policy source. KMS `CreateGrant` provenance, allowed operations and constraints matter, and grant propagation is eventually consistent. S3 Bucket Keys can reuse a short-lived bucket key without a fresh KMS API call/key-policy evaluation for every benefiting request. Consequently, immediate revocation claims and “missing KMS event means no object read” require temporal qualifications, not a guessed cache-expiry guarantee. ([KMS policies](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html); [CreateGrant](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateGrant.html); [grants](https://docs.aws.amazon.com/kms/latest/developerguide/grants.html); [Bucket Keys](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html))

`GetCallerIdentity` is a documented attribution special case even under its own explicit deny; it does not demonstrate a data-action deny bypass. Access Analyzer external findings reason about sharing outside a zone of trust, not actual access; organization-internal business violations can lie inside that zone. The retrieved simulator documentation describes more SCP support than older summaries but still excludes RCPs and warns of advanced-configuration differences. **Design:** store analysis type, supported resource set, supplied context and visibility gaps beside every helper result; none certifies complete effective permission. ([STS](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html); [Analyzer](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html); [simulator](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_testing-policies.html#policies_policy-simulator-how-it-works))

## Recursive depth follows capabilities rather than a hop cap

### D0 through D8+ are evidence rungs, not a maximum chain length

**Design:** a new relevant capability creates a new edge with its own exact assets, operation, evidence and readiness, recursively. D8+ explicitly permits further authorized cross-service/provider branches; it is not an eighth-hop limit. A case effort budget is scheduling, never evidence that a whole family/provider was covered. No requirement forces a sound confidentiality finding to become RCE, and no arbitrary “three tries” rule closes siblings.

| Rung | Work and exit evidence | Reopen or refuse the claimed inference when… |
|---|---|---|
| **D0 Hint** | Preserve source-qualified reference/check/config lead and intended boundary question. | Source missing, pattern alone, copied severity or no candidate resource. |
| **D1 Ownership/current reachability** | Exact owner/resource/version/path and source time; separate asserted ownership from current observed route. | DNS/IP/name-only attribution, historical reference, unapproved destination. |
| **D2 Baseline** | Owner B performs intended operation; A's direct baseline and app/identity/session context captured. | Wrong object, stale session, broken fixture, unknown side effects or incomplete capture. |
| **D3 Exact boundary** | Resolve relevant policy/trust/network/consumer prerequisites and defeating controls; record unknowns. | Unsupported semantics, missing policy visibility, applicability disagreement. A bounded operation can still be observed without claiming global policy completeness. |
| **D4 Controlled read/write** | Fresh canary read or reversible write with before/test/after readback, true negative control and actual source receipts. | Success status without marker/effect; list substituted for read; owner access used as negative control. |
| **D5 Derived identity/effective permission** | Independently bind resulting session/workload principal; one permitted canary action establishes the new capability. | Token-shaped string, chosen session label, identity-only result or inherited assumption of admin. |
| **D6 Privileged consumer execution** | Exact artifact/revision consumed, trigger/run observed, actual execution identity and terminal canary effect. | Bytes merely stored, wrong alias/digest, preseeded owner action, no trigger/downstream result. |
| **D7 Owned cross-account/tenant/project** | Both controlled scopes granted; prove entry/identity and target canary operation separately with bilateral lineage. | Outside scope, unknown target ownership, same-provider hostname or class coincidence. |
| **D8+ Terminal impact, replay and cleanup** | Smallest sufficient synthetic consequence, clean-start replay/new marker, one-edge counterfactual, legitimate positive control, restored denial and cleanup/cost receipts. | Missing intermediate edge, replay/control contamination, unresolved access/retention/cost or merely imagined harm. Further relevant branches recurse at D1–D3. |

For each next edge compute `ready = authorized ∧ owned-bound ∧ operation-known ∧ prerequisites-supported ∧ channel-connected-approved ∧ budget-available ∧ observable ∧ reversible/cleanup-owned`. The result is edge-specific `ready`, `unknown`, `blocked-*` or `negative-for-variant`, never “cloud impossible.” A technical data-plane deny is recorded faithfully; changing the blocking control is a separate hypothetical mutation, not an automatic next action. Cycle detection keys principal/session, action, exact resource/version and context/policy snapshot, not a fixed number of hops. Continue only when a new capability or causal test adds meaningful information.

### Three first work items unlock useful depth before transport automation

**First build the typed ownership/identity/source graph; second build the exact-operation evidence/readiness/cleanup ledger; third build one pinned Prowler export adapter with gap-aware worklists and class handoffs.** These priorities support storage/delegation, identity/trust and artifact-consumer hunts immediately in planning and owned evidence review, without promising scanner execution. ### Gates distinguish software correctness, provider behavior and judgment

**Gate A** is deterministic offline engineering acceptance. Require explicit requirement→fixture→assertion→result→limit mappings for schema/migrations, no partial writes, provider-native identities and aliases, strict source/version adapters, scanner verdict versus lifecycle, aggregate versus resource results, denied/missing/paginated inventories, unsupported conditions as unknown, action/method/sensitive-read readiness, expiry/audience, exact deny applicability, expired SAS/signed URL scope false positives, independent controls, tamper/symlink rejection, stale facets, lineage and root grouping. Guard sockets/subprocess/SDK/browser/model calls and assert no target queuing. Accounting tests include native-measured versus external-declared API calls, retries/polls/pagination/token exchanges/unknown sends, no import double charge, object/runtime/storage commitments and cost labels. Offline accounting must never claim to constrain an unmediated SDK.

**Gate B-local** runs owned loopback/emulator vulnerable and matched fixed fixtures with independent readback, replay, legitimate positive control, distinct expected-denied control, cleanup and stale/verify/report round trip. Cases include storage/delegation, wildcard defeated by deny/condition, identity-only success, public service with protected data, artifact accepted but unconsumed, wrong runtime identity, missing capture and unresolved teardown. **Gate B-cloud** is a separate actual sandbox exercise: current rules/policy, deployer versus participant, exact resources and operation caps, real provider identity/audit/canary/control receipts and independent residual resource/access/cost reconciliation. A local policy emulator never certifies AWS/Azure/GCP IAM. No gate is claimed passed here.

**Gate C** tests model/skill judgment on fictional/redacted adversarial cases, not live targets. Predeclare expected fact/unknown/owner/next-edge/stop outcomes. Compare the same model/rules against a truly isolated without-skill baseline, retain outputs/model/run metadata and invalid runs, and exclude contaminated baselines rather than rebranding them as improvement. Require zero critical authorization/evasion/false-confirmation errors in the acceptance set and report all other failures/denominators. Static JSON fixture tests are not behavioral evaluation. Preserve the historical **674-test** checkpoint; future work must rerun the full then-current suite and record actual interpreter/date/count/skips, with no invented expected new test count. ## Conclusion

The important engineering change is the **unit of evidence**: a cloud hunt concerns an exact principal/session operation against a versioned owned resource, not a hostname or failed control. That change makes deeper investigations more credible because every new identity, workload consumer, copy and account transition can be proved independently and refuted without erasing sibling hypotheses. It also exposes the genuinely missing work—resource scope anchors, provider semantics, external accounting and execution mediation—instead of hiding it behind a scanner integration.

The next decision is therefore not which scanner to run broadly. It is which approved environment and three canary paths will establish the first useful boundaries: **private storage/delegation, usable identity/trust, and stronger artifact consumption**. The practical worksheet and two-week example in [the canonical plan](../plans/cloud-misconfiguration.md#first-hunt-worksheet-and-day-one-checklist) turn that decision into finite work while retaining every deeper permitted branch. Until an owner supplies scope, principals, sample exports, execution approval and cost/cleanup authority, those branches remain explicit engineering/hunt plans—not fabricated target results.
