# Web cache deception poisoning plan

**BugVault should investigate web cache poisoning and web cache deception as two different, controlled failures of response reuse, not as a cache-header checklist.** Poisoning requires attacker-controlled input to change an origin representation while a shared cache omits that determinant from its effective key and later serves the stored result to a separate owned viewer. Deception requires an authenticated, intended-private representation to be routed by the origin while an intermediary treats the same request as cacheable/static and later serves it to a lower-privilege owned or anonymous viewer. The safest next step is an offline, exact-request/context evidence worklist followed by vulnerable-and-fixed owned-loopback fixtures; a live pilot needs separate written campaign authorization, isolated keys, two test identities, an approved observation channel, budget and verifiable expiry or targeted cleanup. **Research date: November 16, 2026.** “Cache decryption” is interpreted here as **cache deception**; please correct that interpretation if cryptographic decryption was intended. No unit tests or target requests were run for this docs-only synthesis; neither these sources nor this work verified a target, a deployed provider configuration, a network cache test or permission to run one. ([PortSwigger poisoning](https://portswigger.net/web-security/web-cache-poisoning); [PortSwigger deception](https://portswigger.net/web-security/web-cache-deception); [local audit](../research_notes/Web%20cache%20deception%20poisoning%20plan/bugvault-audit.md))

## Two causal chains require different proof and different harm assessments

**Poisoning is a key-completeness failure coupled to origin influence and shared persistence.** First identify one exact, disposable, independently isolated cache key; then establish on a cold request that an inert value in one query field, request header, nonidentity cookie, path component or other *permitted* input changes an origin-produced body or `Location`. Show that the relevant serving cache treats A's marked request and V's clean request as the same effective key, stores the altered representation, and serves A's marker to V after A's request has completed, with V sending no marker or trigger. The consequence may be an inert cross-viewer representation change; XSS, redirect abuse, script delivery and wider blast radius need separate evidence and are **not** entailed by a harmless marker. A reflection seen only by A, a forwarded-but-unkeyed field the origin ignores, or an ordinary public asset correctly served from cache is not poisoning. Historical PortSwigger case studies show possible gadgets, not present-day behavior at any campaign. ([PortSwigger poisoning methodology](https://portswigger.net/web-security/web-cache-poisoning#constructing-a-web-cache-poisoning-attack); [Practical Web Cache Poisoning, published 2018 and updated 2025](https://portswigger.net/research/practical-web-cache-poisoning); [OWASP risks](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#key-risks))

**Deception is a cache-eligibility and origin-routing mismatch that crosses a privacy boundary.** On a V-owned account, the origin must produce a V-specific, intended-private raw response at an ambiguous, static-looking URL; a shared layer must then retain it and serve that exact URL to an independently controlled low-privilege A or anonymous context. V priming and A retrieval reverse the actor order of poisoning. A static extension alone, a private page loaded only in V's own browser, an intentionally public document or direct origin access available to A without priming does not establish the mechanism. Deception can expose sensitive private information; the safe proof uses a short **V-only synthetic marker**, not a real session token, billing record or other user's data. If the lower viewer can fetch V's marker at an unprimed canonical/private URL, investigate authorization/IDOR or an application data cache separately before claiming deception. ([PortSwigger deception](https://portswigger.net/web-security/web-cache-deception); [OWASP application-cache and complete-path guidance](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#6-protect-application-level-caches))

The baseline matters because **HTTP caching is optional and provider-specific**. RFC 9111 defines a minimum key of request method and target URI, with `Vary` selecting representations and freshness or validation governing reuse; it does not promise storage. A conforming cache respects response `no-store`, a shared cache cannot store an unqualified `private` response, and `no-cache` allows storage but requires validation before reuse. The `Authorization` request-header rule restricts shared reuse absent an explicitly permitting response directive (`public`, `s-maxage` or `must-revalidate`); cookie-based sessions have no identical blanket rule, `Vary: Cookie` is not a substitute for authorization, and `Set-Cookie` alone does not prohibit HTTP caching. A private HTTP/browser cache, a service worker's Cache Storage, an application/fragment cache and a CDN/reverse-proxy cache are distinct hypotheses with distinct reportability; a second independently controlled network client and layer evidence are needed for a **shared** cache claim. A true browser-only or private-cache anomaly should not be relabelled CDN deception merely because a page reappears. ([RFC 9111 §§2–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-2); [RFC 9111 authenticated responses](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5); [RFC 9111 sensitive information](https://www.rfc-editor.org/rfc/rfc9111.html#section-7.3); [OWASP key design](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#2-design-a-complete-cache-key); [service-worker versus HTTP cache](https://web.dev/articles/service-worker-caching-and-http-caching))

## Isolated, exact request shapes determine endpoint priority

**Safety and discriminating evidence outrank traffic volume.** Begin with existing authorized captures, application documentation and owner-provided test-only routes; rank a public read-only marker surface only when a distinct key and expected origin output can be established without contaminating ordinary traffic. Do not infer that `/me`, a `.css` suffix or a CDN banner is presently cacheable. Record scheme, authority/port, *literal* path bytes and ordered query (including duplicate names and encodings), method, content negotiation, auth/cookie presence and separate A/V role/tenant/workflow labels. Treat query, header, cookie, path, authority/forwarding and method/body as **different input locations**: origin forwarding, effective keying and cache eligibility each require their own observation. Existing BugVault endpoint families and sorted-query-name variants cannot serve as cache-key oracles. ([RFC 9111 key and `Vary`](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [PortSwigger implementation flaws](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws); [local request-shape limits](../research_notes/Web%20cache%20deception%20poisoning%20plan/bugvault-audit.md))

| Priority and endpoint family, **not a discovered target** | Exact input/representation question | Required contrast and permission/risk |
| --- | --- | --- |
| **P1: disposable, public HTML** such as an owner-supplied help/preview page | One known `?view=`/`?lang=` value or inert header changes server HTML, metadata or an in-scope link. | Fresh keyed K1 versus distinct K0; origin marker with/without the field, then independent clean V on K1. GET/read grant and isolated URL first; never prime a shared homepage. |
| **P2: semi-dynamic HTML and localized/device/theme variants** | `Accept-Language`, `Accept`, device header, nonidentity `locale`/`theme` cookie, or query `?theme=` changes a representation. | Match every other `Vary`/representation field; compare same-language and changed-language keys. A legitimate keyed language variant is a negative, not a flaw. No identity-bearing cookie leakage. |
| **P3: read-only API/JSON and captured GraphQL-over-GET** | Exact `?view=`, `?tenant=`, `operationName`, persisted-query ID or variables alter a response; query order/duplicates remain explicit. | Establish a captured, nonmutating operation and server-generated marker, then key/`Vary` contrast. Tenant and session output belong in the private-data lane unless a separately isolated, expressly approved own-account comparison exists. GraphQL POST is a separate method/case. |
| **P4: redirects, canonicalization and errors** | `?next=`/`?return=` or `Forwarded`-derived scheme/host changes an in-scope `Location`; an owned missing path yields a marked 3xx/4xx body. | Compare raw response and `Location` without auto-following; distinguish origin error from edge/WAF error. Seed a harmless owned marker only by an approved normal workflow; GET retrieval is not authorization for marker creation. |

Verify read-only operation, V-only intent, raw body and same-key lower viewer; GraphQL POST is not implied by GET approval. |

This is a **worklist**, not an instruction to try every field or extension. Static extension, directory-prefix and exact-filename rules, delimiter interpretation, decoding, dot segments and browser URL rewriting are competing explanations for a deception candidate. A delimiter test must first distinguish the canonical private response from an arbitrary suffix or SPA fallback; a path that returns an identical app shell without the V marker is not a private origin route. The 2024 research supplies hypotheses, not a universal parser fingerprint, and the program's written URL/path restrictions still apply to every encoded spelling. ([PortSwigger path/delimiter cases](https://portswigger.net/web-security/web-cache-deception#path-mapping-discrepancies); [Gotta Cache ’Em All, published 2024 and updated 2026](https://portswigger.net/research/gotta-cache-em-all); [OWASP route/key design](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#2-design-a-complete-cache-key))

## Cold-fill and second-viewer ladders establish causality, not headers alone

**Both ladders start with an isolation preflight, not a marker prime.** In a *future approved run*, choose K1 plus genuinely distinct unprimed K0 and K2 under a disposable, owner-known namespace; prove separation from the effective key/configuration or layer-local observations, not merely from different-looking URLs or two `MISS` labels. Hold method and representation selectors constant and explicitly identify the auth determinant that must differ between contexts. Establish freshness/TTL and the affected layer sufficiently to plan a bounded serial read and cleanup. A query “cache buster” is not isolation until shown keyed; an internal fragment cache can cross URL boundaries even if an edge key is isolated. If a collision could affect production visitors, **stop before any prime**. ([PortSwigger cache-oracle method](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws#cache-probing-methodology); [Web Cache Entanglement, updated 2025](https://portswigger.net/research/web-cache-entanglement); [RFC 9211 per-cache semantics](https://www.rfc-editor.org/rfc/rfc9211.html#section-2))

### Poisoning: A changes the origin output; V omits A's input

| Ordered rung | What the future operator must establish | Distinct falsifier or bounded stop |
| --- | --- | --- |
| **P0 — baseline and key** | Cold K1/K0/K2 provenance; one owned public representation and a normal public-cache positive control; recorded effective-key hypothesis and owner/edge logs where available. | Unknown key, prepopulated key, global fragment overlap or unapproved shared path ⇒ no prime. |
| **P1 — origin influence** | On a fresh K1 miss, A supplies one short inert marker M through the chosen input. Origin receipt/controlled route contrast ties M to a **raw body or `Location` generated upstream of the serving cache**; an input-absent fresh control does not generate it. | Header reflected only by edge, DOM-only reflection, origin ignored field, or WAF/error response ⇒ no origin-influence conclusion. |
| **P2 — shared reuse** | After A's response completes, V in a separate owned network context requests the same *effective key* with no M or trigger; its raw response contains M in the corresponding component. Per-layer store/hit and no fresh origin generation distinguish persistent entry from direct reflection or collapsed concurrent miss. | A's own repeat, V sending M, different `Vary`/auth variant, origin-generated V response or only a 304 ⇒ inconclusive/negative for this mechanism. |
| **P3 — negative/replay/cleanup** | Unprimed K0 and K2 never yield M; a fixed/keyed/no-store or non-reflecting control fails to transfer M; if authorized, replay once with a **new** marker and fresh isolated key after reset. Retain expiry/purge receipts. | Control key has M ⇒ stop for contamination; exhausted budget/TTL or unverifiable residual entry ⇒ cleanup-pending, not a clean completion. |

### Deception: V primes private data; A retrieves it without V's authority

| Ordered rung | What the future operator must establish | Distinct falsifier or bounded stop |
| --- | --- | --- |
| **D0 — privacy and route** | V's canonical, raw server response contains only V's synthetic marker; own A/anonymous baseline at the canonical route and an unprimed isolated K0 denies or omits it. Compare a benign arbitrary suffix with **one** motivated static-looking path under K1; prove the origin still selects V's private handler. | Public sharing, SPA shell/redirect/static file, wrong object or direct unprimed A access ⇒ reclassify/park. |
| **D1 — V fill and shared decision** | V visits K1 by the approved browser/workflow, with exact request bytes, status, content type, `Vary`/auth context and V-marker position captured; edge/shield/origin evidence identifies any store and whether a static rule or override applied. | V does not receive its private marker or policy/rule/layer cannot be resolved ⇒ no deception-store claim. |
| **D2 — lower viewer** | After V's completed response, separately controlled low A or anonymous GET uses the same literal URL and representation selectors **without V credentials or marker**, retrieving V's marker in the raw response; no A-origin private generation and shared-layer evidence are sought. | A's request gets a login page, its own marker, a different key, a 304 with no proven bytes, or a private browser hit ⇒ no shared disclosure proof. |
| **D3 — negative/replay/cleanup** | A's unprimed K2 lacks V's marker; canonical A remains denied; fixed route/no-store/keyed-cache control and a public static positive control discriminate the cause. If allowed, fresh marker/key replay; targeted expiry/purge and marker removal have independent receipts. | Residual V entry or unowned data ⇒ stop and escalate cleanup, not another path or broad invalidation. |

An `Age`, `X-Cache`, `Cache-Status` or `CF-Cache-Status` value **alone proves neither chain**. RFC 9211's optional `Cache-Status` lists caches origin-nearest first, with per-member `hit`, forwarding reason, `stored`, `ttl`, possible `collapsed` and an implementation-specific—not necessarily complete—`key`; one layer's hit does not identify every layer or the body owner. `Age` is a calculated age across caches; vendor statuses have vendor-specific meanings, and a concurrent collapsed request can look like a hit. Avoid adding request `Cache-Control: no-cache`, `max-age=0`, conditional validators or a “force origin” header to the primary B/A read unless that change is *itself* the recorded contrast: they can change forwarding and do not purge stored responses. Repeated reads are justified only to distinguish completed persistent reuse from a transient/in-flight event within a bounded freshness window; no timing races or warming loops. ([RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [RFC 9111 freshness and Age](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2); [CloudFront request collapsing](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html#request-custom-traffic-spikes))

## An offline evidence ledger must precede wiring and any pilot

The local audit finds **no installed cache module or skill, cache case ledger, cache CLI, cache-specific coverage row, active cache test, configured live campaign or connected browser-control tool**. Existing imports still offer useful surface leads, but HAR normally retains field names and status rather than ordinary raw cache header values or bodies; Burp import stores response-header **length placeholders**, not their values; native stored responses have header maps and bodies but can collapse repeated header lines and do not automatically carry A/V account labels. Static-looking `.css` routes can be missed by the endpoint census, while endpoint families and query-name-only variants lose exact key candidates. Scan *stored responses as well as endpoints* in a future offline adapter, keep imported source/entry/hash and native `target-http` receipts distinct, and never fabricate a cache trace or a native response ID from a Burp ID. These are repository facts from the dated audit, not a newly run test suite. ([local audit](../research_notes/Web%20cache%20deception%20poisoning%20plan/bugvault-audit.md); [native/import boundaries](../recon/README.md#skill-triggers-and-the-request-executor))

**Proposed, not installed:** use a campaign-private, append-only ledger keyed by exact origin, literal path and ordered query (including encoding/duplicates), method and representation selectors, tested input *location/name*, owned object, separate A/V/anonymous account-role-tenant-workflow/session labels, candidate cache layer and case variant. Source records should include capture channel and basis, original file/entry selector and SHA-256, time, complete/partial status and raw-versus-decoded-body qualifications. Request authorization/cookie values stay private or fingerprinted; preserve lossless cache-relevant response-header occurrences in a restricted artifact only with a privacy grant and expose a value-free projection by default. Record separately the proposed key, origin-influence fact, key-equivalence fact, cache store/serve attribution, raw marker transfer, privacy intent and demonstrated effect, each with evidence references and unknowns. Case events remain `candidate`, `observed`, `negative`, `inconclusive`, `blocked`, `stale` or `cleanup-pending` as appropriate, without collapsing sibling path, query, Vary, auth or layer variants. Hash-bound baseline, cold-fill, second-viewer, distinct negative, replay, owner log and cleanup receipts, source/policy freshness checks, and declared/manual cross-channel attempt accounting are required; an imported scanner issue or one positive predicate never advances a finding. ([local schema proposal](../research_notes/Web%20cache%20deception%20poisoning%20plan/bugvault-audit.md#3-staged-offline-build-and-acceptance-contract-proposal-nothing-implemented-here); [RFC 9211 trace limits](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [BugVault evidence gate](../recon/prompts/validator.md#gate-in-order-stop-at-the-first-failure))

A future ledger grant checks evidence *recording readiness*, never authorizes traffic. Stop for unknown isolation, out-of-scope path/hop, 429/5xx/challenge, unexpected real-user data, lost observer, cap exhaustion or unresolved cleanup, and do not change clients to bypass a stop. The existing finding lifecycle still needs a clean replay, independent negative control, real owned-context consequence and reportability review; marker transfer alone does not show real-person harm or a complete XSS/ATO chain. ([scope policy](../.claude/skills/scope-policy/SKILL.md); [browser workflow](../.claude/skills/scope-policy/references/browser-workflow.md); [Burp accounting](../.claude/skills/scope-policy/references/burp-workflow.md#authorization-and-execution-boundary); [validator](../recon/prompts/validator.md))

The unresolved design questions are concrete: which program rules permit cache mutation and anonymous retrieval; who owns the cache/edge/shield, key-debug and purge mechanisms; what literal path and query survive browser and proxy rewriting; which policy revision and TTL govern the candidate; can a test-only key be distinguished from every public and fragment-cache key; and what private data class and V/A roles may be used without collecting secrets? Until answered with owner or authorized capture evidence, preserve a **blocked or inconclusive** case rather than asserting a provider default, a target flaw or endpoint-wide coverage. The stand-alone engineering handoff is [plans/cache-deception-poisoning.md](../plans/cache-deception-poisoning.md). ([OWASP complete-path guidance](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path); [RFC 9211 optional visibility](https://www.rfc-editor.org/rfc/rfc9211.html#section-2))

## Conclusion

The most valuable future cache observation is not a `HIT`; it is a **source-qualified change in who receives which bytes, through which layer, under an independently isolated key**. That framing lets BugVault discard benign public caching and browser-local reuse early, hand direct authorization failures to the correct class, and reserve risky shared-cache mutation for a narrowly approved, reversible experiment. Until the offline contract and owned fixtures exist, a cache-looking capture should enrich the backlog without creating the illusion of either permission or a confirmed vulnerability.
