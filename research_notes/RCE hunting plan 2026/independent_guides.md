# Four independent guides for authorized RCE hunting (reviewed 2026-11-20)

## 1. Which four independent guides provide the most useful primary guidance?

### Takeaway
Use one publisher-distinct page for each major path. These are guidance on where to look and what evidence means, not claims that a particular target is exploitable. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide); [ImageMagick](https://imagemagick.org/security-policy/)

### Cited Findings
- **Command injection — PortSwigger Ltd., Web Security Academy, “OS command injection.”** Exact URL: https://portswigger.net/web-security/os-command-injection . No individual author or page publication/last-updated date was verified; the footer’s © 2026 is not a page-update date. The page distinguishes visible command output from blind cases where response timing or an out-of-band interaction is the observation. Its practical insight is to choose an observable channel appropriate to the application’s actual response behavior rather than treating absent output as a negative result. — [PortSwigger](https://portswigger.net/web-security/os-command-injection)
- **Template injection — OWASP Foundation, *Web Security Testing Guide*, WSTG-INJT-18, “Server-side Template Injection.”** Exact URL: https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/ . No individual author or page update date was verified; `/latest/` is mutable, and the © 2026 footer is not a revision date. Its practical insight is to distinguish free-text template context from input already inside a template statement and observe evaluation in a *server response*; syntax may be expression-based or directive-based, and a result that prints nothing is not automatically a negative. — [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/)
- **Unsafe deserialization — Microsoft Learn / .NET documentation, “Deserialization risks in use of BinaryFormatter and related types.”** Exact URL: https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide . Fetched page metadata names `GrabYourPitchforks` as `author` and `levib` as `ms.author`, with `ms.date: 2022-03-02` and `updated_at: 2024-11-13`; these are documentation metadata, not independently verified dates of each claim. Its practical insight is to trace whether untrusted bytes actually reach an unsafe deserializer in the deployed runtime: `BinaryFormatter.Deserialize` is unsafe for untrusted input, but the in-box implementation always throws starting in .NET 9, so an API name or old payload format alone is not execution proof. The guide also names other unsafe polymorphic serializers and warns a binder is not a complete fix. — [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)
- **File processing / upload-to-processor path — ImageMagick Studio LLC, “Security Policy.”** Exact URL: https://imagemagick.org/security-policy/ . No individual author or publication/last-updated date was verified; version numbers on the page describe software behavior, not page dates. Its practical insight is to inspect the **effective** deployment policy and the processor path, not merely an upload endpoint: coders, external delegates, indirect reads, resource limits, rule order, and restrictions on web-safe formats differ by configuration; ImageMagick documents a way for operators to inspect the active policy. — [ImageMagick](https://imagemagick.org/security-policy/)

### Inferences
- These four pages are independent publisher-hosted guidance, not GitHub pages or mirrors of selected repositories; together they support sink-and-consumer mapping before any impact test. That is a synthesis of the command, template, runtime and image-policy guidance, **not** a claim that any particular bug bounty target has RCE. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide); [ImageMagick](https://imagemagick.org/security-policy/)

### Gaps
- The selected PortSwigger, OWASP, and ImageMagick pages did not expose a verified per-page publication or revision date in the retrieved material; do not substitute a copyright year, `/latest/` path, or software version. The Microsoft metadata does not establish when each individual passage changed.

## 2. What is a safe, actionable hunting sequence for an authorized program?

### Takeaway
Inventory concrete input-to-execution paths offline, reproduce the mechanics in an owned lab, and only then run a few explicitly approved, inert, context-specific checks against an in-scope workflow. Preserve controls, exact request/response provenance and cleanup; do not spray payload lists or infer permission from these guides. This is a conservative synthesis of the four sources, not a tested procedure. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide); [ImageMagick](https://imagemagick.org/security-policy/)

### Cited Findings
- PortSwigger’s stock-check example reaches a shell because the application supplies user values as command arguments; its blind feedback example may execute a command without returning output in HTTP. Therefore the initial review question is whether a captured parameter reaches a command invocation, including an asynchronous consumer. — [PortSwigger](https://portswigger.net/web-security/os-command-injection)
- OWASP identifies user-editable markup and template-bearing workflows (for example reviews, wiki content or CMS features), and recommends separating text context from code context while observing server responses. A literal string or harmless arithmetic check in a lab is a narrower first observation than an execution attempt; the page’s broader exploit guidance is **not** a standing authorization to pursue RCE on a live target. — [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/)
- Microsoft identifies the key deserialization trust boundary: data sent over a network, stored in a file or synced across machines can later become input to a deserializer. An inventory should include delayed file/import/session-state consumers, and code review should verify the deployed formatter and runtime behavior rather than guessing from a serialized-looking client value. — [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)
- ImageMagick documents public-facing image processing, delegate/coder restrictions, sandboxing and resource caps; it describes a production policy where delegates and certain scripting/vector/URL-capable formats are restricted. Map upload, conversion, preview and derivative creation as separate stages, and ask the system owner for the active policy and processor logs when available. — [ImageMagick](https://imagemagick.org/security-policy/)

### Inferences
- **Lab-first plan:** for each route, record exact field, method, account, output/worker, format and consumer; reproduce only the suspected mechanism with inert marker fixtures in an owned local service; compare baseline, one changed input, a distinct negative control and a repeat; then stop at the least-impact observation the written program permits. This combines the sources’ distinctions between reached sinks, asynchronous processing, deployed runtime and effective policy; it is a recommended validation design, not a test the guides themselves performed. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide); [ImageMagick](https://imagemagick.org/security-policy/)
- Prioritize a demonstrated server-side consumer over superficial filename, extension, syntax, header or serialized-format clues. For uploads, a marker in a derivative supports processing; a marker merely in an upload acknowledgement supports only intake. For deserialization, a reachable unsafe API is an exposure lead until actual deployed behavior is established. — [ImageMagick](https://imagemagick.org/security-policy/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)

### Gaps
- These public guides do not supply any particular program’s written scope, allowed methods, callback permission, request budget, processing environment or cleanup agreement. Without those, keep the plan offline/owned-lab only; no live target, callback or scanner action is justified by the research itself.

## 3. Which observations establish server execution, and which remain ambiguous?

### Takeaway
Classify client-only effects, server-side evaluation, processor attribution and OS execution separately. A repeatable, controlled server effect is stronger than a syntax match, timing change, acceptance response or callback, but RCE needs an attributable execution path and an authorized minimal impact demonstration. This is an evidence-standard inference, not a claim made verbatim by any one page. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide); [ImageMagick](https://imagemagick.org/security-policy/)

### Cited Findings
- **In-band versus blind:** PortSwigger distinguishes direct command output in HTTP from blind command execution whose output is not returned; it discusses response delay and out-of-band DNS interaction as indirect channels. Those channels report different facts and should not be collapsed into “command output observed.” — [PortSwigger](https://portswigger.net/web-security/os-command-injection)
- **Server template evaluation versus RCE:** OWASP’s illustrative arithmetic is evaluated by a server-side Jinja2 template and appears in the HTTP response; OWASP separately discusses identifying the engine and building an RCE exploit. Thus evaluation of a harmless expression establishes a template-evaluation lead, not arbitrary OS-command execution. Directive assignment can also be silent unless a separate output makes it observable. — [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/)
- **Environment-specific deserialization:** Microsoft states unsafe deserialization can lead to DoS, disclosure or RCE, not that every deserialization event causes RCE; it notes .NET 9’s changed default `BinaryFormatter` behavior. Establish the actual implementation, version, whether untrusted data reaches it, and the relevant application object graph before any consequence claim. — [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)
- **Environment-specific file processing:** ImageMagick’s default/open policy and hardened options have different coder, delegate, path and resource rules; the operator can inspect the active policy. A file being received, stored, converted or served does not by itself identify which delegate or process ran, let alone prove attacker-controlled OS execution. — [ImageMagick](https://imagemagick.org/security-policy/)

### Inferences
- **Client-side signs:** if a browser UI shows a calculated value but the saved raw HTTP response retains the original literal and the computation appears only after DOM rendering, classify it as possible client-side template behavior, **not SSTI/RCE**. A server-produced, repeatable result absent from a distinct literal control is stronger evidence of server-side evaluation; worker logs may be needed for delayed email/export surfaces. This is a proposed attribution control derived from OWASP’s emphasis on server responses, not a claim that OWASP’s page tests browser-side rendering. — [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/)
- **Blind/OOB ambiguity:** a delay may reflect application scheduling or network variation; a DNS callback may reflect a fetcher, delegate or other service rather than a shell. Use unique attempt identifiers, baseline/negative-control windows, replay and—if the owner can provide it—process or worker logs linking the attempt to the specific consumer. Do not send callbacks unless the program explicitly authorizes the destination and channel. This is a conservative inference from PortSwigger’s indirect channels and ImageMagick’s distinct delegate/URL processing capabilities. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [ImageMagick](https://imagemagick.org/security-policy/)
- **Reporting ladder:** mark reflected/syntax/client-only behavior as a lead; mark controlled raw server evaluation or documented processor action as a stronger, still path-specific observation; claim RCE only when an authorized, minimal, attributable server-side execution effect survives replay and a distinct negative control. Avoid gadget chains, secret reads, destructive commands and high-volume timing probes in a bounty environment. This is a safety recommendation synthesized from the four sources, not a demonstration of exploitability. — [PortSwigger](https://portswigger.net/web-security/os-command-injection); [OWASP WSTG](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/07-Injection/18-Server-side_Template_Injection/); [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide); [ImageMagick](https://imagemagick.org/security-policy/)

### Gaps
- No source provides a universal timing threshold, a callback-to-process attribution rule, a cross-engine template fingerprint, or the effective security policy of an unknown target. No live requests, lab run or RCE confirmation were performed for these notes.
