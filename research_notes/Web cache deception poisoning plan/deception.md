# Web cache deception: offline investigation design

## Which authenticated endpoint families merit review, and where are the safety boundaries?

### Takeaway

Interpret the request's “cache decryption” as **web cache deception** (WCD), provisionally; this is not cryptographic decryption, and it is distinct from poisoning a public cache entry. Prioritize an authorized, read-only route whose *private, server-generated* representation can contain one harmless marker belonging to researcher-owned account V; the sensitivity of a real token or invoice is a reason to restrict the test, not to retrieve one. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception)

### Cited Findings

- Published mechanism: WCD is an origin/cache interpretation mismatch that stores private dynamic content under a seemingly static URL and then serves it to a different requester. Poisoning instead changes a cached response by manipulating an input/key relationship. The Academy recommends starting with sensitive dynamic responses and usually `GET`, `HEAD`, or `OPTIONS`, but does **not** establish that any particular production endpoint is cacheable. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#constructing-a-web-cache-deception-attack)
- Published cache policy: `no-store` forbids storage by a conforming HTTP cache; an **unqualified** `private` forbids storage by a conforming shared cache while allowing a private one (field-qualified `private` has narrower semantics); `no-cache` allows storage but requires successful validation before reuse. A session cookie or `Set-Cookie` alone does not make an otherwise cacheable response private. — [RFC 9111 §§3, 5.2.2.7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.7); [OWASP response classification](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#1-classify-responses-before-caching)
- Published caveat often missed in endpoint ranking: RFC 9111 separately prohibits shared-cache reuse of a response to a request carrying `Authorization` unless a response directive explicitly permits it (`must-revalidate`, `public`, or `s-maxage`); this special rule concerns that header, not cookie-based authentication in general. — [RFC 9111 §3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5)
- Published scope of caching: HTTP caches most commonly store `200` GET representations, but can also store redirects, some errors, partial content, and other methods where permitted. `HEAD` is useful for metadata but alone cannot prove body-marker disclosure; a `302` or `404` can be a cache observation rather than a successful sensitive-content leak. — [RFC 9111 §2](https://www.rfc-editor.org/rfc/rfc9111.html#section-2)
- Published defense: explicitly classify authenticated/personalized/tenant-specific routes, avoid broad static-extension caching, reject unexpected trailing segments on dynamic handlers, keep routing and authorization consistent, and test the *complete* cache path rather than assuming one CDN is the only cache. — [OWASP WCD guidance](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#4-prevent-web-cache-deception); [OWASP complete-path testing](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path)

### Inferences

- **Candidate inventory, not confirmed targets:** (1) `/me`, profile, preferences and account dashboard **GET** routes with a researcher-editable plain-text field; (2) a tiny owned private document/note or its read-only preview; (3) owned, nonfinancial export *retrieval* after a separately approved creation workflow; (4) known read-only GraphQL-over-GET or persisted-query operations whose selected fields include V's marker; (5) personalization/read-only account-specific JSON with observable identity differences. Record exact host, path, method, query-name/value semantics, auth mechanism, role/tenant, content type, status, response cache policy, source capture, and whether the marker is server-supplied rather than merely a client-rendered UI element. The grouping is inferred from the published dynamic-response and complete-key principles, **not** a claim that these route names or GraphQL GET are cacheable on a target. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#constructing-a-web-cache-deception-attack); [OWASP classification/key design](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#2-design-a-complete-cache-key)
- **Defer to a separate, stricter grant or skip:** session lists and security settings if they expose active sessions, reset links, MFA secrets or recovery codes; token/key pages, `/session`, `/refresh`, OAuth/SSO callbacks, signed URLs; payment instruments, billing details and real invoices; export generation (may be a write/job, large private dataset, or costly), admin/tenant-wide exports and other people's documents; mutations, password or security changes, logout/revoke, and any URL with a real secret in its path/query. A V-owned *non-secret marker* in an otherwise sensitive-looking representation proves the boundary without copying the real secrets. Separate, explicit authorization is needed for any write to seed or clean up the marker and for financial, identity or job-triggering routes. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#constructing-a-web-cache-deception-attack); [OWASP sensitive-response policy](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#1-classify-responses-before-caching); [RFC 9111 §2](https://www.rfc-editor.org/rfc/rfc9111.html#section-2)
- **Prefer a simple comparison:** an independently created V-only note/profile field over a live key, session identifier, invoice or bulk export; A is a second researcher-owned account with the same role where feasible, and an unauthenticated client is an alternative if the program permits it. If public sharing of the note is the product's intended behavior, choose another genuinely private route rather than calling that disclosure WCD. — [OWASP complete-path testing](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path)

### Gaps

- No campaign, written rules, actual account privileges, endpoint captures, data classifications, cost policy or approved test/browser channel were supplied. Thus no real endpoint can be ranked as vulnerable or even approved for live testing; token-, payment- and export-specific exclusions above are conservative design choices, not claims about a particular program.

## Which edge-versus-origin parsing and cache-rule hypotheses should be kept distinct?

### Takeaway

Build a per-operation discrepancy ledger, not a universal “append `.css`” recipe: first establish what the origin handler returns for a *single* changed request shape, then separately establish whether any shared cache stores and reuses that same representation. File extensions, path prefixes, exact filenames, delimiters, decoding, normalization, and query-key choices are separate hypotheses, with browser URL rewriting and multi-layer caches as confounders. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception); [Gotta Cache ’Em All](https://portswigger.net/research/gotta-cache-em-all)

### Cited Findings

- Published cache-rule families are static **extension**, **directory prefix**, and **exact filename** rules; a cache can also use custom response/path/query rules. In the Academy's path-mapping example, a REST-style handler can ignore an extra segment even though a cache sees a static-looking filename; the Academy warns this behavior may differ *between endpoints*. Its dedicated path-mapping lab is a deliberately vulnerable teaching example, not evidence about other hosts. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#path-mapping-discrepancies); [path-mapping lab](https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-path-mapping)
- Published delimiter method: compare the unmodified private route, an arbitrarily suffixed route, and that same suffix preceded by one candidate delimiter; only then ask whether a static-looking extension on that candidate is cached. `;` can be a matrix-variable delimiter in Spring; `.` can select a format in Rails. Neither framework label nor delimiter works universally. The delimiter lab specifically covers a static-directory rule rather than demonstrating one single suffix mechanism for all cases. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#delimiter-discrepancies); [path-delimiter lab](https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-path-delimiters)
- Published decoding/forwarding distinction: the edge might test cacheability on encoded bytes, then forward a decoded path; alternatively the origin might decode an encoded delimiter that the edge does not. A raw `#` fragment is not normally forwarded by a browser, while encoding can change the interpretation; browser URL transformations therefore matter before inferring a usable victim URL. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#delimiter-decoding-discrepancies); [Gotta Cache ’Em All, limitations/encodings](https://portswigger.net/research/gotta-cache-em-all)
- Published normalization distinction: origin-normalizes/edge-does-not and edge-normalizes/origin-does-not require *different* explanations. For a prefix rule, one branch has the edge retain a static prefix while the origin resolves encoded dot segments to a dynamic route; the reverse branch additionally needs a delimiter that truncates the origin's view. An exact-filename rule has its own constraints. The cache-normalization lab combines a directory rule, normalization and a delimiter; it is not proof that every CDN handles encoded slashes alike. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#exploiting-static-directory-cache-rules); [cache-normalization lab](https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-cache-server-normalization)
- Published key semantics: a cache key includes at least the method and target URI in the HTTP model; implementations can incorporate `Vary`-selected headers and other dimensions. RFC 9111 explicitly notes that a query string does *not* categorically bar heuristic caching. `Vary` governs response selection when its nominated request fields differ. — [RFC 9111 §§2, 4.1, 4.2.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1)
- Published research/provider limitation: *Gotta Cache ’Em All* measured examples of parser behavior and CDN defaults in its research setting, and emphasizes URL rewrites, configurable rules and browser limitations. Its vendor examples are leads to test in a given deployment, **not** a current provider fingerprint or a guarantee that a host's rule ordering, normalization, query inclusion or `Cache-Control` overrides match the paper. — [Gotta Cache ’Em All](https://portswigger.net/research/gotta-cache-em-all)

### Inferences

- **Offline candidate matrix (hypotheses, not payloads or findings):**

  | Contrast | Origin-side question | Edge/key-side question | What would disconfirm it? |
  | --- | --- | --- | --- |
  | Extra segment → extension | Does the exact authenticated handler return V's marker for an unexpected path segment, or reject it? | Is the *same* path eligible only when the added terminal extension matches a known static rule? | New handler, public static content, a redirect, error, or no shared reuse. |
  | Delimiter → extension | Does a suffixed control differ from base, while one delimiter + suffix preserves V's server response? | Does the edge treat bytes after that delimiter as part of a static-looking URL rather than truncate identically? | Base and arbitrary suffix are already identical; or both layers interpret the delimiter alike. |
  | Encoded delimiter/rewritten request | Is a decoded delimiter/rewritten path actually routed to the private origin handler? | Does eligibility/key calculation occur before the same decoding/forwarding step? | Browser strips/re-encodes it, edge rejects it, or response changes representation. |
  | Static directory / dot segments | Which layer resolves encoded slash/dot segments, and in what order relative to routing? | Is cache eligibility applied to a prefix the *origin does not use* for its final handler? | Both normalize identically; response never contains V marker; or extension rule explains a hit instead. |
  | Exact static filename | Does an origin delimiter preserve the dynamic handler while the edge sees an exact static filename after normalization? | Is the *specific filename* eligible rather than all similarly shaped paths? | A control filename is equally cached, suggesting a broader rule; or the marker is absent. |
  | Query / GraphQL GET | Do benign query values, operation selectors, variables, locale or representation headers alter the origin response? | Are those values actually in the key, `Vary` or neither; is a proposed buster genuinely keyed? | A proposed alternate key is the *same* cache key, or the response is legitimately public/partitioned. |

  These contrasts are derived from the Academy's separate rule/parser cases and RFC key model, not known target behavior. Limit future authorized checks to one well-motivated contrast at a time; do not turn the research paper's ASCII/extension discovery examples into an unapproved automated sweep. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception); [RFC 9111 §2](https://www.rfc-editor.org/rfc/rfc9111.html#section-2)
- **Parameter discipline:** record the *literal request target* as received on the network and the resulting `Location` separately from the browser address bar; retain each query shape/encoding and `Accept`/language/cookie/Authorization presence. A cache-buster is not an isolation control until shown to create a distinct key: if a layer ignores or reorders parameters, K0 and K1 might collide. Query values must contain no token or real private data, and GraphQL GET remains restricted to a known read-only, V-owned field selection. — [PortSwigger cache-key/buster discussion](https://portswigger.net/web-security/web-cache-deception#using-a-cache-buster); [OWASP key design](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#2-design-a-complete-cache-key)
- **Provider-agnostic comparison:** for each precise path/query/representation tuple, hypothesize origin route, edge eligibility, cache key, and observed `Cache-Control`/`Vary`; then measure each separately in a future authorized run. “Uses CDN X,” “has `.js`,” or “`Age` increased” alone cannot tell which layer served V's marker or which rule fired. An app/data cache may also leak despite a correctly configured HTTP `no-store`. — [Gotta Cache ’Em All](https://portswigger.net/research/gotta-cache-em-all); [OWASP application-level caches](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#6-protect-application-level-caches)

### Gaps

- No actual edge/origin logs or route rules, CDN configuration, multi-POP topology, query canonicalization, `Vary` behavior, browser forwarding capture or key debugger were supplied. Research examples cannot identify which parser/rule/order applies to a target; an opaque or missing cache-status header leaves the serving layer unresolved.

## How should own-account evidence, negative controls, stop conditions and cleanup be designed?

### Takeaway

Future testing needs a small, written-authorized, **isolated-key V→A** experiment with a synthetic V-only marker, an independent readback, an unprimed A/anonymous control and explicit evidence that the same shared cache key was served after V primed it. Cross-account content alone is not WCD: rule out intended public sharing, direct authorization failure, private browser/service-worker reuse and a redirected or unrelated representation before making a cache-mediated claim. — [OWASP complete-path testing](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path); [RFC 9211 cache telemetry](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [web.dev browser layers](https://web.dev/articles/service-worker-caching-and-http-caching)

### Cited Findings

- Published evidence signals: PortSwigger describes a unique cache key for each exploratory request, `X-Cache`/similar hit–miss indications and response-time differences, but notes a response policy such as `Cache-Control: public` alone is not proof that storage occurred. Its labs use victims for teaching; that pattern must be *replaced* with two researcher-owned accounts in bug-bounty work. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#using-a-cache-buster); [path-mapping lab](https://portswigger.net/web-security/web-cache-deception/lab-wcd-exploiting-path-mapping)
- Published standardized telemetry: RFC 9211 `Cache-Status` can describe multiple caches in order (origin-nearest first), `hit` means served without forwarding, `fwd` reports forwarding reason, `stored` reports a forwarded response was stored, and optional `key` is implementation-specific. It is optional, can be omitted for security, and a hit in *one* cache member does not automatically locate every layer's behavior. — [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2)
- Published cache interpretation: `Age` conveys an estimate of cached response age; freshness, revalidation and `Vary` can change whether a stored representation is reused. A request `Cache-Control: no-cache`/`max-age=0` can alter forwarding/revalidation and is not itself a purge mechanism or an uncontaminated same-key comparison. — [RFC 9111 §§4.1–4.3, 5.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4); [RFC 9211 `fwd`/`hit`](https://www.rfc-editor.org/rfc/rfc9211.html#section-2.2)
- Published cleanup caveat: changing a route to `no-store` does not delete old stored entries; OWASP calls for targeted invalidation/purge of affected keys and attention to every cache layer. Its guidance also says an application cache can leak across users independently of HTTP caching. — [OWASP response classification](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#1-classify-responses-before-caching); [OWASP coordinated policies/purge](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#5-coordinate-origin-and-intermediary-policies)
- Published browser confounder: service-worker Cache Storage is separate from the browser HTTP cache and from any network/CDN cache; a service worker can intercept a request before it reaches the network. A page replay in the same browser is therefore weak evidence of shared-edge caching. — [web.dev, service worker and HTTP caching](https://web.dev/articles/service-worker-caching-and-http-caching)

### Inferences

- **Preconditions (no test is authorized by this note):** record the written program URL/rules, exact in-scope host and read/write methods, route/asset exclusions, separate V/A test credentials, approved dedicated browser-through-Burp or separately approved channel, time window, request cap/rate shared across paths, no other-user navigation, one disposable marker field and cleanup/purge owner. First resolve whether “decryption” actually meant something else; if yes, do not repurpose this WCD plan. These are constraints of the assignment and the source distinction between shared and private caches. — [RFC 9111 §2](https://www.rfc-editor.org/rfc/rfc9111.html#section-2); [OWASP complete-path testing](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path)
- **A bounded, hypothetical receipt sequence:** (0) Pick independently distinct, researcher-isolated keys **K0 (unprimed control)**, **K1 (candidate)** and **K2 (alternate-key miss)** only after checking the proposed distinguishing parameter/path *is keyed*; avoid a predictable shared public path. (1) On V's disposable object, seed **one** non-secret random marker `bv_wcd_<random>` by an approved normal workflow; record V's readback *before* priming, the absence of that marker in A's own representation, and the explicit private-access expectation. (2) At K0, establish that A/anonymous cannot directly obtain V's marker *without V priming that key*; verify A's canonical, unambiguous V-resource route also denies/omits it. Do **not** use K0's 403/404 cache entry as K1. (3) With V authenticated, request K1 once and record raw request/response, status, content type, V-marker location, cache policy/`Vary`, and per-layer cache telemetry. (4) With a genuinely separate anonymous client or owned A, replay **the identical K1 method, URL and representation-selecting headers**, changing only the intended auth context; look for marker **in the raw response body**, a same-key shared hit/no-forward indication, and a second bounded identical replay only if the grant/budget permits. (5) Request unprimed K2 with A/anonymous: expect miss/denial and *no* marker; independently read V's canonical private resource afterward to show the marker remains V-owned and the comparison isn't a page-render or content-change artifact. Record order, timestamps, cache member, receipts and hashes; do not log cookies or tokens in the research notes. This is an **inference/proposed test design**, not a claim of observed behavior. — [PortSwigger Academy](https://portswigger.net/web-security/web-cache-deception#detecting-cached-responses); [RFC 9211 cache telemetry](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [OWASP complete-path testing](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path)
- **Causal classification:** if A/anonymous gets V's marker at an unprimed canonical or alternate key, first investigate public-by-design sharing, direct authz/IDOR, or application-cache isolation; do not call it WCD. If K1 shows a cache hit but no V marker, storage alone is not disclosure. If A receives the marker but the serving layer/key cannot be established, record a suspected leak with unresolved cause rather than “confirmed WCD.” If the result exists only in V's browser, after client-side hydration, or in an intentionally public document, it is not evidence of cross-client private-data reuse. A different A-owned marker is unnecessary; V's one marker plus absence/readback controls suffice. — [PortSwigger WCD definition](https://portswigger.net/web-security/web-cache-deception); [OWASP application-cache and authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#6-protect-application-level-caches); [web.dev browser layers](https://web.dev/articles/service-worker-caching-and-http-caching)
- **Private-cache and routing controls:** use independent client contexts and capture the actual network response, not a screenshot or the same browser tab; if service-worker/browser-cache involvement cannot be excluded, park the shared-edge claim. Compare raw body and `Content-Type` with the canonical V route, check `Location` and each redirect hop separately without automatically following an unapproved destination, and distinguish a static SPA/app-shell `200`, `304` validation, `403/404`, login HTML, and genuine personalized JSON/HTML. One common-looking page for base and arbitrary-suffix controls may mean a fallback/redirect, *not* an origin delimiter; no V marker means no V-content proof. A no-store/private policy is an expected control, not proof of actual non-storage; if a shared layer reports a hit despite it, preserve the discrepancy for investigation and do not infer which layer ignored policy. — [PortSwigger delimiter-test warning and cached-response indicators](https://portswigger.net/web-security/web-cache-deception#exploiting-delimiter-discrepancies); [RFC 9111 storage and authenticated-request rules](https://www.rfc-editor.org/rfc/rfc9111.html#section-3); [OWASP complete-path testing](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path)
- **Stop/cleanup:** stop at any out-of-scope redirect/host, unexpected private or real-user data, real credential exposure, inability to isolate key or ownership, unapproved write/job/cost, 429/5xx/challenge, cache/response anomalies suggesting collision with a public key, lost observer, exhausted budget or unclear purge authority. Don't enumerate users, spray suffixes, trigger a victim, broadly invalidate a CDN or use cache poisoning of a high-traffic asset as a WCD proof. Remove the disposable marker from V after the approved run, retain only redacted/hash-bound receipts, and ask the operator for targeted K1 purge/expiry verification across affected layers; mark **cleanup unresolved** until independently verified, because deleting/changing the origin object or adding `no-store` need not evict an already-stored copy. A second run requires a new isolated key and renewed grant/budget checks. — [OWASP response classification/purge](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#1-classify-responses-before-caching); [OWASP complete-path/purge guidance](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path); [RFC 9111 §4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.4)

### Gaps

- Without origin/edge logs or reliable per-layer `Cache-Status`, receipt chronology can suggest but may not conclusively assign a hit to a specific shared cache versus an application cache or proxy. Unknown cache-key composition makes a “unique” query buster unsafe to assume. No universal TTL/purge guarantee, safe experiment size or provider-specific default can be inferred from the generic sources; the campaign owner must supply those and a verifiable cleanup path.
