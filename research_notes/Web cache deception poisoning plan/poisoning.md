# Web cache poisoning — offline investigation notes

## Which endpoint families are plausible, and how should they be prioritized?

### Takeaway

Prioritize a **verified, isolated cache key and a response-changing origin input** over a static-looking filename or a popular page. This is an offline design, not a claim that any BugVault target caches these routes; the phrase “cache decryption” is ambiguous and probably means **web cache deception**, a related but different failure mode from poisoning.

### Cited Findings

- A shared cache reuses responses for more than one user, whereas a private cache is dedicated to one user. RFC 9111 says the most common stored response is a `200` to `GET`, but redirects, negative responses such as `404`, partial responses, and some responses to other methods can also be stored; caching is optional, not guaranteed by status or extension. — [RFC 9111 §§1–3](https://www.rfc-editor.org/rfc/rfc9111.html#section-2)
- The Academy defines poisoning as **unkeyed input changing a backend response that is then cached and served to others**. It says cache eligibility can depend on extension, content type, route, status and response headers, and explicitly warns that cache-key isolation is needed to avoid contaminating real visitors. — [PortSwigger Academy, Web cache poisoning](https://portswigger.net/web-security/web-cache-poisoning)
- OWASP distinguishes poisoning (attacker input omitted from key) from deception (private/dynamic content misclassified as static), and recommends explicit route policies, separate static and dynamic namespaces, and specific handling for redirects and errors. — [OWASP Web Cache Security Cheat Sheet, Key Risks and §§1,3–5](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html)
- PortSwigger's 2018 research illustrates inputs influencing cached HTML, resource imports, redirects and localized content, as well as interactions between external and internal caches. Its case studies were reported and patched, not evidence about a present-day target. Original publication **9 August 2018**, page updated **3 September 2025**. — [Practical Web Cache Poisoning](https://portswigger.net/research/practical-web-cache-poisoning)
- The 2024 “Gotta cache 'em all” paper distinguishes **key generation** (poisoning) from **cache eligibility rules** (deception); it describes path-parser differences affecting apparent static extensions, directories and filenames, and redirect responses stored under a different resource key. Original publication **8 August 2024**, page updated **8 January 2026**. Its vendor examples are historical configurations, not defaults to assume for a campaign. — [Gotta cache 'em all](https://portswigger.net/research/gotta-cache-em-all)
- `no-store` forbids compliant caches from storing a response; `private` disallows storage of the response by a shared cache (subject to qualified-field semantics); `no-cache` **allows storage but requires validation before reuse**. A shared cache must not reuse an `Authorization`-bearing request's response absent an explicitly permitting directive (`public`, `s-maxage` or `must-revalidate` in RFC 9111). A session cookie or `Set-Cookie` alone is not a shared-cache prohibition. — [RFC 9111 §§3,3.5,4,5.2](https://www.rfc-editor.org/rfc/rfc9111.html#section-3); [OWASP §1](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#1-classify-responses-before-caching)

### Inferences

Proposed **candidate inventory**, not a vulnerability ranking or assertion of cache behavior. For each exact `scheme://host:port/path` and method, retain response status/type, `Cache-Control`/`Surrogate-Control` if present, `Vary`, `Age`, `Cache-Status`/vendor status, `Date`, `ETag`, expected owner, and which input could alter the **origin-generated** representation. Treat each response variant and cache layer separately. These are planning deductions from [RFC 9111 §§2–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-2), [the Academy](https://portswigger.net/web-security/web-cache-poisoning), and [OWASP §§1–5](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html).

| Candidate family | Response-changing input / proof surface to inventory | Priority **if an independently isolated key is possible**; otherwise stop |
| --- | --- | --- |
| Test-only or disposable public HTML (`/help`, `/docs`, preview page) | Canonical URL, embedded links, metadata, locale, reflected inert marker | First: ordinary GET response, low-consequence marker and easiest to contrast origin versus cache. Never use a homepage or normal shared URL merely because it is cacheable. |
| Semi-dynamic public HTML and localized/device variants | `Accept-Language`, language cookie, `User-Agent`/client hints, `Vary`, host/scheme-generated links | Next: compare deliberately different expected variants under **the same verified isolated URL**, with a matching-`Vary` control; an intended language split is not poisoning. |
| Read-only API / JSON / GraphQL **GET** | Exact operation/variables, query selection, localization, tenant-derived representation | Next only where GET is actually captured/declared, safe, and separately keyed; a query parameter echoed in JSON is not by itself cache persistence. GraphQL POST is a separate method/policy case. |
| Error and redirect family (e.g. owned missing URL, canonicalization, asset redirect) | `Location`, error text, cache status, redirect hop and target | Conditional: a cached 3xx/404 or edge-generated error may behave differently from 200. Do not follow or create out-of-scope redirects; do not induce WAF/5xx/429 responses for a proof. |
| JS/CSS, static/immutable assets, source maps and their redirectors | Query-derived import/link, error body replacing an asset, `Location` of asset redirect | High potential blast radius, **not** high permission: plan offline or use a dedicated owner-provided test asset/key only. An existing production JS/CSS key is unsuitable for an inert live prime. |
| Authenticated or tenant-specific GET / personalized content | Session cookie/identity, tenant and role, `Authorization`, personalized `Vary` | Separate **deception/access-control** lane unless a genuine unkeyed origin-changing input and shared-store proof also exist. Only A/B operator-owned synthetic data; if isolation or cache policy is uncertain, remain offline. |

Order is a **safety gate** first (written scope, disposable owner-provided namespace, bounded budget, rollback), then a **cache oracle** (per-layer evidence), then origin input influence, then cross-context reuse, and only then possible significance. “Static” is no guarantee: OWASP warns against extension-only policy, and the 2024 paper illustrates static/dynamic path confusion. — [OWASP §§3–5](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html); [Gotta cache 'em all](https://portswigger.net/research/gotta-cache-em-all)

### Gaps

- No campaign, route list, written method grant, cache configuration, test-only namespace, purge owner, or two owned-context captures was supplied. No family above is known to be present or cacheable on a target.
- “Cache decryption” is not defined by these sources as a web-cache attack. Confirm whether the parent task intends **cache deception**; do not merge a private-response disclosure proof with a poisoning proof. — [OWASP Key Risks](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#key-risks)

## Which inputs may reach the origin yet be omitted or transformed in the cache key?

### Takeaway

Treat **forwarding to application logic**, **inclusion in each layer's effective key**, and **cache eligibility** as three independent unknowns. One inert dimension and one confirmed isolated key at a time is the safe experiment; apparent reflections on a cache hit can mask rather than reveal origin processing.

### Cited Findings

- RFC 9111's cache key contains at least method and target URI, but actual GET-only caches often key only by URI and may add headers through `Vary` or local configuration. A `Vary`-named header must match the original request to reuse a stored response without validation; matching can normalize permitted whitespace, combine duplicate field lines and apply semantics-preserving normalization. `Vary: *` never matches. — [RFC 9111 §§2,4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1)
- The Academy documents exclusion of whole query strings or particular query parameters, normalization of ostensibly keyed data, exclusion of a `Host` **port**, and parameter cloaking when cache and origin split or prioritize duplicate parameters differently. It also covers uncommon method/body mismatches (“fat GET”); none is a presumed feature of an arbitrary site. — [PortSwigger Academy, implementation flaws](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws)
- PortSwigger's 2020 follow-up cautions that a query-string cache buster may itself be unkeyed, that disclosed/debug cache-key representations can hide additional dimensions, and that internal fragment caches can contaminate unrelated paths even when the public URL is isolated. Original publication **5 August 2020**, page updated **3 September 2025**. — [Web Cache Entanglement](https://portswigger.net/research/web-cache-entanglement)
- The 2024 research describes different decoding, delimiters, dot-segment normalization and **forwarded request** transformations at CDN/proxy/origin layers. Whether paths collide in the cache is not equivalent to whether the origin routes them to the same handler. — [Gotta cache 'em all, URL discrepancies and Normalization](https://portswigger.net/research/gotta-cache-em-all#normalization)
- OWASP recommends trusting `Forwarded`/`X-Forwarded-*` only when added or replaced by trusted proxies, canonicalizing scheme/host for links and redirects, rejecting ambiguous duplicate parameters and malformed encodings, and aligning CDN and origin normalization. — [OWASP §§2–5](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#2-design-a-complete-cache-key)
- Cloudflare's **6 May 2026** vendor guidance says GET bodies may be sent onward and cached without their contents being in the Cloudflare cache key; this is a **vendor-specific warning**, not evidence that any origin accepts a GET body or that another provider behaves the same way. — [Cloudflare, Avoid web cache poisoning](https://developers.cloudflare.com/cache/cache-security/avoid-web-poisoning/)

### Inferences

Offline **one-variable matrix** for a future authorized, test-only route; collect both the effective-key observation and the *origin* response/route observation on an isolated fresh key. Do not treat these as a payload list or dispatch a wordlist. The dimensions follow [the Academy's implementation analysis](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws), [the 2020 research](https://portswigger.net/research/web-cache-entanglement) and [OWASP §2](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#2-design-a-complete-cache-key).

| Dimension | Candidate origin influence to look for | Distinguishing one-dimension contrast; stop condition |
| --- | --- | --- |
| Query | Search/filter/render values; `operationName`, GraphQL document/variables on **captured GET**; canonical URL or redirect `Location`; ignored analytics parameter | Compare **one** benign value/absence change under a separately verified key, not a mix of fields. Then compare the *same isolated key* on B without input. Changing query alone is **not** a valid cache buster until proved keyed. |
| Query parsing | Order, duplicate name, delimiter interpretation, percent-encoding and normalized bytes | Change just one aspect and compare separately the origin's selected value and cache's key/reuse. A duplicate interpreted as first-at-cache/last-at-origin is a *hypothesis*, not a finding. Avoid malformed/oversized strings and production keys. |
| Headers | Benign language/device/`Origin`; forwarded host/proto/scheme or rewritten-path metadata; generated absolute URL/metadata/`Location` | Hold `Accept-Encoding`, `Accept`, UA, language and all named `Vary` fields equal except the tested one. For forwarded host/scheme/route, only approved in-scope values on an owner-supplied test route; unexpected routing, redirect or host outside scope **blocks** the branch. |
| Cookies | Language/theme/device selection or owned A/B session/tenant | Keep benign variant cookies distinct from identity-bearing cookies; compare `Vary: Cookie` and deliberate shared/private policy. Do not put session values in URLs, cache-key debug output or notes. |
| Path and authority | Path-info/suffix, case, encoded delimiter, slash/dot-segment, port, scheme and virtual host | First show two candidate URLs are distinct **isolated** keys (and map to which origin route) before using a path variant; a normalization collision with a public key or another tenant must never be primed. Never assume scheme/host/port is omitted. |
| Method/body/encoding | GET body, safe GET versus HEAD/POST, method override; content negotiation and `Content-Encoding` | Method is normally a key dimension and unsafe methods must write through. Keep method and representation stable for the core proof; body/override/POST are **lab or separately written-grant** variants only, with no mutation. Compare raw response bytes after accounting for compression. |

**Classify each dimension per endpoint and layer**: `origin not reached/unknown` (pre-existing hit, WAF or edge rewrite), `origin reached but ignored`, `origin changed but input keyed`, `origin changed and unkeyed at a named layer`, or `ambiguous`. A key-collision pair does **not** establish origin influence; a fresh reflected marker does **not** establish key omission; and either alone does **not** establish shared storage. These distinctions are deductions from [RFC 9111 §§2–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4), [PortSwigger's three-stage methodology](https://portswigger.net/web-security/web-cache-poisoning#constructing-a-web-cache-poisoning-attack), and [RFC 9211's per-cache statuses](https://www.rfc-editor.org/rfc/rfc9211.html#section-2).

### Gaps

- Effective keys may contain undisclosed, vendor-specific dimensions, and some caches omit `Cache-Status` entirely; a cache-key debug header is informative but cannot conclusively enumerate every dimension. — [Web Cache Entanglement, Select a Cache Oracle](https://portswigger.net/research/web-cache-entanglement); [RFC 9211 §2.7](https://www.rfc-editor.org/rfc/rfc9211.html#section-2.7)
- Without owner logs or a clean origin-path oracle, an edge rewrite or application-cache hit may impersonate origin forwarding. Do not resolve this gap by sending larger volumes, bypassing a WAF, or finding an unapproved network path.

## How can a controlled proof distinguish reflection from persistent shared-cache reuse?

### Takeaway

The minimum persuasive sequence is **verified isolated key → origin-generated inert marker on A's fresh request → B receives A's exact marker on the same key without sending it → separate negative key and a bounded replay**. When per-hop cache diagnostics and owner origin logs are absent, label the layer/provenance uncertain rather than claiming that an edge CDN stored it.

### Cited Findings

- RFC 9111 requires that cache reuse match target URI, compatible method and nominated `Vary` fields, and that a stored response be fresh, permitted stale, or validated. A cache reusing a response **without validation** must emit `Age`; request `no-cache` can force validation, whereas response `no-cache` does not ban storage. — [RFC 9111 §§4–4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4)
- RFC 9211 defines a **per-cache**, optional `Cache-Status`: `hit` means no forward from that cache; `fwd=uri-miss`, `vary-miss`, `request`, `stale` and `bypass` have different meanings; `stored` describes a forwarded response being stored; `collapsed` marks a concurrent collapsed request; `key` is implementation-specific. A chain can include both origin-side and edge-side caches, so one `hit` does not identify the origin or prove a browser-independent shared edge entry. — [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2)
- PortSwigger's Academy calls for a cacheable oracle with hit/miss feedback, comparing similar request pairs to infer key handling; it warns that a cache-buster must itself yield a unique key. Its older research notes a proxied/unproxied mismatch when Burp changed `Accept-Encoding` or added a cache-buster, creating **different** effective keys. — [PortSwigger Academy, implementation flaws](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws#cache-probing-methodology); [Practical Web Cache Poisoning, The common pitfall](https://portswigger.net/research/practical-web-cache-poisoning)
- OWASP asks that the complete production cache path be tested with multiple owned identities/tenants and one changed header/query/cookie/path component at a time; private data should not be cached solely because it has a static-looking URL. — [OWASP §7](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path)

### Inferences

**Future operator-run proof ladder** (all steps conditional on written authorization, a known test-only namespace, explicitly limited requests, A/B-owned contexts, a reviewed cleanup/purge owner, and the project's approved observation path). This protocol synthesizes [RFC 9111 §§3–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4), [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-3), and [PortSwigger's cache-oracle methodology](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws#cache-probing-methodology).

1. **Gate the key before introducing a marker.** Select an owner-created URL/key `K-A` that cannot coincide with a public URL after cache and browser normalization. Select a second isolated `K-control` with the same route shape. Observe first-use miss, route and cache metadata for **both**; establish distinct entries using per-layer key evidence or owner logs rather than identical-looking bodies or two misses alone. A `bypass` is not cacheable-key proof. A random query is *not* isolation until a contrast establishes it is keyed. No safe key separation ⇒ stop; don't use a public key or purge to make a miss.
2. **Establish origin influence separately.** On fresh `K-A`, request once as owned context A with a short, inert alphanumeric marker `M-A` in **one** input (never an active destination or code). Require marker bytes in an origin-produced body or relevant `Location`/header (not merely in the request, a proxy debug echo, or DOM rendering); compare a fresh isolated control route with that input absent or a distinct harmless marker. Record exact request/response hashes and, where available, an owner origin request ID/log showing what arrived and what generated the response. A first `fwd`/`stored` is supportive but a lower cache could still have answered. Reflection without origin attribution stays a lead.
3. **Test storage and key omission.** On an already primed `K-A`, B sends the **same effective URL, method and `Vary`-selecting fields** from a separate owned cookie jar/profile, **without `M-A` anywhere**. Request raw response without auto-following the redirect, conditional headers or request `Cache-Control: no-cache`; check whether `M-A` appears in the same response component with matching stable body/header bytes. `Cache-Status` member `hit` (or another documented oracle), coherent `Age`/remaining TTL, and origin logs showing **no new generation** for B support stored shared reuse. Keep B's identity difference explicit: if an intentionally keyed identity or `Vary` field changes, a miss is expected, not a refutation.
4. **Run distinguishing negative controls, not additional poisonings.** On independent `K-control`, B must **not** receive `M-A`; if it does, suspect an internal fragment/global cache, origin coincidence or isolation failure and stop. On another fresh isolated key, an input-value flip should generate its own new marker only when forwarded (not on a hit); hold other headers fixed. Where a header is intentionally in `Vary`, a mismatching header should produce `vary-miss`/another legitimate variant, not count as an unkeyed-input flaw. Reverse the A/B order on a fresh test-only key **only if within the preapproved budget**. Each negative has its own capture/hash, not just a statement that an earlier response looked different.
5. **Repeat once within a short, bounded freshness window** only if the key remains isolated, to distinguish B's immediate self-hit/in-flight collapse from reuse over time. No expiry timing race, cache-saturation loop, forced invalidation, or repeated re-prime. Owner logs or per-hop `Cache-Status` distinguish an edge hit from an upstream application-cache hit; if neither is available, say `cross-context repeat observed; storing layer unknown`. Any rollback or narrowly targeted purge requires owner agreement and its own receipt.

**Evidence row per attempt**: route and exact request shape; A/B account/tenant labels (no secret values); key-isolation check and precondition; tested input/location; expected `Vary` fields; marker and control marker; ordered timestamp/request ID; status/`Location`; raw body hash and marker span; `Cache-Control`, `Age`, `Date`, `ETag`, `Via`, `Cache-Status` **all members** (or vendor status with a vendor-specific interpretation); observed owner-origin trace/log if available; response-hash comparison with known volatile bytes itemized; observed stop/cleanup; and one of `origin-influence`, `key-collision`, `stored-at-layer`, `cross-owned-context`, `impact` marked **proved / not proved / unresolved separately**. Do not put cookies or credentials into notes. This artifact contract is an inference from [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2), [RFC 9111 §§4–5](https://www.rfc-editor.org/rfc/rfc9111.html#section-4), and [OWASP §§2,7](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path).

**False-positive decisions:** A's own re-request is not cross-user proof; A and B viewing a live origin reflection is not cache proof; B's browser cache or service worker is not a shared intermediary; `Age: 0`, a fast response, an `ETag`, a single vendor `HIT`, or `stored` on one miss is not by itself a complete persistence proof. A `304` after `fwd=stale` shows validation rather than an unforwarded fresh hit; `collapsed` can reuse an in-flight response without persistent storage. A marker in a JS-rendered DOM rather than raw response bytes does not prove origin-generated representation. These are controlled interpretations of [RFC 9111 §§4–4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4), [RFC 9211 §2](https://www.rfc-editor.org/rfc/rfc9211.html#section-2), and [OWASP Key Risks](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#key-risks).

### Gaps

- A black-box response alone cannot conclusively show that the **origin** (rather than another upstream cache) generated A's marker, identify the storing layer, or show that B's request did not reach the origin when intermediate diagnostics are absent; prefer owner-provided origin/edge logs. — [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-3)
- Synthetic markers and two operator-owned contexts establish a controlled mechanism, not real-user exposure, exploitability of a script/import, or harm. No live evidence has been collected for this note.

## Which normalization, tiering, timing and blocking conditions require separate controls?

### Takeaway

Key collisions, origin routing, and *where a response was stored* can diverge across layers; neither a cache-buster nor a `Vary` header should be assumed effective without an isolated contrast. If isolation fails, a fragment cache contaminates other paths, or WAF/rate/cleanup state is uncertain, the correct result is **blocked/inconclusive**, not a larger or faster experiment.

### Cited Findings

- RFC 9111 permits heuristic freshness in defined cases, including query-bearing URIs (the older blanket rule against heuristic caching of `?` URIs was not widely implemented); `s-maxage`, `max-age`, `Expires`, revalidation and serving stale have separate semantics. Unsafe-method requests can invalidate stored responses, and concurrent misses can be collapsed. — [RFC 9111 §§4,4.2–4.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2)
- RFC 9211 explicitly separates `fwd=uri-miss` from `vary-miss`, `request`, `stale`, `partial`, `method` and `bypass`; `stored` is only meaningful for a forwarded response and `collapsed` concerns requests combined in flight. Cache-Status is optional and might be exposed only in debug mode; its `key` value can itself disclose sensitive implementation details. — [RFC 9211 §§2,6](https://www.rfc-editor.org/rfc/rfc9211.html#section-2)
- PortSwigger's 2020 research reports **invisible key dimensions** despite debug headers and internal fragment caches that spread one marker to unrelated pages; it explicitly calls this latter situation difficult to test safely. The 2018 paper shows different geographic caches and a common `Accept-Encoding`/cache-buster mismatch; these are historical illustrations, not a reason to target other regions. — [Web Cache Entanglement](https://portswigger.net/research/web-cache-entanglement); [Practical Web Cache Poisoning](https://portswigger.net/research/practical-web-cache-poisoning)
- The 2024 paper maps delimiter, encoding and dot-segment disparities between cache and origin and notes that browser URL rewriting may change what is actually transmitted. Its “Cache-What-Where” examples depend on **both** a cache-key discrepancy and a response-changing gadget; a static-looking URL alone is not sufficient. — [Gotta cache 'em all](https://portswigger.net/research/gotta-cache-em-all)
- OWASP calls for explicit cache policies on errors/redirects, consistent normalization and tested narrow invalidation; it says not to rely on `Vary: Cookie` as authorization, or on `Set-Cookie` as an anti-cache directive. — [OWASP §§1–5,7](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html)

### Inferences

**Controlled contrasts and stop rules** (not a live test script), derived from [the Academy](https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws), [RFC 9211](https://www.rfc-editor.org/rfc/rfc9211.html#section-2), [Gotta cache 'em all](https://portswigger.net/research/gotta-cache-em-all), and [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html):

| Confounder | Contrast/interpretation | Blocker / safe disposition |
| --- | --- | --- |
| Query or path “cache buster” ignored, removed, decoded or normalized into existing key | First compare two untouched isolated keys, same response class but distinct cache entries; compare the cache's effective key **and** owner origin route if possible | If keyed separation cannot be shown, **no marker prime**. Never replace this with a popular path, direct IP, forced miss, or purge. |
| Duplicate query/header, conflicting host authority, encoded delimiter, path-info, slash/dot segment | In owner staging/lab, change one parse decision and compare origin route/value against **every visible layer's key** | Reject or park ambiguous real-target request if any form can map to ordinary content or bypass a guard; do not infer a collision merely from identical body bytes. |
| Expected language/device/tenant variant or `Vary` | Preserve all nominated fields except the one under test; compare matching and intentionally mismatching selecting headers on the **same isolated URL**, with a separate isolated URL reserved for the negative control | `vary-miss` or separate custom-key variants are normal. Authentication-dependent pages with no safe synthetic data or authorization are out of this poisoning exercise. |
| `no-cache`, `private`, `no-store`, short TTL, 304, stale reuse | Interpret directives per cache and separate `stored`, fresh `hit` and revalidated response; schedule only a bounded within-TTL serial observation | Do not chase an expiry window, inject request cache-control that alters normal selection, or use an unapproved purge/race. A policy override is a separate hypothesis. |
| Edge/reverse-proxy/application fragment cache or multiple POPs | Record all `Cache-Status` members, visible node IDs and owner origin receipts; B through a separate owned client on the **same approved path** | If a marker appears on a distinct control path, suspect global fragment contamination and stop immediately; do not spray geographic edges or infer the identity of the storing layer. |
| WAF/block page, soft-404, error cache, redirect chain | Match body/source of error versus origin, status, `Location`, forwarding reason and whether the *same* isolated resource is being selected | Rate limit, challenge, 5xx or uncertain safety ⇒ stop and retain as blocked. Never use a WAF error as a proxy for origin influence, evade a detector, or send an out-of-scope redirect. |
| Browser/private cache, service worker, content encoding, client rendering, clock/timing | A/B separate network contexts; raw wire response at the approved observer; equal representation headers; evaluate content before client transforms; use timings only as weak corroboration | B self-hit, DOM-only canary or unmatched `Accept-Encoding` ⇒ unresolved, not an edge-cache finding. |

**Decision gate for the future detailed plan:** `lead` = cacheability or marker influence alone; `candidate` = isolated key + origin influence + probable key omission; `mechanism evidenced` = independent owned-B fresh shared reuse of **A's key**, with a distinct *negative-control* key and `Vary` controls plus a bounded replay; `layer attributable` = correlating cache/origin logs or unambiguous per-layer diagnostics; `impact` = separately demonstrated authorized consequence. An unresolved rung must not inherit evidence from the next. This is a proposed evidentiary classification based on [PortSwigger's three-stage method](https://portswigger.net/web-security/web-cache-poisoning#constructing-a-web-cache-poisoning-attack), [RFC 9111 §4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4), and [OWASP §7](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html#7-test-the-complete-cache-path).

### Gaps

- Cache/edge policy, `Vary` support, normalization order, tier topology and WAF provenance are deployment-specific; the named research papers cannot tell us which applies to a future campaign. Past vendor observations and lab examples must not be promoted into current target facts. — [RFC 9211 §2](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [Gotta cache 'em all](https://portswigger.net/research/gotta-cache-em-all)
- No source establishes a universally safe cache buster, fixed request count sufficient for every TTL, or browser-independent way to isolate an internal fragment cache; when these are unknown, no live marker test is justified. — [Web Cache Entanglement, Internal Cache Poisoning](https://portswigger.net/research/web-cache-entanglement); [PortSwigger Academy caution](https://portswigger.net/web-security/web-cache-poisoning#identify-and-evaluate-unkeyed-inputs)
