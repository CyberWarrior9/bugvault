# Web cache deception and poisoning: standards and provider semantics

Research-only source check, accessed **2026-11-16**. The IETF RFCs are fixed 2022 publications; the linked Cloudflare, AWS, and Fastly documentation is **mutable** and describes products and possible configurations, not any BugVault target. No target, browser, Burp, DNS, or cache was tested.

## What does RFC 9111 require of shared caches, keys, directives, and freshness?

### Takeaway
RFC 9111 defines constraints on **when a stored response may be reused**, not a promise that a particular response will be stored: method and target URI form the minimum key, `Vary` qualifies selection, and freshness/revalidation gate reuse. `Set-Cookie` alone does **not** prohibit caching, while a request bearing `Authorization` has a distinct shared-cache restriction. [RFC 9111 §§2–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-2); [§7.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-7.3)

### Cited Findings
- Caching is optional. A cache key contains at least the request method and target URI; additional fields or local keying are possible. Caches commonly cache only `GET`, and other cacheable statuses may include redirects, 404s, and partial responses when their requirements are met. A stored response can be reused only for a matching target URI/method and nominated `Vary` fields, and only when fresh, properly allowed stale, or validated. [RFC 9111 §§2–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-2)
- A cache must not store unless the method/status are suitable; response `no-store` is absent; a shared cache is permitted under `private` and `Authorization` constraints; and an explicit cacheability signal or heuristically cacheable status exists. These are necessary conditions, **not** a directive to store. The specification explicitly acknowledges cache extensions and the narrowly specified `must-understand` exception to `no-store`; avoid turning a general rule into an unconditional claim about all implementations. [RFC 9111 §3](https://www.rfc-editor.org/rfc/rfc9111.html#section-3); [§5.2.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.3)
- For responses to requests carrying an **`Authorization` request header**, a shared cache must not use the response to satisfy later requests unless response directives explicitly permit it and their constraints are honored; RFC 9111 names `public`, `s-maxage`, and `must-revalidate`. A `Cookie` request header is not equivalent to this `Authorization` rule; cookie-dependent variants need correctly matched `Vary`/keying or non-cacheability. [RFC 9111 §3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-3.5); [§4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1)
- `Vary` requires a cache not to reuse a stored response without revalidation unless nominated request header fields match the original request, allowing specified semantic normalization. `Vary: *` never matches for reuse. Merely observing `Vary` does not establish a vendor implements it as expected; Cloudflare and CloudFront document special handling below. [RFC 9111 §4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [Cloudflare Vary](https://developers.cloudflare.com/cache/concepts/vary/); [CloudFront request-header caching](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/header-caching.html)
- Response `no-store` forbids intentionally storing the immediate request/response; unqualified `private` forbids a **shared** cache from storing but permits a private cache; unqualified response `no-cache` permits storage but requires successful validation before reuse. Qualified `private="Field"` or `no-cache="Field"` can suppress storage/reuse of nominated header fields alone, but the RFC notes qualified forms are often not implemented specially. Request `no-cache` expresses a preference to validate; request `no-store` does **not** erase an already stored response. [RFC 9111 §§5.2.1.4–5.2.1.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.1.4); [§§5.2.2.4–5.2.2.7](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)
- For a shared cache the explicit freshness precedence is `s-maxage`, then `max-age`, then `Expires` (otherwise possible heuristic freshness under eligibility restrictions). `s-maxage` overrides `max-age`/`Expires` for shared caches and implies `proxy-revalidate`; `must-revalidate` also forbids stale reuse without origin validation. Stale serving otherwise requires disconnection or explicit client/origin permission, such as an extension directive or out-of-band contract. Query-bearing URLs are **not** categorically barred from heuristic freshness. [RFC 9111 §§4.2.1–4.2.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.1); [§5.2.2.10](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.10)
- **`Set-Cookie` alone does not inhibit caching** under the RFC; an otherwise cacheable response carrying it may satisfy later requests. Servers should issue appropriate response cache directives. This is not a claim that a named CDN will necessarily retain `Set-Cookie`. [RFC 9111 §7.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-7.3)

### Inferences
- For a future authorized test, classify the **actual response** before interpreting a suspected leak: cache eligibility, response directives, `Vary`, request `Authorization` versus cookie authentication, freshness and any application/edge transformations can each change the conclusion. A header alone cannot establish storage and reuse. [RFC 9111 §§3–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-3)

### Gaps
- The RFC cannot identify a particular deployment's cache policy, transformed headers, custom key, actual origin response, or which intermediary served a candidate response; these require authorized evidence or operator configuration review.

## What can Cache-Status, Age, X-Cache, and CF-Cache-Status actually diagnose?

### Takeaway
RFC 9211 standardizes **per-cache handling reports**, not a proof of the bytes stored or which user's content crossed a boundary. Vendor status headers and `Age` help triage, but neither `HIT` nor a rising age substitutes for observing a distinct, owner-controlled marker in a different controlled identity's response. [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [RFC 9111 §4.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.3)

### Cited Findings
- `Cache-Status` is an optional structured list: entries run **closest to origin first, closest to user last**, and a cache may omit the header or omit optional parameters. `hit` means that particular cache satisfied the request without forwarding; `fwd` identifies forwarding reason (`uri-miss`, `vary-miss`, `stale`, `bypass`, etc.); `stored` with `fwd` says that cache stored the forwarded response; `ttl` is remaining freshness and may be negative. `key` is an implementation-specific representation, not necessarily the complete raw key. [RFC 9211 §§2–2.8](https://www.rfc-editor.org/rfc/rfc9211.html#section-2)
- A `hit` can include a locally derived `304`/`206` or a stale response served without forwarding; if revalidation **did** forward, that layer is not a hit. RFC 9211's examples include multiple caching layers and a forwarded request that is collapsed with another. Thus one layer's hit cannot identify the source of a personalized body or guarantee persistent storage in every layer. [RFC 9211 §§2.1–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2.1)
- Standard `Age` is a **calculated estimate** of time since generation or validation, incorporating time resident in multiple caches and transit, not a universal single-edge fill timestamp. Cloudflare says its `Age` appears on `HIT`, `STALE`, and `UPDATING`, may inherit an upper-tier age, and can be **origin-supplied** even on Cloudflare `DYNAMIC`/`BYPASS`. [RFC 9111 §4.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.3); [Cloudflare cache responses](https://developers.cloudflare.com/cache/concepts/cache-responses/)
- `CF-Cache-Status` distinguishes `HIT` (found), `MISS` (eligible but not there), `DYNAMIC` (request not eligible), `BYPASS` (eligible request, response not cacheable), `EXPIRED` (expired/fetched from origin), `REVALIDATED` and `UPDATING` (distinct revalidation paths), and `STALE`. A Cloudflare Worker/WAF/redirect can yield `NONE/UNKNOWN`; these statuses describe Cloudflare's handling, not a cross-user body comparison. [Cloudflare cache responses](https://developers.cloudflare.com/cache/concepts/cache-responses/)
- **Fastly's non-standard `X-Cache`** defaults to `HIT` for Fastly's hit states and otherwise `MISS`, but `PASS` is reported as `MISS`, **edge-generated synthetic content can be `HIT`**, and stale/background-revalidation hits report `HIT`; shielding/restarts can produce multiple values. `X-Cache-Hits` is per cache server, not per data center. These headers can be altered/removed by VCL. [Fastly X-Cache](https://www.fastly.com/documentation/reference/http/http-headers/X-Cache/); [Fastly X-Cache-Hits](https://www.fastly.com/documentation/reference/http/http-headers/X-Cache-Hits/)
- CloudFront can **collapse concurrent requests with the same key**: the first appears `Miss` and subsequent collapsed requests `Hit` in its edge-result logs even though they were waiting on that fetch. A hit-class signal alone must therefore not be treated as proof that an independently reused, persistent response was stored. CloudFront also may evict objects before TTL and revalidate expired objects. [CloudFront request collapsing](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html#request-custom-traffic-spikes); [CloudFront expiration](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html)

### Inferences
- Require **raw body bytes with an independently unique marker**, the exact URL/key-relevant request fields, ordered cold-fill/repeat/control receipts, separate identities and a distinct negative control. Diagnose each visible layer separately; a status hint or `Age` on a response whose body was never compared cannot prove web cache deception or poisoning. [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [RFC 9111 §4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4)
- When a control request includes `Cache-Control: no-cache`, do **not** label it a universal origin-forcing mechanism: RFC 9111 describes a preference, and CloudFront explicitly says viewer `Cache-Control`/`Pragma` cannot force it back to origin. [RFC 9111 §5.2.1.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.1.4); [CloudFront expiration](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html#expiration-individual-objects)

### Gaps
- No generic header establishes the actual cache key, origin request, whether a body marker was stored, or any cross-account effect; a CloudFront-specific interpretation of `X-Cache` should not be inferred from Fastly's `X-Cache` definition. Owner-side CDN logs/configuration and controlled response captures would resolve ambiguity.

## Which Cloudflare, CloudFront, and Fastly defaults differ from the standards or from configured behavior?

### Takeaway
Each provider exposes controls that can change eligibility, keying, forwarding, revalidation and path handling. Especially important: Cloudflare's default extension filter and **opt-in** Armor; CloudFront's distinct **cache** and **origin-request** policies and **normalized behavior match versus raw path forwarded**; Fastly's default URL-plus-Host hash and configurable VCL/readthrough semantics. [Cloudflare default behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/); [CloudFront policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-how-origin-request-policies-and-cache-policies-work-together.html); [CloudFront path normalization](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html#path-normalization); [Fastly cache key](https://www.fastly.com/documentation/guides/full-site-delivery/caching/manipulating-the-cache-key/)

### Cited Findings
- **Cloudflare default eligibility:** absent rules, the CDN uses extension, **not response MIME type**, as its static-file eligibility filter (e.g. `.jpg`, `.css`, `.js`, `.pdf`); **HTML/JSON are not cached by default**, `robots.txt` is a documented exception. Its default TTLs in the absence of origin directives vary by status. A Cache Rule, Page Rule, Worker or TTL override can change eligibility; the `.jpg` suffix is a *candidate*, not proof of a cached personalized document. [Cloudflare default behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/)
- **Cloudflare Armor:** Cache Deception Armor must be **enabled by a Cache Rule**: `Eligible for cache` and the Cache Key setting's Armor toggle. It compares a URL extension with returned `Content-Type` and declines caching on a relevant mismatch; documented exceptions include `application/octet-stream`, `.jpg` served as `image/webp`, and `.gif` as `video/webm`. It depends on Origin Cache Control and **origin `Cache-Control` or an Edge Cache TTL rule may override protection**. An unverified setting or a matched `Content-Type` is not proof of a vulnerability or protection. [Cloudflare Cache Deception Armor](https://developers.cloudflare.com/cache/cache-security/cache-deception-armor/)
- **Cloudflare key and path:** its documented *default* key contains the full URL with query string, `Origin`, certain method-override headers and forwarding/rewrite headers; cookies can be added using a **custom** key. The default key's `$scheme` is the **origin** scheme, whereas a custom key's `$scheme` is the viewer scheme. Cloudflare recommends enabling **Normalize URLs to origin** with URL normalization/custom keys to avoid mismatch. Its URL normalization can be configured separately for edge and origin, while baseline adjacent-slash normalization applies even when optional normalization is off. Do not assume that extension matching, key formation and origin routing see identical raw path bytes. [Cloudflare cache keys](https://developers.cloudflare.com/cache/how-to/cache-keys/); [Cloudflare URL normalization](https://developers.cloudflare.com/rules/normalization/); [Cloudflare normalization mechanics](https://developers.cloudflare.com/rules/normalization/how-it-works/)
- **Cloudflare directives are configuration-dependent:** its short default-behavior page says `no-cache`/`max-age=0` do not cache, but the more detailed **Origin Cache Control** table and cache-status page say **with OCC enabled** (default Free/Pro/Business) they may be **stored and revalidated**, whereas with OCC disabled (Enterprise default) they are not cached. `Set-Cookie` with default cache level and OCC enabled yields `BYPASS`; with OCC disabled Cloudflare can strip it and cache. With `Eligible for cache`/`Cache Everything` plus explicit Edge Cache TTL it can strip `Set-Cookie` and cache; without that TTL it preserves `Set-Cookie` and repeatedly `MISS`es. Its documented Vary feature is configured via Cache Rules/`cf.vary`, not an assumption that every arbitrary `Vary` header keys by default; `Vary: *` bypasses. [Cloudflare default behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/); [Cloudflare OCC table](https://developers.cloudflare.com/cache/concepts/cache-control/#origin-cache-control-behavior); [Cloudflare Set-Cookie cases](https://developers.cloudflare.com/cache/concepts/cache-behavior/#interaction-of-set-cookie-response-header-with-cache); [Cloudflare Vary](https://developers.cloudflare.com/cache/concepts/vary/)
- **CloudFront key versus forwarding:** by default its key has distribution domain and requested URL path, **not** query strings, viewer headers or cookies; managed policies differ (e.g. `CachingOptimized` adds normalized `Accept-Encoding` and has minimum TTL **1 second**, while `CachingDisabled` has zero TTL). A **cache policy** selects keyed query strings/headers/cookies and automatically forwards them; an **origin request policy** can additionally forward fields **without keying them**. This gap is a *poisoning hypothesis only if an origin varies its response on an unkeyed, forwarded input*; default absence from the key does not imply forwarding to origin. [CloudFront default key](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-the-cache-key.html#cache-key-default); [CloudFront policy combination](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-how-origin-request-policies-and-cache-policies-work-together.html); [managed policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-cache-policies.html)
- **CloudFront behavior match versus origin path:** cache behaviors match **first** applicable path pattern (order is security-relevant); CloudFront normalizes paths per RFC 3986 **for behavior selection**, then forwards the **raw URI path** to origin after the behavior is chosen. `//` and `..` can alter behavior selection. The cited documentation **does not establish** that cache storage keys on the normalized behavior-selection path; keep behavior selection, origin path, and cache key as distinct questions. Query strings and cookies are not considered in path-pattern evaluation. [CloudFront cache behavior/path normalization](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html#path-normalization); [CloudFront default cache key](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-the-cache-key.html#cache-key-default)
- **CloudFront directives/cookies:** positive **minimum TTL** makes CloudFront cache for at least that duration even with origin `no-cache`, `no-store`, or `private`—an explicit vendor warning, not RFC-compliant behavior to assume of generic caches. CloudFront caches **eligible** `GET`/`HEAD` responses, may optionally cache `OPTIONS`, and does not cache responses to the other methods it forwards. Configured cookie forwarding may cache and replay origin `Set-Cookie` on hits; when cookies are *not* forwarded, CloudFront strips request cookies and response `Set-Cookie`. CloudFront can strip `Authorization` on `GET`/`HEAD` unless configured to forward it, and may remove origin `Vary` values it does not handle as configured. [CloudFront expiration/minimum TTL](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html#ExpirationDownloadDist); [CloudFront behavior/methods](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html#DownloadDistValuesAllowedHTTPMethods); [CloudFront cookies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Cookies.html); [CloudFront request and response headers](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html#request-custom-headers-behavior)
- **Fastly key/path:** default VCL hash uses `req.url` **including query** and lowercased `req.http.host`, plus an internal purge generation; default key does **not** distinguish HTTP from HTTPS, and `req.url` case is not normalized in the way Host case is. Custom request settings/`vcl_hash` can replace/add key inputs and accidentally collapse distinct URLs/hosts; the response's `Vary` can distinguish variants inside a primary hash. Don't assume an extension-specific cacheability filter or a target's path normalization from this default-hash description. [Fastly `vcl_hash`](https://www.fastly.com/documentation/reference/vcl/subroutines/hash/); [Fastly manipulating key](https://www.fastly.com/documentation/guides/full-site-delivery/caching/manipulating-the-cache-key/)
- **Fastly cacheability caveat:** readthrough parsing prefers `Surrogate-Control: max-age` over `s-maxage`, `max-age`, `Expires`; absent indicators its underlying default is **2 minutes**, while standard CDN VCL may use a **service-configured fallback TTL**. Its docs say `no-cache`, `no-store`, and `must-revalidate` **do not influence Fastly caching** (though they pass downstream); standard CDN VCL passes on `private` or `Set-Cookie`. Fastly explicitly documents a divergence from RFC 9111: `Authorization` does not by itself bar caching; an explicit pass rule can be used. Custom VCL/Compute overrides can change all of this. [Fastly cache-control headers](https://www.fastly.com/documentation/guides/full-site-delivery/caching/about-cache-control-headers/); [Fastly HTTP caching semantics](https://www.fastly.com/documentation/guides/concepts/cache/cache-freshness/#divergences-from-rfc-9111); [Fastly `vcl_fetch`](https://www.fastly.com/documentation/reference/vcl/subroutines/fetch/)

### Inferences
- The dangerous condition is **origin output varying on an input the serving cache does not distinguish**, or a path interpreted as cacheable by one layer but personalized by another; extension, header, query, cookie, raw/normalized path and content-type observations must be paired with actual configuration or controlled A/B body evidence. These are research hypotheses, not a finding against any target. [RFC 9111 §4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1); [CloudFront policy combination](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-how-origin-request-policies-and-cache-policies-work-together.html); [Cloudflare Armor](https://developers.cloudflare.com/cache/cache-security/cache-deception-armor/); [Fastly hash](https://www.fastly.com/documentation/reference/vcl/subroutines/hash/)

### Gaps
- Provider identification from a banner cannot reveal a distribution's effective cache rule, policy revision, function/VCL, path rewrite, tier/shield, OCC setting, origin headers, or which inputs actually reach the origin. The Cloudflare short default page and detailed OCC docs are not fully reconcilable without inspecting the actual rule/OCC context. AWS/Fastly pages do not state a stable last-updated date in the fetched content. Re-check all mutable vendor pages before a later pilot.

## Which future controls and blockers would safely distinguish deception or poisoning?

### Takeaway
Plan **bounded, authorized, disposable-account** comparisons, not a spray or real-user exposure: one marker-bearing owned response, the exact-key replay from a second owned identity or unauthenticated context, and controls that independently test origin routing and cache-key separation. A positive cache header without the foreign marker in the response body remains a lead, not a demonstrated leak. [RFC 9111 §4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4); [RFC 9211 §2](https://www.rfc-editor.org/rfc/rfc9211.html#section-2)

### Cited Findings
- **Deception pair, subject to an approved campaign:** use an owned A-only benign marker in a legitimately authenticated dynamic page; compare the exact same full URL with an in-scope, single synthetic static suffix to the ordinary page and to an intentionally nonexistent static path. After a controlled A fill, compare one B-owned or logged-out retrieval of the **identical** URL/key-relevant headers with the A marker in raw response bytes; repeat with a **new** marker/key to exclude a preexisting cache object. A denial/redirect, missing marker, wrong account, or a suffix that changes origin resource is a negative/inconclusive outcome, not proof of protection for all paths. This comparison operationalizes RFC matching requirements and Cloudflare's documented parent-path example; do not use real victim content. [RFC 9111 §4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4); [Cloudflare Armor/deception example](https://developers.cloudflare.com/cache/cache-security/cache-deception-armor/)
- **Poisoning pair, subject to the same gate:** on an owned inert response, separately record baseline and a single value supplied in **one** candidate input (query/header/cookie/path) that demonstrably changes the origin response on a miss; then have B omit that input **only if both requests select the same verified cache key**, and see whether B receives A's benign marker. For query/path input the visible URL may differ; do **not** assert key equality from similar-looking URLs. Negative controls: an independently keyed input that **should** select a distinct representation, a non-reflecting input, and an otherwise identical request with no previous fill. A `HIT` whose body lacks the marker, marker present only in submitted request, same-account reflection, or cache-key variant separation is not cross-user poisoning. The need to distinguish forwarded-but-unkeyed fields follows directly from CloudFront's policy model and RFC `Vary`. [CloudFront policy combination](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-how-origin-request-policies-and-cache-policies-work-together.html); [RFC 9111 §4.1](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1)
- **Cloudflare-specific blockers/controls:** first determine whether the path is extension-eligible versus a Cache Rule/Worker override; inspect effective Cache Key, Armor enabled status, returned `Content-Type` (including `application/octet-stream` exception), Origin Cache Control and Edge TTL, `Set-Cookie` treatment, `Vary` action, query-key exclusions and whether normalized key/path matches what origin receives. Use both ordinary dynamic path and nonexistent static control; do not infer Armor is on from a clean response, nor a vulnerable cache from a `MISS`. [Cloudflare default behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/); [Armor](https://developers.cloudflare.com/cache/cache-security/cache-deception-armor/); [cache behavior](https://developers.cloudflare.com/cache/concepts/cache-behavior/); [cache keys](https://developers.cloudflare.com/cache/how-to/cache-keys/); [URL normalization](https://developers.cloudflare.com/rules/normalization/)
- **CloudFront-specific blockers/controls:** obtain the ordered path behaviors and their attached cache/origin-request policies, effective minimum/default/maximum TTL, cookie/`Authorization` forwarding and edge functions before treating a normalized-versus-raw path pair as relevant. Contrast a pattern that should enter a static behavior with one that should enter the default behavior, while verifying **origin response and routing**, not inferring the storage key from the normalized match. For potential unkeyed query/header/cookie input, separately establish **forwarding** and **response variation** on a cold request before cross-identity reuse. Account for collapsed requests and zero/positive minimum TTL; do not use viewer `Cache-Control: no-cache` as a guaranteed purge. [CloudFront cache behavior](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html#path-normalization); [policy combination](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-how-origin-request-policies-and-cache-policies-work-together.html); [request collapsing](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html#request-custom-traffic-spikes); [expiration](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html)
- **Fastly-specific blockers/controls:** review effective `vcl_recv` pass conditions, `vcl_hash`, `vcl_fetch`/Compute caching override, `Vary`, `Surrogate-Control`, cookie/Authorization treatment and shield before hypothesizing a shared key. Contrast URL+query and Host partitions against a **separately authorized** customized-key hypothesis; never collapse unrelated hosts or send out-of-scope Host traffic. If `X-Cache` is `HIT`, rule out a synthetic, stale, shield or restarted result by comparing raw marker bodies and layer evidence. [Fastly hash](https://www.fastly.com/documentation/reference/vcl/subroutines/hash/); [Fastly caching semantics](https://www.fastly.com/documentation/guides/concepts/cache/cache-freshness/); [Fastly X-Cache](https://www.fastly.com/documentation/reference/http/http-headers/X-Cache/)

### Inferences
- **Evidence/stop contract for an eventual BugVault plan:** keep one exact URL and representation context per case; log identity A/B, owned object and innocuous marker, method, complete request selector names (redact values), response **body hash and redacted marker excerpt**, status, `Cache-Control`/`Surrogate-Control`, `Vary`, `Set-Cookie` presence, `Content-Type`, `Age`, provider cache diagnostics, timestamp and ordered replay/control artifacts. Prevent browser-only cache confusion with a separate approved second identity context; avoid shared public keys already populated by users, redirects beyond scope, real user PII, and unapproved purges or writes. A negative is scoped to that URL, variant, rule and time; inconclusive stays open. The controls follow the RFC's matching/revalidation gates and vendor diagnostics but do **not** themselves grant traffic. [RFC 9111 §§3–4](https://www.rfc-editor.org/rfc/rfc9111.html#section-3); [RFC 9211 §§2–3](https://www.rfc-editor.org/rfc/rfc9211.html#section-2); [Cloudflare cache responses](https://developers.cloudflare.com/cache/concepts/cache-responses/)

### Gaps
- Research alone cannot establish authorization, an available dedicated browser, an owned A/B test surface, rule access, origin logs, safe cleanup, a request budget, or actual cache behavior. Without those, record the relevant provider hypothesis as **blocked/unverified**; do not substitute target requests, Burp, DNS, or another client for this offline note.
