The test result is a recorded checkpoint, not a rerun by this audit. ### Inferences

- **Reuse architecture, not claimed cloud capability:** extend campaign-local SQLite, content-addressed evidence, import provenance, exact-context/facet snapshots, source-qualified receipts, obligations, stops and destination handoffs. Do not rename the hostname/JS/app-role graphs and claim cloud inventory is solved. The source schemas show useful ingredients but no provider account/subscription/project/resource identity model. [Basis: store](../../recon/store.py#L20-L135), [takeover schema](../../recon/takeover.py#L22-L49), [workflow schema](../../recon/invariants.py#L28-L86).
- **Two identities must be different fields:** existing HAR `account` is the operator's application account label; a cloud account/subscription/project is a provider scope. Treating them as the same ID would pool unrelated principals and lose tenant boundaries. [Basis: HAR context](../../recon/har.py#L99-L102), [workflow context](../../recon/invariants.py#L51-L55).
- **Initial delivery should be offline-first:** the strongest existing implementation precedents are evidence ledgers, not SDK automation. A new cloud ledger can safely make inventory gaps and authorized next edges explicit without pretending to execute or adjudicate them. [Basis: SSRF non-execution](../../recon/ssrf.py#L1-L5), [takeover non-execution](../../recon/takeover.py#L1-L5), [upload boundary](../../recon/README.md#L163-L176).

## 2. Which authorization, credential, traffic and evidence boundaries must the plan preserve?

### Takeaway

Current machine enforcement is primarily **URL + HTTP method + mode + request/time budgets + DNS/IP-pinned HTTP**, not provider action/resource authorization. A cloud SDK/CLI does not inherit these controls. Written program permission, resource ownership, provider policy and a bounded approved execution path must all remain prerequisites, while artifact integrity, observed facts and semantic vulnerability validation remain distinct. [Sources: scope](../../recon/campaign.py#L379-L434), [HTTP enforcement](../../recon/net.py#L139-L188), [external boundary](../../AGENTS.md#L105-L119), [semantic limit](../../recon/factcheck.py#L1-L5).

### Cited Findings

- `Scope.check()` accepts supported URL schemes, host, port and path against include/exclude rules; URL userinfo is refused and exclusions win. It does not take cloud account IDs, ARM IDs, projects, IAM actions, a request-body resource selector or credential principal as scope inputs. `Policy` defaults to GET/HEAD and validates explicit extra methods in active/loud mode. [Sources](../../recon/campaign.py#L392-L416), [policy fields](../../recon/campaign.py#L437-L461), [method validation](../../recon/campaign.py#L541-L547).
- `recon send` sends one request via `ScopedClient`, accepts operator-supplied headers/body, and returns a genuine stored request ID. Extra methods are individually granted; writes never auto-follow redirects. Nothing in this command is provider-aware signing, credential acquisition, identity discovery, SDK retry/pagination control or effective-policy evaluation. [Sources](../../recon/cli.py#L714-L753), [send arguments](../../recon/cli.py#L1341-L1354), [client API](../../recon/net.py#L191-L269).
- Native target/passive budgets include failed attempts and persistent campaign usage. HTTP connects through validated pinned peers; mixed public/private sets fail closed, and configured proxies fail closed. These protections do not cover arbitrary subprocess/SDK/scanner traffic, DNS utilities or an OS-wide sandbox. `host_pacing` is not an atomic simultaneous-process reservation gate. [Sources](../../recon/net.py#L139-L188), [execution limits](../../recon/README.md#L598-L609), [concurrency caveat](../../recon/README.md#L59-L63).
- Standing campaign plans can permit writes and operator-run scanners/native paths; defaults are not blanket write bans. Written source, exact targets/exclusions, checks, methods, pacing/concurrency, request cap, time window, disposable resources, before/after checks, cleanup and stops are required. External accounting is manual; a failure of scope/rate/budget never authorizes another tool. [Sources](../../.claude/skills/scope-policy/SKILL.md#L8-L34), [repo execution instructions](../../AGENTS.md#L89-L119).
- Dedicated visible browser/Burp is the default live path; interactive account/provider login, signup and mailbox work use the dedicated test profile. Browser preparation is not connected control or HTTPS capture verification. Burp active sends/preparation, settings/task controls and Collaborator actions require explicit approval and do not mint native response IDs or inherit recon enforcement. This audit used **none** of those tools. [Sources](../../AGENTS.md#L89-L119), [Burp workflow](../../.claude/skills/scope-policy/references/burp-workflow.md#L29-L74), [takeover provider-account distinction](../../.claude/skills/hunt-takeover/SKILL.md#L17-L36).
- SSRF grants are explicit branches (`dns`, `internal`, `cloud`, `credential`, `protocol`, `execution`, or all), with destinations and prerequisite capabilities still checked. Granted branches are intended to run to authorized depth; a missing branch grant blocks that branch, not all research. A callback grant is not credential/cloud permission. [Sources](../../recon/ssrf.py#L25-L96), [skill authorization](../../.claude/skills/hunt-ssrf/SKILL.md#L17-L47), [depth doctrine](../../.claude/skills/hunt-ssrf/references/deep-branches.md#L1-L9).
- The existing SSRF reference distinguishes identity proof, permission description, one consequential read and broader chain impact, and rejects persistent CLI credential profiles. However, some reference wording is too categorical for a new cloud skill: a role name does not establish effective permissions, a provider metadata pattern is not applicability, and “most programs accept” is not program authorization. Treat these as review targets, not new authoritative policy. [Sources: local ladder and table](../../.claude/skills/hunt-ssrf/references/deep-branches.md#L51-L91), [skill prerequisites](../../.claude/skills/hunt-ssrf/SKILL.md#L154-L185), [validator credential rule](../../recon/prompts/validator.md#L38-L58).
- Typed HTTP predicates are only `status_is`, `header_present`, `header_equals`, `body_contains_raw`. They bind to a stored response/context snapshot, recheck integrity, and report supported/contradicted/inconclusive/stale. They do **not** evaluate IAM conditions, authorization causality, ownership, attacker capability or impact. Narrative `observed` facts are not machine-checked semantic truth. [Sources](../../recon/factcheck.py#L19-L56), [verification](../../recon/factcheck.py#L101-L166), [documented limits](../../recon/README.md#L526-L544).
- Findings enforce replay/control **file presence and unequal hashes**, not meaning. The validator separately applies scope, prerequisites, deterministic replay, a true negative assertion, privilege-versus-impact, root-cause deduplication and minimal impact. Owner access is a positive baseline, not a negative control. Reportability additionally needs demonstrated harm/misuse, private-credential unlock or a complete chain; missing/failed realism questions park the chain. [Sources](../../recon/findings.py#L224-L246), [validator](../../recon/prompts/validator.md#L18-L84), [realism schema](../../recon/chain.py#L45-L55).
- Model routing is policy, not an implemented gateway/adapter/reviewer. Keep the selected session model unchanged; provider access cannot enlarge target permission. Model-disclosure approval/context gating is incomplete; raw responses, tokens and private-program/cloud metadata must be minimized and not broadcast across providers. The model-routing document has older GET/HEAD-only executor wording; the actual current HTTP method support is broader under explicit grants, but still **not** a cloud executor. [Sources](../../docs/model-routing.md#L1-L6), [routing/fail-closed rules](../../docs/model-routing.md#L27-L79), [context disclosure](../../docs/model-routing.md#L111-L153), [shared data guidance](../../AGENTS.md#L70-L85), [current methods](../../recon/README.md#L384-L416).

### Inferences

#### Recommended mandatory permission envelope — proposed, not existing configuration

The cloud plan should represent this envelope explicitly and fail closed on missing material; it should **not** imply that adding JSON grants independently authorizes traffic. This extends the existing standing-plan and offline-ledger distinction. [Basis: scope-policy](../../.claude/skills/scope-policy/SKILL.md#L19-L34), [takeover permission layers](../../.claude/skills/hunt-takeover/SKILL.md#L17-L36).

1. **Authority/source:** program URL, archived written authorization/rules hash and review date, class exclusions, engagement window, operator approver, provider acceptable-use/testing policy source/version/date, third-party/provider-account permission, and separate approval for evidence disclosure to an AI provider. Fresh review is needed before execution; this local audit cannot supply it.
2. **Provider/resource scope:** provider and partition/cloud environment; organization/tenant/account/subscription/project identifiers; permitted regions/services/resource IDs and object prefixes; exclusions, owners and disposable-resource constraints. A shared provider API hostname or known application tenant is not sufficient authority for every resource behind it.
3. **Principal/credential scope:** supplied A/B cloud principals and owning authorities, origin of credential material, allowed identity-verification/permission-description/credential-use actions, exact audience/resource and expiry, permitted role/federation hops and destinations. A test-app account label, unsigned JWT claim, role display name or key ID is not this binding.
4. **Action semantics:** exact provider operation/action allowlist plus HTTP method. A provider RPC carried by POST may be a read; a GET may cause state/cost. Neither inference overrides current `policy.allowed_methods`; missing POST permission still blocks a POST-based read. Record expected effects, sensitive response classes and cleanup obligations per action.
5. **Execution channel:** dedicated verified browser/Burp by default; separately approved scoped native HTTP where suitable; external operator tools only under an explicitly applicable bounded plan. No SDK, cloud CLI or signed-client transport may be presumed approved merely because scanners or native HTTP were approved. Future native integration must mediate every relevant network hop/action, not just the first API URL.
6. **Shared bounds:** one reconciled campaign envelope across all channels, with requests/attempts, retries, redirects, pagination, async polling, token exchanges, role/federation hops, bytes read/written, created objects, time, rate/concurrency and maximum cost/resource commitments. Keep native-measured and external-declared counts visibly separate; imported records must not double-charge old sends or erase unknown attempts. The proposed offline ledger cannot reserve real external traffic.
7. **Stops/resume:** expired/revoked/ambiguous authorization, unexpected principal/account/region, unapproved resource/destination, 429/challenge/lockout/5xx/degradation, budget/time/cost cap, sensitive third-party data, credential spill, lost observer, unknown write result, failed/unverified cleanup. Charge uncertain attempted sends; stop the relevant provider/account/resource run, preserve evidence, and require reviewed reconciliation before resume. Never use a second transport, new credential, region or model to bypass the stop.

These are proposed cloud-specific refinements, not current keys or an assertion of complete enforcement. They preserve the existing model of minimum necessary data, owned-resource effects, stop-on-policy-failure and non-blanket write permission. [Basis: current transport](../../recon/net.py#L139-L188), [external run accounting](../../.claude/skills/scope-policy/references/burp-workflow.md#L47-L74), [owned cleanup/stop vocabulary](../../recon/invariants.py#L120-L125).

#### Credential handling and depth doctrine

- Prefer opaque campaign-local credential handles and value fingerprints, with only provenance, principal/issuer/audience hints, restrictions, expiry and authorized-use metadata in the ledger. No raw credentials, presigned URLs, service-account JSON/private keys, session tokens or signed requests in shared notes/model packets. Existing `.recon` response/request bodies can contain secrets; hash-only lead records do not sanitize the original capture. No new secret storage should be described as secure merely because a regex rejects obvious signatures. [Basis: hash-only JS lead](../../recon/jsintel.py#L191-L206), [capture privacy](../../recon/README.md#L610-L610), [SSTI signature/redaction checks](../../recon/ssti.py#L642-L661).
- Track **material observed → issuer/principal independently bound → validity observed → action/resource permission observed → unauthorized consequence observed** as separate dimensions. “Identity call succeeded” is not “can read all buckets”; a policy wildcard is not effective access; `AccessDenied` is not a complete inventory or proof that a credential is invalid. Each exercise needs its own permission and evidence. [Basis: format-only classification](../../recon/jsintel.py#L25-L61), [reportability/realism](../../recon/prompts/validator.md#L38-L84).
- Full-depth investigation means follow every relevant, evidenced, authorized edge through identity, IAM/resource policy, control plane/data plane, cross-account/federation, secret access and execution-equivalent effect when allowed. Do **not** substitute “read-only forever,” “no credential use ever,” or “three tries completes the class” for the program's actual policy. Missing permission/tools or exhausted effort leaves a named blocked/inconclusive edge, not a universal negative. Retain the smallest sufficient reportable proof without manufacturing a requirement to escalate every primitive to RCE. [Basis: SSRF depth doctrine](../../.claude/skills/hunt-ssrf/references/deep-branches.md#L1-L9), [program allowance](../../.claude/skills/hunt-ssrf/SKILL.md#L162-L211), [effort versus completeness](../../.claude/skills/hunt-ssrf/SKILL.md#L213-L228).

### Gaps

- There is no provider-action/resource scope enforcement, credential audience/issuer binder, signing adapter, shared external reservation broker or provider API semantic gate in the current audited boundary. A future design must add and test these rather than claim URL scoping supplies them. [Current scope signature](../../recon/campaign.py#L392-L416), [current send signature](../../recon/cli.py#L714-L753), [external enforcement limit](../../AGENTS.md#L105-L119).
- Fresh AWS/Azure/GCP/other-provider policy and service mechanics are deliberately unresolved: no external research was authorized. Existing local examples cannot certify current behavior. A production plan must require dated primary-source review before the specific provider branch can execute. [Existing provider reference scope](../../.claude/skills/hunt-ssrf/references/deep-branches.md#L51-L68), [takeover freshness caveat](../../docs/takeover-acceptance.md#L70-L85).

## 3. What should the cloud skill, offline ledger, evidence gates and implementation milestones contain?

### Takeaway

Recommend a new **`hunt-cloud-misconfiguration`** skill, canonical coverage class **`cloud-misconfiguration`**, and an **offline `recon cloud` evidence/worklist family**. These names and all schema/case/gate details below are proposals only. Ship truthful resource/identity inventory and evidence handling first, with separate engineering/authorization decisions for any provider execution adapter. [Design basis: existing skill wiring](../../recon/skillmap.py#L1-L40), [offline ledger precedent](../../recon/takeover.py#L1-L49), [current command boundary](../../recon/catalog.py#L153-L173).

### Cited Findings

- New skills belong only in `.claude/skills/<id>/SKILL.md`; directory and frontmatter name must match, coverage routing and catalog must agree, and tests assert catalog/folder equality and executable CLI references. A future addition would change the baseline to **26 skills / 18 hunting skills / 8 guides**, but that change has **not** happened here. [Sources](../../Handover.md#L435-L448), [structural tests](../../tests/test_recon_skills.py#L69-L139).
- The current CLI/catalog explicitly distinguishes offline ledgers, scoped `send`, manual external tools and reference-only tools. All cloud verbs must preserve that distinction; installing a provider tool or accepting an export is not execution support. [Sources](../../recon/catalog.py#L75-L150), [CLI offline help](../../recon/cli.py#L756-L773), [send help](../../recon/cli.py#L1341-L1354).
- Existing ledgers preserve snapshot-bound stale history, integrity, declared counts, open variants and cleanup instead of automatically promoting findings. Coarse coverage does not close all exact contexts; generic replay/control cannot certify a business rule. [Sources](../../recon/ssrf.py#L181-L243), [takeover snapshots](../../recon/takeover.py#L363-L405), [business/race limits](../../recon/README.md#L623-L632), [validator limitation](../../recon/prompts/validator.md#L92-L105).
- Gate A/B/C precedents intentionally distinguish deterministic regressions, owned simulation/loopback, and model judgment. Static judgment fixtures are not LLM evaluation; contaminated without-skill baselines are invalid; an in-process provider simulation is not cloud/DNS/TLS/browser validation. [Sources](../../docs/business-race-gate-matrix.md#L10-L55), [takeover gates](../../docs/takeover-acceptance.md#L21-L57).

### Inferences

#### A. Proposed skill triggering and ownership

The skill description should trigger on a `cloud-misconfiguration` row, explicitly scoped provider inventory/policy export, storage exposure/presigned access, cloud secret lead needing issuer/resource binding, provider identity/trust/IAM/RBAC configuration, public service/function/API deployment, container/workload identity, cloud snapshot/registry/artifact exposure, or a proven primitive whose next edge is cloud authorization. Triggering selects a workflow; it is neither a provider match verdict nor permission. [Basis: endpoint heuristics](../../recon/score.py#L157-L236), [existing secret/signed-storage leads](../../recon/jsledger.py#L282-L303), [SSRF cloud cases](../../recon/ssrf.py#L46-L55).

- New seeding should retain **reason + source + candidate type + unresolved identity + evidence basis**. Seed from stored scoped signals/authorized imports, not invented bucket/project names or automatic namespace enumeration.
- Preserve `pack:s3-perms` as a suggestion; map a supported, identified cloud candidate to the new row rather than pretending that pack already executed. Keep `cloud-metadata` as an SSRF chain primitive unless an explicit migration is designed; do not silently relabel historical classes.
- Existing `info-disclosure` continues to route to `hunt-js-bundle` for client-source discovery. Cloud destination work gets explicit source lineage; it does not hijack every disclosure row.
- Scope-aware out-of-scope/intel entries may be retained offline, but not made live-ready, resolved, queued or contacted automatically. Missing method, identity, resource binding, raw capture or permission gets a separate readiness blocker.

These refinements follow the existing candidate-versus-destination and intel separation rather than assuming new implementation. [Basis: JS handoff](../../recon/jsledger.py#L709-L806), [host/intel separation](../../recon/active.py#L250-L253), [takeover discovery boundary](../../.claude/skills/hunt-takeover/SKILL.md#L64-L77).

#### B. Proposed offline schema-1 model

Use additive campaign-local `cloud_*` tables, strict bounded schema-versioned JSON, deterministic canonical serialization and explicit migrations/future-version refusal. Do not force provider resources into endpoint-family identity or use arbitrary executable predicates. Reuse existing helpers only after checking their semantics/limits; existing workflow/HTTP fact vocabularies do not already express cloud IAM. [Basis: existing schemas](../../recon/store.py#L20-L135), [finite workflow predicates](../../recon/invariants.py#L127-L156), [strict HTTP predicates](../../recon/factcheck.py#L19-L56).

| Proposed record | Required meaning / fields |
|---|---|
| `cloud_imports` / source receipts | Original-file SHA-256, format + exact supported exporter/version/schema, adapter version, import time, collection time/window, provider/environment, labelled collector principal and declared scopes, record selectors/indexes, normalization limits/errors, omitted/truncated sections and evidence basis. No live refresh on import. |
| `cloud_scopes` | Provider; partition/cloud environment; hierarchy nodes for AWS organization/account, Azure tenant/subscription/resource group, GCP organization/folder/project ID and number, plus provider-specific equivalents. Unknown is explicit; no fictional project/account inferred from a hostname. Written authorization and exclusions are separately referenced. |
| `cloud_principals` / bindings | Provider-native principal ID and type, authority/scope, role/service/workload/session/federated identity, alias evidence, session constraints/tags/audience/expiry when known, A/B owned labels, provenance and verification level. Separate supplied labels, decoded unverified claims and independently observed identity. |
| `cloud_resources` | Exact provider-native ID; scope/hierarchy; service/type; region or explicit global/unknown; name and aliases; resource version/generation when supplied; owner/owned/disposable status and evidence; data classification; lifecycle/current/historical status. A hostname, bucket name or ARN fragment alone is insufficient ownership proof. |
| `cloud_edges` | Typed source → relation → destination with evidence, collection time, conditions, verification basis and expiry: contains/belongs-to, references, runs-as, binds-credential, policy-attached, federates-to, may-assume, exposes-endpoint, may-access, observed-access, lineage. Conditional permission/potential trust edges never silently become demonstrated access. |
| `cloud_policy_snapshots` | Exact identity/resource/organization policy/RBAC/trust source documents or redacted authoritative projections; version/hash; attachments and inheritance known/missing; action/resource/condition context; collector visibility; parser support and explicit evaluation gaps. A parsed statement is not a complete effective authorization result. |
| `cloud_credential_refs` | Opaque local handle/fingerprint, discovery lineage, material kind, issuer/audience/subject hints versus independently bound identity, scope restrictions, session/expiry/revocation observations and permitted-use envelope. No raw secret, automatic profile creation, token exchange or credential validation. |
| `cloud_inventory_runs` / facets | Declared provider scopes × services × regions × collector principals, item/page counts, next-page/continuation state, denied/unsupported/omitted scopes, authoritative snapshot times, inventory/source caps. “Not seen,” “not authorized to enumerate,” and “does not exist” are different outcomes. |
| `cloud_contexts` / exact operations | Principal/session A/B + provider scope + exact resource/object/prefix + service action + endpoint/transport/method + region/version + workflow/time/conditions. Include policy/resource/config facets so unrelated changes do not invalidate everything and relevant changes reopen dependent cases. |
| `cloud_case_events` | Case family + variant, prerequisites, permission snapshot, context hash, expected boundary/policy source, state/outcome, independent stage facts, marker/control marker where meaningful, ordered source-qualified receipts, declared/measured attempts, resource/byte/cost accounting, artifact roles/hashes, parent event/root key, stale flags and semantic-review disposition. |
| `cloud_stops` / obligations | Provider/account/resource/run stop scope, reason/time, unknown-effect liability, cleanup owner/deadline/resource/version, deletion/revocation/reversion/post-check or approved retention receipts, resume approval/reason. Cleanup evidence remains recordable after scope narrows; recording it does not authorize a new external cleanup action. |
| `cloud_handoffs` | Source lead/event/resource/principal/policy snapshot → destination coverage/finding/owner, required next proof, grant/path blocker, root-cause lineage, and result imported back without promoting either ledger. |

Canonicalization must be provider-aware: preserve native identity case/partition/tenant/project distinctions and retain alias provenance; never merge solely on display name, common hostname, bucket label, role name or a decoded claim. Graph relations require exact endpoints and edge-specific proof, not same-host/class coincidence. [Basis: current generic uniqueness](../../recon/store.py#L21-L30), [current context separation](../../recon/har.py#L99-L102), [generic-chain limitation](../../recon/chain.py#L220-L253).

Suggested states are `untested`, `needs-context`, `ready`, `attempted`, `pending`, `observed`, `negative-for-variant`, `blocked`, `inconclusive`, `not-applicable`, with staleness/integrity/cleanup as independent dimensions. `observed` is behavior, **not** a vulnerability; `negative-for-variant` never closes sibling scopes/resources/principals. `not-applicable` needs a supported prerequisite reason; missing tools/permission is blocked. Expose inventory/coverage denominators and unprocessed pages/scopes, not a misleading global complete flag. [Basis: existing state patterns](../../recon/invariants.py#L101-L111), [SSRF uncertainty](../../.claude/skills/hunt-ssrf/SKILL.md#L82-L88), [coarse coverage caveat](../../recon/README.md#L590-L596).

#### C. Proposed import contract and CLI

Start with a **normalized `bugvault-cloud-v1` local JSON envelope** for operator-owned inventory/config/identity/attempt artifacts. This is a proposed format, not currently accepted by `recon import`. Explicitly reject unknown keys, unsupported versions, ambiguous envelopes, inconsistent scope/principal/resource joins, excessive nesting/records/pages/bytes, unsafe paths/symlinks and unredacted sensitive fields; validate before registration/partial writes. Preserve unsupported records as counted gaps, not empty clean inventories. [Basis: bounded current imports](../../recon/ingest.py#L18-L59), [surface-only contract](../../recon/ingest.py#L145-L201), [existing strict-ledger regression goals](../../docs/business-race-gate-matrix.md#L10-L25).

Prowler, ScoutSuite and CloudSploit, plus authorized provider inventory/config exports, are **possible later input sources**, not supported integrations. Select actual owned/redacted sample artifacts and pin exact versions and field mappings before promising a parser. Do not guess an export schema from a tool name, assume all releases match, dispatch the scanner, or copy its severity/check status as a confirmed vulnerability. Keep collector permissions/omissions and time visible. [Basis: current explicit subsets](../../recon/README.md#L560-L575), [catalog integration caveats](../../recon/catalog.py#L75-L99).

Proposed offline-only verbs: `recon cloud import|sync|declare|inventory|graph|plan|show|record|handoff|cleanup|resume|status|verify|export`. They should parse existing evidence, reconcile snapshots, plan applicable cases, show gaps/grants, record operator evidence and export **redacted** context; never resolve a resource, call a provider, queue target requests, sign a request, use a credential or promote a finding. `verify` must rehash/rebind and fail meaningfully on corruption/stale prerequisites. If implemented incrementally, advertise only verbs actually present. [Basis: truthful existing CLI](../../recon/cli.py#L756-L773), [catalog contract](../../recon/catalog.py#L153-L173), [takeover verification meaning](../../.claude/skills/hunt-takeover/SKILL.md#L79-L109).

#### D. Proposed case families and evidence-driven triggers

These are comprehensive **planning families**, not proof all providers/services or every variant are covered. Applicability depends on observed architecture, authority and supported evidence. Each family expands into exact scope × principal × action × resource × conditions × transport variants; no universal attempt count closes it. [Basis: exact-context precedent](../../recon/ssrf.py#L22-L26), [effort/completeness warning](../../.claude/skills/hunt-ssrf/SKILL.md#L213-L228).

| Proposed family | Trigger / boundary to test or review | Minimum honest claim / owner |
|---|---|---|
| CM-00 Authority, identity and inventory baseline | Any cloud lead/export; unclear account, project, region, principal or collector visibility. | Establish source-qualified scope/identity and missing inventory dimensions; never a vulnerability by itself. |
| CM-01 Object storage read/list exposure | Captured S3/blob/GCS/compatible object or bucket/container policy, known owned marker. | Separate list from object read and intended-public from private; use a boundary-enforcing negative control. |
| CM-02 Storage write/overwrite/delete policy | Captured owned disposable object operation or authoritative policy lead. | Granted inert write with independent readback/version binding, protected control and cleanup; upload lifecycle owns artifact processing. |
| CM-03 Presigned/delegated access | Captured presign/SAS/signed POST/download/finalize lifecycle. | Exact resource, operation, lifetime, audience and policy constraints; signed-URL presence alone is not a flaw. Upload/IDOR/authz handoff as appropriate. |
| CM-04 Public service/control-plane exposure | Explicitly scoped endpoint plus deployment/config evidence for API/function/admin/database/search/cache service. | Separate addressability, authentication, data access and state change. Public listener/port/status is not unauthorized effect. |
| CM-05 Identity policy and RBAC | Exported grants/bindings or observed low/high cloud principal contrast. | Parsed action/resource grant is a configuration fact; effective access and lower-role gain require context/deny/condition/principal proof. |
| CM-06 Resource policy and cross-account/tenant trust | Resource/trust policy referencing supplied A/B accounts/tenants or external principal. | Prove actual affected resource, attacker-holdable principal, conditions and unauthorized access; no arbitrary third-party tenants. |

| CM-08 Credential exposure, validity and scope | JS/map/APK/config/upload/metadata credential lead. | Keep format, material availability, identity, validity, permission and consequential access distinct; issuer exercise only if allowed. |
| CM-09 Metadata/workload credential boundary | Proven server fetch/render/file-read primitive with known deployment shape. | SSRF/SSTI owns acquisition mechanics/grants; cloud ledger receives exact credential/principal/resource lineage, not assumed cloud compromise. |
| CM-10 Secrets/configuration disclosure | Scoped secret/config API or exported secret-store/access policy, owned test secret. | Metadata description is not secret-value read; only minimum owned marker/data, distinct denial and permitted credential use. |
| CM-11 Snapshots, images, backups and artifacts | Owned snapshot/image/registry/package/serverless bundle/export share or policy. | Distinguish discoverability, metadata, pull/read, export/share and execution; no bulk downloads or paid resource creation by inference. |
| CM-12 Network/perimeter/service endpoint policy | Exported firewall/security-group/service-perimeter/private endpoint configuration plus known path. | Rule presence is not end-to-end reachability or unauthorized data access; preserve network position and downstream blocks. |
| CM-13 CDN/origin/CORS/cache interaction | Captured cloud delivery configuration and actual owned browser/content flow. | Prove bypass/read/write/poisoning effect under exact auth and cache context; headers/CDN tag alone stay conditional. |

Inert owned contrasts may demonstrate one action; no homemade universal IAM oracle. |
| CM-15 Escalation and cross-service chain | Proven initial access and a specific permitted role/policy/deployment/credential pivot. | Separate ability to configure, assume/pass/use an identity and terminal effect. Writes/execution only under the specific program/provider grants, fresh controls and cleanup. |

The cloud specifics are proposed research coverage, not assertions of implemented checks or current provider behavior. Their ownership follows existing capture/secret, SSRF, upload, authorization, takeover and reportability boundaries. #### E. Proposed cross-skill handoff contract

Every handoff should carry source record/artifact hashes, exact cloud scope/principal/resource/action binding, captured application account/role/tenant/workflow if relevant, parent event and root key, demonstrated fact versus hypothesis, outstanding preconditions, branch grants, approved execution path, remaining budget and cleanup obligations. A destination accepts responsibility for **its own proof**, not the source's label. [Basis: current JS destination enforcement](../../recon/jsledger.py#L793-L806), [authz parent/artifact rules](../../.claude/skills/hunt-access-control/SKILL.md#L112-L128), [findings relations](../../recon/findings.py#L80-L109).

| Source / destination | Ownership boundary |
|---|---|
| `hunt-js-bundle`, `apk-static-mapping`, `static-api-mapping` → cloud | Client artifact/endpoint/secret discovery only; cloud side resolves authority, identity, permission and protected consequence. No raw credential in packet. |
| `hunt-ssrf` → cloud | Server-side attribution and metadata/credential acquisition stay SSRF; cloud exercises require independently authorized credential-use/action/resource scope. Both hops need evidence. |
| `hunt-ssti` → cloud | Template evaluation/read evidence remains SSTI; cloud principal/permission/effect requires new source-bound proof. Arithmetic or an offline severity ceiling cannot establish cloud access. |
| `hunt-file-upload` ↔ cloud | Upload keeps presign/intake/processing/publication/retrieval/deletion lifecycle; cloud keeps provider identity/storage/resource policy. One shared object lineage, not duplicate impacts from the same fix. |
| `hunt-access-control` / `hunt-idor` ↔ cloud | Function/field/tenant policy versus object-reference substitution stays with the established owners; cloud IAM/RBAC/resource-policy context is added where relevant. Own A/B resources only. |
| `hunt-auth-bypass`, `hunt-oauth`, `hunt-saml`, `hunt-ato`, `hunt-mfa-bypass` ↔ cloud | Login/token/SSO/MFA/account takeover semantics stay with the auth owner; cloud trust and role/resource consequence is a separately evidenced edge. A successful token fetch is not acceptance/ATO. |
| `hunt-takeover` ↔ cloud | Namespace/provider claimability, exact candidate-host marker, TLS/browser chain and cleanup stay takeover; resource configuration/identity evidence may enrich the dossier. No automatic claiming. |
| `hunt-csrf`, `hunt-xss` ↔ cloud | Browser-initiated mutation or actual script execution requires the browser-class proof. CORS/CSP policy or cloud API status is not that proof. |
| `hunt-business-logic`, `hunt-race-conditions` ↔ cloud | Owner-defined entitlement/quota/value/state invariants and schedule-dependent causal effects stay with those ledgers; no cloud SDK concurrency inferred from an import or two successful replies. |

The graph should support cross-host/provider chains using **actual matching lineage**, not existing same-host/class-coincidence hints. Link confirmed findings only after class-specific review; keep unproven edges on the cloud worklist. [Basis: generic hint limitation](../../recon/findings.py#L290-L306), [campaign class matching](../../recon/chain.py#L220-L253), [lineage-specific alternative](../../recon/invariants.py#L149-L156).

#### F. Proposed evidence classes and validator gates

Avoid one scalar “confidence” or a severity tier automatically raised by a key, wildcard or hostname. Store evidence classes independently and require only those relevant to the claim. These are **new proposed classes**, not new `fact check` predicate types or finding stages. [Basis: current predicate boundary](../../recon/factcheck.py#L19-L56), [finding artifact/semantic separation](../../recon/findings.py#L8-L16).

| Proposed evidence class | What it may establish | What it must not imply |
|---|---|---|
| E0 Reference/lead | Host/resource string, fingerprint, client secret pattern, scanner assertion or conditional graph edge with source. | Existence, ownership, validity, policy violation or severity. |
| E1 Snapshot/config fact | Exact structured field/document statement, source/selector/hash/time and parser support. | Full effective policy, current live state or attacker access. |
| E2 Identity/ownership binding | Supplied ownership plus authoritative principal/resource identifiers or separately authorized identity receipt; explicit verified versus asserted fields. | Permission for unrelated actions/accounts or blanket authorization to use credentials. |
| E3 Reachability/authentication observation | Source-qualified request/response and independent marker where applicable. | Authorization violation, complete inventory, credential scope or execution. |
| E4 Boundary/consequence proof | Exact controlled principal/action/resource comparison, positive baseline, fresh replay, true distinct negative assertion and independent readback/owner trace where needed. | All service actions, every resource/region or unrestricted escalation. |
| E5 Terminal chain/cleanup evidence | Every edge's provenance and scope, attacker-realistic prerequisites, terminal owned effect, independently checked cleanup/revocation/reversion or owner retention. | Imagined downstream effects, other providers or generalized autonomy. |

Proposed mandatory semantic review: current program/provider permission and scope → resource/principal binding and inventory caveats → exact policy/action prerequisites → clean replay → boundary-enforcing negative control → attacker capability below obtained privilege → lineage/root-cause duplicate check → demonstrated terminal effect and cleanup → existing reportability/realism questions. Configuration-only assessments may be retained as posture findings **only under the program's stated reporting rules**; the current generic validator does not automatically make them reportable. No real harm needs to be inflicted: inert test resources/readbacks should establish the minimal permitted consequence. [Basis: validator order/reportability](../../recon/prompts/validator.md#L18-L84), [small-severity honesty](../../recon/prompts/validator.md#L55-L58), [takeover program-specific reporting](../../.claude/skills/hunt-takeover/SKILL.md#L133-L135).

For structured policy facts, initially report only finite exact-field/statement projections with source selectors and parser version. Explicitly label unresolved inherited policies, denies, condition keys, session boundaries, organization controls and collector blind spots. If effective-permission reasoning is later added, it needs a provider-versioned supported subset, authoritative comparison fixtures and an `unknown` result for unsupported semantics; never certify effective access from an allow wildcard alone. [Basis: finite-predicate precedent](../../recon/invariants.py#L127-L139), [HTTP-facts semantic limit](../../recon/factcheck.py#L150-L166), [downstream credential-policy realism](../../recon/prompts/validator.md#L79-L84).

#### G. Proposed Gate A/B/C acceptance — no gates claimed passed

**Gate A — deterministic offline contract.** Build an explicit requirement → test → result → limit matrix. Acceptance needs all mandatory rows actually checked, not merely a green aggregate count. [Basis: current partial acceptance matrix](../../docs/business-race-gate-matrix.md#L10-L25).

1. Fresh/legacy campaign initialization, idempotence, migrations, future schema/unknown-key refusal and preservation of unrelated tables/coarse history.
2. Exact AWS/account/partition, Azure tenant/subscription, GCP project-ID/number, region/global and provider-native resource identity; ambiguous aliases and same display name remain separate; malformed/dangling/cross-scope graph references rejected.
3. Import formats explicitly pinned; bounded nested/oversized/malformed inputs; dedup by bytes + context; record provenance; denied/paginated/incomplete inventories never become negatives; no partial writes on rejected envelopes.
4. Principal/session/audience/expiry and claimed-versus-verified separation; fake native request IDs, relabelled imported responses, unowned resource markers and credential-bearing exports refused.
5. Strict grant/source/date/action/resource/method/mode/expiry/exclusion readiness; missing provider policy or credential-use allowance blocks only its branch; unknown API operation semantics do not become read-only by HTTP-verb inference.
6. Independent E0–E5 facts; exact snapshot/selector checks; unsupported policy semantics return unknown; file hashes or marker bytes cannot automatically promote findings.
7. Fresh replay versus real negative assertion; wrong-account/resource/region/action, reused/contaminated markers, same-content controls and before-image-only controls fail the relevant proof contract.
8. Dependent policy/principal/resource facets reopen stale cases; expiry/revocation/current scope changes withdraw live readiness without deleting historical receipts; historical integrity remains distinguishable from current applicability.
9. Requests/retries/pagination/token exchange/polls and bytes/objects/cost counted once with provenance; native-measured versus external-declared remains visible; uncertain sends/effects stay charged/open; no claim of atomic external reservation.
10. Stops propagate to the intended run/provider/account/resource boundary; grants or model/channel switches cannot clear them; cleanup binds exact resource/version and supports approved retention; unresolved obligations block further affected work.
11. CLI/report/catalog/skillmap/count wiring, bounded redacted export/recall, exact case status versus coarse coverage conflicts, root-cause lineage and URL-only finding-anchor restrictions remain truthful.
12. Offline operations have explicit socket/subprocess/SDK/browser/model-call guards; tests prove no provider requests, DNS lookups, SDK import-time credential discovery or target queueing occur during import/sync/plan/record/verify.

**Gate B — owned vulnerable/fixed rehearsals, with environment labels.** Use in-process policy/provider simulations and owned-loopback services only; do not label either real AWS/Azure/GCP verification. Require vulnerable, fixed and matched control outcomes, fresh replay, independently observed state, imported public-ledger receipts, reopen/verify/report and cleanup for each applicable scenario. [Basis: existing owned simulation](../../docs/takeover-acceptance.md#L33-L41), [loopback versus model distinction](../../docs/business-race-gate-matrix.md#L27-L43).

- Storage: private versus intended-public marker read/list; separately controlled write/overwrite/delete; version/retained copies; signed object/method/expiry binding; accepted response with denied/missing readback.
- Identity/policy: A/B owned principals and provider scopes with same display names; partial inventory/denied page; apparent wildcard grant blocked by explicit deny/condition/inheritance; wrong session/audience/expired credential; identity success without protected access.
- Workload/metadata/federation: source primitive with and without required header/method capability; token receipt versus accepted constrained identity; actual downstream denial prevents terminal-chain proof. Simulated token services must be labelled simulated.
- Services/artifacts: public address but protected API; readable metadata but protected secret value; public artifact intended by policy; private marker artifact exposed; allowed policy edit without terminal effect; cross-service effect only when exact parent resource/principal lineage matches.
- Reliability/safety: throttling/challenge/error/cost/unknown-effect stops, retries/pagination charged, incomplete captures, stale policy/principal changes, tampered evidence, cleanup failure/approved retention, private-secret spill refusal.
- Negative chain tests: unrelated same-host and campaign-wide class matches must not combine into a cloud proof; simulated owner/admin actions do not establish a low-role escalation; callback/script-reference success does not establish execution.

**Gate C — model judgment and skill behavior, not live hunting.** Prepare adversarial fictional/redacted cases spanning every major family and all stop/uncertainty boundaries. Include provider suffix/NoSuchBucket, arbitrary scanner JSON, intended-public asset/browser key, AWS ID without secret pair, unsigned privileged JWT, identity-only success, wildcard-plus-deny, denied inventory page, missing browser/SDK grant, stale token, unowned resource, SDK fallback after a budget failure, RPC read over ungranted POST, control contamination, unrelated cross-resource chain and failed cleanup. [Basis: existing judgment limits](../../docs/business-race-gate-matrix.md#L45-L55), [invalid baseline lesson](../../docs/takeover-acceptance.md#L43-L57).

Predeclare expected class owner, facts versus hypotheses, minimum evidence, next permitted edge, blocked branches, source normalization readiness and stop disposition. Run skill versus a clean uncontaminated baseline only when model execution/provider-data approval exists; keep the same model/task/rules, saved outputs, model/run metadata, blind semantic grading where feasible, per-case assertions, failures and uncertainty. Require zero critical unsafe-permission/execution/false-confirmation errors in the acceptance set, report all other scores/denominators and reruns, and never claim general detection efficacy from small samples. Static fixture structure tests alone do **not** pass behavioral Gate C; invalid baseline runs are retained but excluded, not repainted as improvement.

Gate A passing does not imply B/C; B/C do not grant live testing. A real authorized provider rehearsal/pilot, if desired, is a **separate go/no-go** with fresh rules, exact owned resources/principals, suitable execution path, costs/budgets, capture and cleanup. There is no live cloud readiness certification in this proposal. [Basis: acceptance separation](../../docs/takeover-acceptance.md#L59-L85), [current go/no-go precedent](../../docs/business-race-gate-matrix.md#L66-L68).
