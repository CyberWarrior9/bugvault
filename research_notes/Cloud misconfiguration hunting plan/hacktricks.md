# HackTricks Cloud research for BugVault cloud-misconfiguration planning

Research/access date: **2026-11-16**. Assigned website: **https://cloud.hacktricks.wiki/en/index.html**. All external pages accessed for this assignment were on `cloud.hacktricks.wiki`; links to other domains appearing inside those pages were **not followed**. This is public-source research, not an assessment: no target probes, cloud-resource tests, logins, credential validation, secret retrieval, tool installation, or cloud changes were performed.

**Evidence labels:** “Source finding” means what the accessed secondary source describes, not a reproduced cloud vulnerability. Every matrix hypothesis and validation/control/deeper-proof cell is an **original planning recommendation**, not an action performed. Source citations support the underlying mechanism; they do not certify the proposed proof or establish program authorization. All provider defaults, product/version statements, permission semantics and logging claims remain **secondary-source leads pending current official-provider review**. The matrices intentionally contain no exploit commands, request payloads, credential-exfiltration instructions, or guard/logging evasion.

## 1. Which initial hints deserve contextual discovery and exposure follow-up?

### Takeaway

Use HackTricks Cloud to generate an asset–principal–operation graph, not a list of supposedly vulnerable public endpoints. The current unauthenticated-access indexes distinguish public reconnaissance, public sharing, anonymous operations, credential-bearing access and enrollment; preserving these distinctions prevents substantial false-positive inflation. [A1] [Z1] [G1]

### Cited Findings

- The general methodology covers inventory, exposed assets, permissions, federation, cross-service/cloud integrations, organization guardrails and security-service configuration. It explicitly recognizes that sensitive access exists beyond administrator wildcards. [M0]
- AWS cross-account access normally needs authorization on both sides, subject to applicable denies and organization controls; account-root trust delegates to an account, not exclusively its root user. A trust edge alone is not an executable permission edge. [A5]
- Azure resource visibility, permissions for a resource, Entra application registrations, tenant-local service principals and actual consent/role assignments are separate facts. Requested app permissions are not equivalent to effective grants. [Z0] [Z2]
- GCP Cloud Asset and IAM tools operate at explicit project/folder/organization scopes. Policy Troubleshooter can produce partial/Unknown results when policy or group visibility is missing; permission testing is not the same as exercising a target operation. [G2]
- S3, Azure Blob and GCS all distinguish known-object access from listing access. Credential-bearing presigned/SAS URLs must be classified separately from anonymous access. [A1] [A6] [Z4] [G5]

## 2. How should effective permissions and deeper paths be investigated without an arbitrary hop ceiling?

### Takeaway

Continue a chain as long as each next edge is relevant, explicitly authorized, supported by prior evidence, affordable within the shared plan, and reversible on owned resources. Do not replace this with either a fixed depth cap or a blanket prohibition on writes: the correct gate is **per-branch readiness**, followed by a minimal synthetic privileged-canary proof rather than credential collection or production impact.

### Cited Findings

- AWS IAM permissions can combine into escalation paths through policy control, usable role trust and a compute consumer. `PassRole` alone is not execution or role assumption; the consumer service and role trust must also work. [A14] [A10]
- AWS federation risk includes broad account trust, OIDC audience/subject over-trust, provider tenant-to-role binding, and externally governed session tags. A missing service source condition is not proof of a confused deputy unless the service supports reaching the foreign destination and other policy/resource constraints permit it. [A2] [A3]
- GCP federation includes **direct** external-principal IAM grants and service-account impersonation. A pool/provider's administration policy is not the same thing as a resource authorization binding. Provider editing or restoration matters only when the resulting accepted subject/set already has usable access. [G3] [G4]
- Azure federation binds issuer, audience and subject to an Entra workload identity. Safe workflow names alone do not establish safety of all code and data executed in that workflow context. [Z3]
- Kubernetes-to-cloud paths are not interchangeable: AWS IRSA differs from EKS Pod Identity; GKE may use direct workload principals rather than KSA-to-service-account annotations; AKS local admin credentials, Entra Kubernetes authorization and Workload ID are different boundaries. [K0] [K1] [A11]
- GCP build behavior depends on the **actual configured runtime account** and project vintage/policy; the page distinguishes the legacy build identity from Compute Engine default/user-managed accounts and from the Cloud Build service agent. [G13]
- Azure Storage key-listing can reach the data plane when Shared Key is accepted, and Function App content can be backed by storage with a different permission boundary. Key Vault's legacy access-policy model differs from Azure RBAC. [Z13] [Z12] [Z9]

### Inferences

#### Branch-readiness model for BugVault — recommendation, not an implemented feature

For every proposed edge, record the exact **source principal → operation → resource → resulting principal/capability → next canary**, plus account/tenant/project, region, network path, authentication mechanism, runtime/revision/version, conditions and time. A convenient role name, permissive allow statement or graph edge must not skip request-context evaluation. This recommendation follows the conditional-path distinctions in AWS, GCP and Kubernetes sources. [A0] [A5] [G3] [G4] [K1]

Use these independent statuses rather than one coarse “cloud checked” flag:

- `lead`: secondary-source or configuration hint; no capability proof.
- `mapped`: exact asset, owned principal and prerequisite chain identified.
- `ready-read` / `ready-write` / `ready-execution`: the **existing written campaign plan** covers this operation, destination and proof; tools are connected, shared request/time/cost budgets remain, and cleanup is feasible. These are proposed planning states, not existing recon grant names.
- `observed`: a particular boundary/capability produced a receipt; next edges remain unproven.
- `canary-proven`: deterministic replay, separate negative control, owner positive control and attributable marker effect establish the exact unauthorized boundary on synthetic resources.
- `negative-variant`, `blocked-scope`, `blocked-grant`, `blocked-tool`, `blocked-cost`, `blocked-cleanup`, `stale` or `unknown`: preserve the exact reason and evidence; do not silently promote or close sibling branches.

**No arbitrary depth ceiling:** after each proven edge, re-evaluate the next one. Terminate when the intended privileged-canary impact is sufficiently established, the next edge adds no reportable value, a dependency fails, the approved budget is exhausted, side effects appear, or cleanup/readiness is lost. Revisit only after a relevant context/grant/evidence change. Cycle detection should key on principal, operation, resource and context/version, not on a universal maximum number of hops. “Unlimited depth” is not unlimited traffic, spend, resource creation or authority.

**Write readiness is not a blanket write ban:** a standing authorized plan may cover a reversible mutation, disposable deployment, controlled policy change, test enrollment, token exchange or narrow test execution. Name the object, expected delta, deadline, owner baseline, readback and cleanup before proceeding; avoid repeatedly asking for exceptions already covered by that plan. A read-only plan cannot be silently widened because a deeper path looks promising.

**Scope and stop conditions remain mandatory:** identify all accounts/tenants/projects, cloud API and data-plane destinations, external integrations and redirect hops covered by the written plan; a discovered identity or resource never widens scope. Reconcile traffic, API calls, object creation, storage/compute spend and time across all approved channels. Throttling, challenges, unexpected errors/side effects, genuine sensitive data, lost attribution or failed cleanup stop the affected branch for owner review; they never authorize alternate transport, retries beyond budget, monitoring evasion or guard weakening.

#### Minimal synthetic privileged-canary design

1. **Define the boundary, not an admin spectacle.** Give fixture identity B exactly one meaningful privilege on a disposable target that A lacks: read a non-secret marker, write a marker object/row, invoke an inert handler, or record an approved state transition. Do not give the tester real administrator rights solely for the proof.
2. **Owner positive control:** B legitimately reaches marker M before the test. **Negative control:** A's direct attempt is denied, and an independent wrong subject/private object/unused artifact does not produce the effect. Use distinct markers, not duplicated responses.
3. **Prove each edge in order:** changed configuration accepted → actual consumer/revision used → resulting principal observed → resource operation accepted → terminal marker readback. An HTTP 200, graph label, token-shaped value, trigger creation or callback is not a substitute.
4. **Do the operation in place where practical.** A disposable function/pod/build can perform the narrow canary action under B without returning B's credential. Keep bearer tokens, private keys, real secret values and production records out of output, logs and research artifacts.
5. **Prove causality with owner evidence.** Capture exact actor/target IDs, request/build/run/revision/version, ordered time window, provider/application audit references and before/after/control hashes. An actor-supplied identity string alone is not authoritative. Redact values while preserving stable source-qualified IDs.
6. **Clean up with evidence:** restore policy/config/version; remove fixture deployments, triggers, test credentials, temporary membership and artifacts; revoke/expire delegated sessions where supported; remove resources that continue charging; verify marker absence and that A is denied again. Preserve receipts rather than deleting audit evidence. Track unrecoverable/retained items and billing deadlines explicitly.

This proof design is an original safe adaptation of the conditional identity/consumer paths described by the sources, not a claim that HackTricks supplies this canary protocol. [A10] [A14] [G4] [G13] [K0]
