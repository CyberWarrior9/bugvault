## 1. What policy graph determines effective permission, and where does an apparent IAM allow cease to be effective?

### Takeaway

An `Allow` statement is a candidate authorization edge, not an end-to-end permission. Evaluate the exact principal/session, action, authorized resource set, conditions, account relationship, organization guardrails, and service-specific dependencies; in particular, **a permissions boundary's implicit deny does not cap every same-account resource-policy grant**, while applicable explicit denies remain controlling. [AWS evaluation detail](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)

### Cited Findings

#### Core evaluation and principal/session distinctions

- AWS processes authentication, request context, and the applicable policy types. In the ordinary same-account case, identity- and resource-based allows combine as a union; identity-policy permission constrained by a boundary combines as an intersection. The overview is not a universal formula covering every principal type or service. AWS explicitly identifies role trust policies and KMS key policies as exceptions requiring appropriate resource-side authorization. [Evaluation overview](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic.html); [Detailed evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)
- An **applicable explicit deny** in the evaluated policy types overrides an allow. Applicability matters: action, resource, principal, condition, account, and policy scope must actually match. A boundary, SCP, RCP, or session policy does not independently confer permission merely because it allows an action. Avoid the overbroad shorthand “all policies are intersected.” [Detailed evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html); [Boundaries](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html); [SCPs](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html); [RCPs](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps.html)

| Authorization path | Relevant implicit-deny behavior in the documented same-account case | Guard against a false conclusion |
|---|---|---|
| Identity-based allow to a user/role | Limited by its applicable boundary and, for a session, session policy | A broad managed policy alone is not effective administrator access. |
| Resource policy grants directly to an IAM user ARN, not its federated session | An implicit deny in the identity policy or boundary does not limit that direct grant | “Boundary omits the service” is not necessarily a blocker. Applicable explicit denies still matter. |
| Resource policy grants to an IAM role ARN | An implicit deny in a boundary or session policy limits the grant | Do not treat a role ARN as a direct role-session grant. |
| Resource policy grants directly to an assumed-role **session ARN** | Identity-policy, boundary, and session-policy implicit denies do not limit the directly granted permission | This does not override explicit denies, applicable organization controls, or service-specific prerequisites. |
| Resource policy grants directly to an STS `GetFederationToken` federated-user session ARN | The same direct-session implicit-deny exception applies | Distinguish it from granting to the ARN of the IAM user that federated. |
| Resource policy grants to the IAM user that federated, while the request is made by its federated session | Boundary/session-policy implicit denies can limit the session's request | The original IAM user and current session are different authorization subjects. |
| Resource policy uses wildcard `Principal` plus an `aws:PrincipalArn` role condition | AWS documents that boundary/session-policy implicit-deny restrictions do not limit this grant in the described case | Preserve the exact statement form; do not normalize it into `Principal: role ARN`. Explicit denies and other applicable controls remain relevant. |

Source for the table: [AWS principal-specific evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html); corroborated by [Boundary evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html#access_policies_boundaries-eval-logic) and [Role principals](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-roles). These are **same-account** distinctions; do not transplant direct-session exceptions into a cross-account calculation without applying the documented cross-account rules and the relevant service model.

- A role is an IAM identity; the caller after role assumption is a **role session principal**. For an assumed-role request, `aws:PrincipalArn` contains the **role ARN**, not the assumed-role session ARN. Anonymous requests lack that key. Comparing the wrong ARN can make an apparent permission inapplicable. [Role/session principals](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-role-session); [Principal ARN context](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-principalarn)
- An account ID or `arn:...:iam::ACCOUNT:root` in the ordinary resource-policy `Principal` element delegates authority to the **account**; it is not necessarily restricted to that account's root user. In contrast, a root ARN in an `aws:PrincipalArn` condition identifies the root principal. Endpoint policy documentation also describes a gateway-endpoint-specific account-principal caveat, reinforcing the need for service-specific interpretation. [Account principals](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-accounts); [Principal ARN](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-principalarn); [Gateway endpoint principals](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-access.html#vpc-endpoint-policies-gateway)
- In role trust policies, IAM converts a specifically named role/user principal ARN to its unique principal ID. Deleting and recreating that identity does not automatically restore the trust relationship. Conversely, condition-key ARNs are not converted to principal IDs, so an `aws:PrincipalArn` condition can continue matching a newly created role with the same ARN/name. A stale principal ID is not proof of a currently assumable role. [Role principals and deletion](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-roles); [User principals](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html#principal-users)
- AWS warns against `NotPrincipal` with `Deny` in resource policies for users/roles with boundaries: it always denies an IAM principal with a boundary attached, regardless of the identities listed in `NotPrincipal`. This is an important **unexpected blocker**, not evidence of broad access. [Boundary warning](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)

#### SCP/RCP attachment direction and current exceptions

| Layer | What it constrains | Important limits/exceptions |
|---|---|---|
| SCP | IAM principals managed by organization **member accounts**, including their root users | Not management-account users/roles; not service-linked roles; does not directly constrain an outside principal merely because it accesses a resource in a member account. Delegated-administrator member accounts remain affected. |
| RCP | Authorized resources in organization **member accounts** for supported services, including access by outside principals | Not management-account resources; not calls by service-linked roles; not AWS managed KMS keys; `kms:RetireGrant` is explicitly excluded. Check the current supported-service/action/resource list. |
| Boundary | Maximum permission from the identity-policy route for its user/role | Not an independent allow and not a universal cap on the direct resource grants listed above. |
| Session policy | The scoped temporary session's identity-derived permission | Cannot expand the assumed role's identity-policy permission, but direct same-account session grants require the separate evaluation above. |

Sources: [SCP effects and exclusions](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html#scp-effects-on-permissions); [RCP effects and exclusions](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps.html#rcp-effects-on-permissions); [Boundaries](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html); [AssumeRole session policies](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html).

- Organization evaluation must include the relevant **root → OU(s) → account** path, not just policies directly attached to an account. SCPs require the action to survive the applicable hierarchy. With RCPs enabled, AWS automatically attaches the non-detachable `RCPFullAWSAccess` allow policy to entities; restrictions are introduced with deny statements. “No explicit allow in this custom RCP” is therefore not by itself a demonstrated deny. [SCP inheritance/effects](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html); [RCP evaluation](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps_evaluation.html)
- **Version-sensitive point:** the retrieved RCP page lists many more services than an older, small launch-era list. It includes S3, KMS, and STS. Use the live supported-service list and the operation's authorized resource types rather than a hard-coded historical count. An RCP applies according to the resources authorized by the operation, not merely the service name in a proposed path. [Current RCP services and operation-resource scope](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps.html#rcp-supported-services)

#### Cross-account trust, conditions, and downstream identity changes

- For ordinary direct cross-account resource access, both evaluations must allow: the requester's account must permit the principal's action and the resource owner's resource policy must permit the access. A bucket/key/role policy naming an external account is not proof that a usable principal in that account can exercise the permission. [Cross-account evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html)
- Role assumption has a separate **trust policy** (“who can assume”) and permissions policy (“what the resulting role can do”). For cross-account `AssumeRole`, the caller needs the appropriate delegated permission and the destination role must trust it. Same-account direct user trust can authorize assumption without a separate identity-policy allow. Success at assumption does not establish any particular data-plane permission. [AssumeRole permissions and trust](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)
- Trust conditions can require MFA, an external ID, or controlled session attributes. Passing source identity and session tags can introduce additional authorization requirements. Role chaining has its own duration and attribute behavior; it is not safe to infer it from a single role's permissions document. [AssumeRole](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html); [Source identity requirements](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html#id_credentials_temp_control-access_monitor-perms)
- An external ID mitigates a **multi-customer confused deputy** by binding the deputy's customer context to a role trust condition. AWS does **not** treat external IDs as secrets. The third party must control unique customer assignment and send the correct customer's value. An exposed external ID or a role ARN alone is not proof of account compromise; missing `ExternalId` is not a universal vulnerability in every trust arrangement. [External IDs](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-user_externalid.html); [Cross-account confused deputy](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html#mitigate-confused-deputy)
- For direct AWS service-principal access, use the actual integration's `aws:SourceArn`, `aws:SourceAccount`, `aws:SourceOrgID`, or `aws:SourceOrgPaths` support to assess confused-deputy protection. AWS notes that some integrations have additional controls. Missing one familiar condition key is not conclusive if another supported mechanism supplies the restriction. `aws:SourceArn` is not a substitute for the human/role principal ARN. [Cross-service confused deputy](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html#cross-service-confused-deputy-prevention); [Source ARN availability](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-sourcearn)
- **FAS is a distinct path:** forward access sessions let a service call downstream services with the initiating IAM principal's permissions/session attributes. Both the initial and downstream service authorize the principal. S3 → KMS decryption is AWS's example. Source VPC/endpoint context from an initial endpoint request is not carried into downstream FAS requests; `aws:ViaAWSService`/`aws:CalledVia` conditions may be necessary to authorize the intended path. A working front-end service call is not evidence that every downstream operation will succeed. [Forward access sessions](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md)
- Do not collapse a direct service principal, FAS, a service role, and a service-linked role. `aws:PrincipalIsAWSService` is true for direct service-principal calls, not calls using an IAM principal's credentials, service role, or service-linked role. The applicable organization exceptions and condition keys differ. [PrincipalIsAWSService](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html#condition-keys-principalisawsservice); [FAS](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md)
- Conditions must model **missing keys**, not just matching values. `IfExists` makes a missing-key condition true; a negated `...IfExists` under `Deny` can therefore deny a request when the key is absent. `Null: true` checks absence and `Null: false` checks presence/non-null. Conditions referring to the wrong request context can invalidate an apparent allow or unexpectedly trigger a deny. [IfExists](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html#Conditions_IfExists); [Null](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html#Conditions_Null)
- A VPC endpoint policy is an additional endpoint-use control, **not a replacement for identity or resource authorization**. The default allows full endpoint access; a restrictive endpoint policy can block the relevant path, and not every service supports endpoint policies. Record the actual network path before treating an endpoint policy as applicable. [Endpoint policies](https://docs.aws.amazon.com/vpc/latest/privatelink/vpc-endpoints-access.html)
- `iam:PassRole` is a permission checked when a service API receives a role, not a standalone API and not proof of direct role assumption. Passing requires the appropriate same-account arrangement, role trust, and service configuration permission; `iam:PassedToService` can restrict the destination service. There is no standalone `PassRole` CloudTrail event: inspect the underlying resource creation/modification event. [PassRole](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_passrole.html)

### Inferences

#### Proposed policy-graph design — explanatory, provenance-bearing, and fail-closed

The following is a **design proposal** derived from the documented distinctions, not a claim that AWS exposes this schema or that BugVault implements it. Its purpose is to prevent a policy-text edge from becoming an unsupported exploitation claim. [Evaluation basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html); [Cross-account basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html); [FAS basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md)

1. **Nodes:** account/partition/Region; organization root and OU; IAM user; IAM role **with immutable principal ID**; issued session; IdP/trust configuration; direct AWS service principal; service/service-linked role; resource including version/owner; access point; endpoint; KMS key/policy/grant; and an exact operation. Keep issuing role and issued session separate. [Principal basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_principal.html); [Organization basis](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps.html)
2. **Evidence-bearing edges:** `identity-allows`, `resource-allows`, `explicit-denies`, `bounded-by`, `session-scoped-by`, `scp-constrained-by`, `rcp-constrained-by`, `trusted-to-assume`, `issues-session`, `service-uses-role`, `FAS-on-behalf-of`, `requires-dependent-operation`, `uses-key`, `grant-authorizes`, and `endpoint-gates`. Store the source statement/grant, policy version/default-version state, attachment path, capture date, owner attestation, evidence hash when actually available, condition AST, and applicability predicate. Never invent an attachment, session policy, response ID, or hash. [Evaluation basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html); [Grant basis](https://docs.aws.amazon.com/kms/latest/developerguide/grants.html)
3. **Operation tuple:** principal type and ARN/ID; session issuer and non-secret session attributes; action; **all** authorized resources; resource owner/account; service/API version; time; source network/endpoint; transport; organization memberships; and whether this is direct, assumed-role, service-principal, service-role, or FAS execution. Unknown context remains unknown, not a wildcard that silently satisfies conditions. [Context/condition basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html); [FAS basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md)
4. **AND/OR structure rather than simple reachability:** alternative valid allow mechanisms are OR edges; prerequisites such as cross-account bilateral permission or S3 plus KMS authorization are AND/hyperedges. A deny is an applicable veto, not a negative edge that can be routed around. Keep service-specific principal semantics rather than flattening every resource policy into the same rule. [Cross-account basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic-cross-account.html); [KMS basis](https://docs.aws.amazon.com/kms/latest/developerguide/policy-evaluation.md)
5. **Evaluate each hop independently:** identify actual principal → collect applicable policy snapshots → evaluate matching explicit denies → select the correct grant route/principal semantics → apply applicable boundary/session/organization/endpoint gates → evaluate service dependencies and resource state → attach an evidence-qualified outcome. On role assumption, create a new session node and recompute the destination action's evaluation; do not intersect every historical actor's policies into a timeless “user permission.” This is a modeling inference from AWS's separation of assumption, sessions, and resource requests. [AssumeRole basis](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html); [Evaluation basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)
6. **Separate read access from control/mutation hypotheses:** a possible policy edit, boundary change, role-passing configuration, or grant creation is its **own exact operation** requiring its own authorization and owned-resource change evidence. A blocked data edge must not be relabeled exploitable because the graph imagines changing the blocking policy. Boundary-protected administrative delegation and `PassRole` illustrate why these are separate checks. [Boundary delegation basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html#access_policies_boundaries-delegate); [PassRole basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_use_passrole.html)
7. **Proposed statuses:** `candidate-from-policy`, `policy-supported-for-context`, `blocked-by-known-control`, `unknown-missing-policy-or-context`, `owned-canary-demonstrated`, and `stale-after-change`. Store the first evidenced blocker **and all other known gates**. A denial closes only the tested context, while an unknown prevents a positive effective-permission claim. These labels are proposed evidence discipline, grounded in AWS's context-sensitive evaluation and warning that simulation may differ from reality. [Evaluation basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html); [Simulator limitations](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_testing-policies.html#policies_policy-simulator-how-it-works)

**“All paths, deep” interpretation:** expand documented candidate relationships and list missing prerequisites at every depth, including alternative allow routes and downstream dependencies. Do not convert missing authorization, an explicit deny, a provider policy, or an out-of-scope account into an invitation to bypass it. For this assignment, expansion remains public-document reasoning only; no graph branch authorizes a live action. [Technical reason for preserving blockers](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)

## 2. How do S3 public-access controls, ownership, KMS policies, grants, and conditions invalidate apparent storage access?

### Takeaway

Storage exposure must survive **S3's effective public-access settings and object ownership**, then the exact operation's additional authorization requirements. For SSE-KMS, a bucket/object allow alone does not demonstrate plaintext access; evaluate KMS authorization, the actual key, grant constraints, service path, and Bucket Key/cache behavior. [S3 BPA](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html); [Ownership](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html); [SSE-KMS permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html)

### Cited Findings

#### S3 defaults, Block Public Access, and ACL/object ownership

- AWS states that new buckets, access points, and objects do not allow public access by default, and that **Bucket owner enforced** is the default Object Ownership mode for newly created buckets, with ACLs disabled. This is a statement about creation defaults, not evidence that an existing bucket retains them. Treat general-purpose and directory buckets as different resource types requiring their own service details. [BPA overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html); [Object Ownership defaults](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html)
- **Current documented control:** BPA exists at organization, account, bucket, and access-point levels. Organization-level S3 policies enforce all four settings together rather than exposing four independently selectable organization flags. Applicable lower-level settings cannot weaken the effective stricter configuration. Organization-level S3 BPA policy is a separate control from SCP/RCP authorization policy. Account BPA settings apply globally but may propagate across Regions at different times. [BPA evaluation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html); [Organization S3 policies](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_s3.html)

| BPA flag | Actual documented effect | What would be a false positive/false negative? |
|---|---|---|
| `BlockPublicAcls` | Rejects applicable attempts to set public ACLs, including public ACLs supplied with object writes | It does **not** alter existing ACLs or policies. Do not infer that a historical public ACL is neutralized by this flag alone. |
| `IgnorePublicAcls` | Ignores public ACL permissions on the bucket and its objects | Persisted public ACL configuration does not establish effective public access. This flag does not itself prevent writing a public ACL. |
| `BlockPublicPolicy` | Rejects applicable new public bucket/access-point policies | It does **not** retroactively neutralize an existing public policy by itself. |
| `RestrictPublicBuckets` | For a bucket/access point with a public policy, restricts access to the documented authorized owner-account users and AWS service principals | A public statement can cause otherwise specifically named cross-account grants in the same policy to be blocked too. Conversely, it is not a blanket ban on every non-public cross-account policy. |

Source: [Four BPA settings and mixed-policy example](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html#access-control-block-public-access-options). All rows remain subject to the other applicable authorization controls; “authorized” does not mean every same-account identity automatically has data access.

- BPA's “public” classification is not a naive search for `Principal: "*"`. Fixed trusted values such as an organization ID or VPC/endpoint condition can make a policy non-public under S3's rules. Conversely, overly broad source-IP ranges can remain public. Public ACL groups include `AllUsers` **and** `AuthenticatedUsers`; the latter is not a synonym for the customer's own workforce. Access-point classification has additional rules, including VPC-origin behavior. [S3 meaning of public](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html#access-control-block-public-access-policy-status)
- BPA does not rewrite existing policy/ACL grants. Removing protection can reactivate preserved permissions. Likewise, disabling ACLs with Bucket owner enforced removes ACLs from access evaluation, but re-enabling ACLs can restore preexisting ACL permissions. This is **latent configuration risk**, not proof of present public access. [BPA persistence](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html#access-control-block-public-access-options); [Re-enabling ACLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html#object-ownership-changes)
- With Bucket owner enforced, the bucket owner owns all objects and ACLs do not grant access. Uploads with no ACL or bucket-owner-full-control ACLs can be accepted; unsupported ACL settings fail with `AccessControlListNotSupported`. A readable ACL or an attempted ACL change does not prove an effective public grant. [Object Ownership changes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html)
- If ACLs are enabled and object owner differs from bucket owner, S3 object authorization can involve **user, bucket, and object contexts**, including object-owner permission and bucket-owner explicit denies. A bucket policy alone does not universally grant access to every cross-account-owned object in that bucket. [Object-operation authorization](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-auth-workflow-object-operation.html)
- S3 encrypts new object uploads with SSE-S3 as a baseline; AWS dates this change to **January 5, 2023**. Encryption at rest is not an access-control deny: a claim that a current new S3 upload is “unencrypted by default” is stale, while “encrypted” alone does not establish privacy from a principal authorized to read it. [S3 encryption defaults](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html)

#### KMS authorization and current grant model

- Every KMS key has a `default` key policy. IAM policies cannot **allow** use unless the key policy enables the relevant IAM delegation; IAM denies do not require that delegation. Root or the key creator does not obtain an unconditional right to use the key. A same-account identity policy containing `kms:*` is not sufficient by itself. [KMS key policies](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html)
- **Current documented model:** a KMS key shared through AWS RAM can additionally have an `AWS_RAM` key policy. KMS evaluates both key policies; a deny in the `default` policy overrides an allow in `AWS_RAM`. Resource-share membership, managed permission, invitation acceptance where applicable, consumer IAM permissions, and propagation all matter. An inventory assuming “exactly one key policy” can now miss a permission source. [KMS evaluation](https://docs.aws.amazon.com/kms/latest/developerguide/policy-evaluation.md); [Key-policy overview](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html)
- In the documented cross-account **key-policy/IAM** route, permission is needed on the key owner's side and in the external principal's account. Only supported cross-account operations are effective: AWS lists cryptographic operations and specified metadata/grant operations. A cross-account `kms:ScheduleKeyDeletion` allow, for example, does not make that operation usable cross-account. Grants are an additional documented access mechanism and must be evaluated independently rather than ignored because a particular identity-policy allow is absent. [Cross-account KMS permissions](https://docs.aws.amazon.com/kms/latest/developerguide/key-policy-modifying-external-accounts.html); [Grants](https://docs.aws.amazon.com/kms/latest/developerguide/grants.html)
- Distinguish `Resource: "*"` **inside a key policy**, whose resource is its associated key, from a broad resource selector in an IAM policy. A text-only wildcard alert can otherwise exaggerate scope. Key policies are Regional; specify the actual key/account/Region and do not equate identical alias names across accounts. [Key-policy resource scope](https://docs.aws.amazon.com/kms/latest/developerguide/key-policy-modifying-external-accounts.html#cross-account-key-policy); [Regional key policies](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html)
- Grants allow, never deny, and each grant applies to **one KMS key**. Allowed operations must be supported by both the grant mechanism and the key's type/usage. Grants can authorize cryptographic operations, certain metadata actions, and delegation via `CreateGrant`; they are not unrestricted key administration. [Grant semantics and operations](https://docs.aws.amazon.com/kms/latest/developerguide/grants.html); [CreateGrant API](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateGrant.html)
- A principal receiving `CreateGrant` through a **policy** can, subject to conditions and applicable controls, grant permitted grant operations that it does not itself hold. A principal receiving `CreateGrant` through a **grant** is limited to a subset of the parent grant's operations and constraints at least as strict. Thus the provenance of `CreateGrant` permission materially changes the delegation edge. [Grant delegation](https://docs.aws.amazon.com/kms/latest/developerguide/grants.html); [Parent/child constraints](https://docs.aws.amazon.com/kms/latest/developerguide/create-grant-overview.html#grant-creategrant)
- **Do not freeze an obsolete grant schema.** The current API distinguishes `GranteePrincipal` and `GranteeServicePrincipal` and requires one, not both. A service-principal grantee requires a `SourceArn` grant constraint and either a retiring principal or retiring service principal. `SourceArn` grant constraints support all KMS key types; the developer guide says they are evaluated when the request is made by an AWS service. This is distinct from the older assumption that all grant constraints are encryption-context constraints. [Current CreateGrant schema](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateGrant.html); [SourceArn constraints](https://docs.aws.amazon.com/kms/latest/developerguide/create-grant-overview.html#grant-constraints-source-arn)
- Encryption-context constraints have **Equals** versus **Subset** semantics: equality requires the prescribed context; subset requires the prescribed pairs but permits additional pairs. These constraints are for symmetric encryption keys and do not constrain `DescribeKey` or `RetireGrant`. SourceArn constraints can apply to `DescribeKey` but do not constrain `RetireGrant`. **Case-sensitivity documentation conflicts are recorded under Gaps below; do not silently assume a case-based bypass or protection.** [Constraint guide](https://docs.aws.amazon.com/kms/latest/developerguide/create-grant-overview.html#grant-constraints); [GrantConstraints API](https://docs.aws.amazon.com/kms/latest/APIReference/API_GrantConstraints.html)
- Grant creation/retirement/revocation is eventually consistent. A short period of continued use after revocation, or denial immediately after creation, is not by itself a permanent authorization bypass. AWS calls grant tokens **nonsecret** representations of grants used for consistency handling; possession alone should not be described as possession of AWS credentials. This assignment neither collected nor used any token. [Grant tokens and consistency](https://docs.aws.amazon.com/kms/latest/developerguide/grants.html#grant_token)

| KMS condition/control | Effective meaning relevant to validation | Required anti-false-positive distinction |
|---|---|---|
| `kms:ViaService` | Restricts applicable key-resource operations to supported service-mediated FAS requests | An allow through S3/another supported service is not automatically a direct-call allow; confirm exact service/Region and permissions to both services. |
| `kms:GrantIsForAWSResource` | Applies to `CreateGrant`, `ListGrants`, and `RevokeGrant` via an integrated service's FAS request on the principal's behalf | The common `true` condition does not let the named principal create a grant directly. It is not a blanket “grant belongs to my account” test. |
| `kms:GrantOperations` | Multivalued `CreateGrant` request operation set | `ForAllValues` constrains every requested operation; `ForAnyValue` requires only one matching operation and can permit additional operations. Do not confuse the two. |
| `kms:GranteePrincipal` / `kms:GranteeServicePrincipal` | Restricts the corresponding grantee field of a proposed grant | A permission conditioned on a particular grantee is not arbitrary delegation to every principal. |
| `kms:GrantConstraintSourceArn` | Restricts the `SourceArn` constraint in a `CreateGrant` request | This creation-time policy key is not identical to the grant's later resource-origin evaluation. Preserve both layers. |
| `kms:GrantConstraintType`, retiring-principal/service-principal controls | Restrict permitted constraints and retirement arrangements at creation | Absence of an inline context-looking clause is not sufficient if another applicable policy condition restricts creation. |
| `kms:EncryptionContext:context-key` | Single-valued policy condition on a particular context pair | AWS warns against set operators with this single-valued key and rejects specified overly permissive `ForAllValues` policy forms; historical snippets must be rechecked. |
| `kms:EncryptionContextKeys` | Multivalued key-set restriction | A permitted set of names is not necessarily a requirement that a particular context pair be present; evaluate presence/value requirements too. |

Sources: [Grant authorization controls](https://docs.aws.amazon.com/kms/latest/developerguide/grant-authorization.html); [ViaService](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.md#conditions-kms-via-service); [GrantIsForAWSResource](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.md#conditions-kms-grant-is-for-aws-resource); [GrantOperations](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.md#conditions-kms-grant-operations); [GrantConstraintSourceArn](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.md#conditions-kms-grant-constraint-source-arn); [Encryption-context conditions](https://docs.aws.amazon.com/kms/latest/developerguide/conditions-kms.md#conditions-kms-encryption-context). #### S3 → KMS dependency, encryption context, and Bucket Key caveats

- For SSE-KMS, S3 documents `kms:GenerateDataKey` for an encrypted `PutObject`, `kms:Decrypt` for download, and both for multipart upload. An object read must be authorized in S3 **and** satisfy the appropriate KMS path; multipart and simple writes cannot be conflated. The key must be compatible and in the same Region as the bucket. [SSE-KMS permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html); [FAS authorization example](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md)
- Objects encrypted with an AWS managed `aws/s3` key cannot be shared to an accessing principal in a different account; customer managed keys are needed for that cross-account sharing. The bucket owner's account and the requesting principal's account must not be conflated: AWS also documents cross-account storage operations where uploading and accessing principals are in the **same** account. [SSE-KMS cross-account details](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html#sse-kms-cross-account-operations)
- S3 warns that a KMS **alias** can resolve in the requester's account rather than the bucket owner's. Identify the actual fully qualified key, not a familiar alias string. KMS authorization still does not establish access to every ciphertext encrypted under that key; the requested data object and cryptographic context remain separate requirements. [SSE-KMS key selection](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html#sse-kms-cross-account-operations); [KMS authorization](https://docs.aws.amazon.com/kms/latest/developerguide/policy-evaluation.md)
- Encryption context is not secret and can appear in logs. Cryptographic decryption requires the encryption context used at encryption. S3's default context uses the **object ARN without Bucket Keys** and the **bucket ARN with Bucket Keys**. A policy written for object-ARN context can cease matching when Bucket Keys are enabled. [S3 encryption context](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html#encryption-context); [Bucket Key policy changes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html#bucket-key-policies)
- **Important downstream qualification:** S3 Bucket Keys cache a short-lived bucket-level key. AWS states that subsequent requests benefiting from it do **not** generate a KMS API call or validate access against the KMS key policy on each such request. Keys are fetched at least once per requester; requester distinctions include role/account and the same role with different scoping policies. Do not claim that every S3 read produces a fresh KMS authorization event, or that a missing per-object KMS event proves no access occurred. [Bucket Key authorization/cache behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html#bucket-key-overview)
- KMS key state and compatible operations are separate from policy permission. `CreateGrant`, for example, documents disabled/incompatible-state errors. A service error or incompatible key type is not proof of a successful permission escalation merely because a policy contains an allow. [CreateGrant state and errors](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateGrant.html)

#### Proposed invalidation-first storage hunt matrix

Each row is a **hypothesis/proof requirement**, not a finding or an instruction to change a production setting. Use existing owner exports and separately authorized disposable canary records; preserve a blocked row rather than trying to remove the blocking control. The rationale is AWS's multi-layer authorization model. [S3 BPA basis](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html); [KMS evaluation basis](https://docs.aws.amazon.com/kms/latest/developerguide/policy-evaluation.md)

|---|---|---|
| Public-looking S3 bucket policy | Fixed trust conditions; effective organization/account/bucket/access-point BPA; RCP; explicit deny; exact action/resource | Current effective configuration plus access to a unique **owned** marker through the claimed principal/path, with a distinct denied control. Public policy text alone is insufficient. |
| Public ACL in an old export | Bucket owner enforced; `IgnorePublicAcls`; object owner; changed ACL state | Current ownership/BPA and marker-backed access. If ACLs are disabled/ignored, classify as latent configuration, not current ACL exposure. |

Encryption metadata or a bucket-policy allow is not plaintext exposure. |

Any claimed cryptographic effect needs separate harmless canary evidence; a prospective grant edge is not that effect. |
| Existing external grant | Wrong grantee/session; unsupported operation/key type; context/SourceArn mismatch; revocation state; applicable denies | Current grant record, relevant policy context, exact permitted canary effect, and distinct nonmatching control. |
| Service-principal trust lacks one familiar source condition | Other integration controls; RCP; required grant SourceArn; service-created encryption context; no controllable source resource | An operator-owned source resource and destination canary, bound service-attribution evidence, and a negative control changing only the relevant authorization context. “Missing `SourceArn` text” is only a lead. |
| Read remains possible shortly after grant/policy change | Grant eventual consistency; S3 Bucket Key reuse; stale configuration or logs | Time-ordered policy/configuration receipts and documented cache/propagation qualifications. Do not call documented transient behavior a permanent bypass. |

### Gaps

- **Official-source conflict — grant constraint case sensitivity:** the developer guide describes `EncryptionContextEquals`/`Subset` pairs as exact, case-sensitive matches; the API `GrantConstraints` page explicitly says that **in a grant constraint the key is not case sensitive, but the value is**, while cryptographic encryption/decryption context matching is fully case sensitive. Do not adjudicate a case-variation finding from documentation alone. Keep the two claims separate and require service clarification or separately authorized owned-canary evidence before claiming a case-dependent effect. [Developer guide](https://docs.aws.amazon.com/kms/latest/developerguide/create-grant-overview.html#grant-constraints-ec); [API reference](https://docs.aws.amazon.com/kms/latest/APIReference/API_GrantConstraints.html)
- The documentation retrieved describes newer service-principal/SourceArn grants and AWS RAM-managed key policies but does not establish their launch date or availability for every integration, SDK version, partition, or Region. Source/API schemas support the documented model; no account was queried to establish actual deployment support. [CreateGrant schema](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateGrant.html); [RAM key policies](https://docs.aws.amazon.com/kms/latest/developerguide/key-policies.html)
- This research does not determine a precise Bucket Key cache expiry or universal immediate-revocation SLA. The cited page describes short-lived/time-limited reuse, not a single guaranteed maximum for every observed path. Preserve temporal uncertainty rather than asserting a fixed exploitation window. [Bucket Keys](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html)
- No bucket's actual creation-era defaults, current effective organization S3 policy, object ownership, encryption mode, key state, grant set, or applicable RCP is known here. General documentation cannot establish any specific bucket's exposure. [BPA evaluation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html); [Object Ownership](https://docs.aws.amazon.com/AmazonS3/latest/userguide/about-object-ownership.html)

## 3. What do STS attribution, Access Analyzer, simulation, and IMDS actually prove, and what evidence should a safe validation plan require?

### Takeaway

Identity attribution, policy-derived possible access, and demonstrated resource access are different evidence classes. STS identity output and Access Analyzer findings are useful context, not proof of unrestricted cloud control; IMDS must remain a **conceptual delivery/dependency model** here, without any credential reading, token use, or metadata probing. [GetCallerIdentity](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html); [Analyzer concepts](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html); [EC2 roles](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-roles-for-amazon-ec2.html)

### Cited Findings

#### STS identity attribution and session provenance

- `GetCallerIdentity` returns `Account`, `Arn`, and `UserId` for the caller. AWS says no permissions are required and that even an explicit deny of `sts:GetCallerIdentity` does not prevent obtaining the same identity information. It is therefore a **documented special case**, not evidence that explicit denies on data/control-plane actions can be bypassed. Success would establish attribution of that caller, not resource permission, account administration, or authorization to validate someone else's credentials. **No call was made in this research.** [GetCallerIdentity API](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html)
- A session ARN and role ARN are distinct. `AssumeRole` accepts a role session name that appears in subsequent attribution/logs; a session-name string is not automatically a verified human identity. The same API separately documents source identity, session policies, tags, and transitive tags. [AssumeRole session attributes](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)
- Source identity persists across role chaining and cannot be changed after it is set. However, AWS states that it **does not control the chosen source-identity value**: the administrator must control how users/IdPs supply it. `sts:SetSourceIdentity` permissions and trust configuration are needed, including across chained-account boundaries. A claimed source identity is not independently authenticated end-user provenance just because it appears in a log. [Source identity behavior and permissions](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html)
- CloudTrail `userIdentity` can distinguish IAM users, assumed roles, federated users, AWS accounts/services, and other identity types. For a role session, `sessionContext.sessionIssuer` identifies the issuing role; source identity and session attributes can add provenance when present. `ec2RoleDelivery` distinguishes IMDS delivery versions where recorded. These fields have optionality and do not justify inventing absent attribution. [CloudTrail userIdentity reference](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html)
- The current CloudTrail reference also documents `onBehalfOf` for Identity Center attribution, `invokedByDelegate` for temporary delegated provider access, and `inScopeOf` for related service/resource context. A parser that assumes every request reduces to a simple IAM username can lose attribution. These are optional context fields, not proof of an exploit. [CloudTrail identity fields](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-user-identity.html#cloudtrail-event-reference-user-identity-fields)
- AWS's source-identity guide says source identity is not captured when an AWS service or service-linked role acts on behalf of a federated/workforce identity. FAS and direct service/role attribution also differ. Absence of a familiar username/source field does not prove unauthenticated access. [Source identity caveats](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html#id_credentials_temp_control-access_monitor-know); [FAS](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_forward_access_sessions.md)

#### Access Analyzer finding meaning and its limits

| Analyzer/output type | AWS-documented meaning | What it does **not** establish |
|---|---|---|
| External access finding | A supported resource is shared outside the configured account/organization **zone of trust**, based on policy/configuration reasoning | Actual access occurred; the sharing is unintended; the external account has a usable principal and matching identity-side permissions. |
| Internal access finding | A possible access path from a user/role inside the selected scope to a **selected supported resource**, with richer policy evaluation | That the access violates business intent, or that a specific newly issued session with unknown restrictions executed the action. |
| Unused access finding | Role, credential, service, or supported action inactivity within the configured observation window | That a permission is exploitable, never needed, or safe to remove without workload review. |
| Policy validation/custom policy check | Grammar/best-practice findings or comparison to a specified policy security property | End-to-end resource access or demonstrated security impact. |
| Generated policy | A template derived from observed CloudTrail activity over a chosen period | A complete statement of all legitimate future activity or an exposure finding. |

Sources: [Analyzer capabilities](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html); [Finding types](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-findings.html); [Finding-generation concepts](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html).

- External analysis does **not** examine logs to determine whether a resource was actually accessed and does **not** know external-account users, roles, SCPs, or other configuration. It analyzes only certain relevant condition keys, does not currently report AWS service-principal/internal-service-account findings, and can conservatively generate false positives where it cannot fully determine external access. [External-analysis limits](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html#access-analyzer-concepts-external)
- Zone of trust is not an assertion that every inside principal is business-authorized. If the zone is an entire organization, sharing across its member accounts does not create an **external** finding merely because a particular workload should not have access. Internal analysis requires a separate analyzer and selected supported resources. [Zone of trust](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-findings.html); [Internal analysis](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html#access-analyzer-concepts-internal)
- Current external support includes KMS key **policies and grants**, while internal-resource support is a different, smaller list. For KMS, an analyzer unable to read key metadata can produce an access-denied **error finding**, not a finding that an attacker has access. Lambda alias/version-qualified policy coverage and cross-account S3 access-point policies have documented limitations. An absence of findings is not global coverage. [Supported resources and caveats](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-resources.html)
- External analyzers generally need Region coverage for supported Regional resources; IAM roles are global and can produce corresponding findings in each enabled Region. Unused-analysis findings do not vary by Region in the same way. Do not duplicate the same global role issue into multiple independent vulnerabilities. [Analyzer Region behavior](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html); [IAM role analysis](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-resources.html#access-analyzer-iam-role)
- Timing matters: AWS describes approximately 30 minutes for many policy updates, up to six hours for account-level S3 BPA/multi-Region access-point updates, and periodic analysis within 24 hours for RCP-only changes that do not trigger a rescan. An `ACTIVE` finding can therefore outlive the access it described. Archiving reflects a management decision; it does not itself remove a grant. [Analyzer timing](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html); [S3-specific timing](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-resources.html#access-analyzer-s3); [Finding status](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html)
- **Current simulator caveat:** the fetched IAM simulator page says it evaluates SCP conditions and resource scoping, and exposes per-policy-type cross-account decisions in `EvalDecisionDetails`; older blanket statements that these are unsupported should not be repeated without checking. It still says it does **not support RCPs**, uses supplied/simulated context rather than a real target service request, and can differ for advanced configurations such as VPC endpoint policies, role chaining, or multiple resource policies. No simulator/API was used here. [Current simulator behavior and limitations](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_testing-policies.html#policies_policy-simulator-how-it-works)

#### IMDS and temporary role credentials — conceptual only

- EC2 applications can receive temporary credentials for an attached IAM role instead of embedding long-term credentials. The **instance profile** is a container for the role; profile and role names can differ. One profile contains one role, and one role can be used by multiple instances/profiles. An instance identifier or profile name alone is not a permission set. [EC2 IAM roles and profiles](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-roles-for-amazon-ec2.html)
- IMDSv2 is session-oriented and requires its instance-specific metadata session token for v2 requests; IMDSv1 is the older request/response mechanism. The IMDS token is conceptually different from the temporary AWS credentials delivered for a role session. Enabling/disabling the endpoint, requiring v2 tokens, and setting response hop limits are distinct controls. This note intentionally omits metadata addresses, paths, headers, and retrieval commands. [IMDS mechanism](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html); [Metadata options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html)
- Do not claim “all EC2 instances now require IMDSv2” from a blanket default. AWS documents per-option precedence: instance launch configuration, account defaults, then AMI configuration where applicable; options can be changed afterward. Account defaults do not retrofit existing instances. The current page also documents a distinct **account-level IMDSv2 enforcement** check after precedence resolution, which can reject a noncompliant launch. “Account default requires v2” and “enforcement is enabled” are not the same state. [IMDS options, precedence, enforcement](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html)
- The hop limit controls the metadata token response's network hops and has container-compatibility implications; it is not a policy granting S3/KMS actions. Even conceptual exposure of workload credentials would still require the effective-permission analysis above. Also, EC2 role credentials are **not subject to the role's configured maximum session duration**, so the ordinary `AssumeRole` duration rule must not be applied universally. [Metadata hop limit](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html); [EC2 credential duration caveat](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-roles-for-amazon-ec2.html)
- **Critical attribution distinction:** EC2 also has automatically created **instance identity roles**, separate from application instance-profile roles. Their credentials are restricted to integrated identity-use services/features; the page explicitly includes `GetCallerIdentity` and says they cannot be used with other services/features that do not integrate with that role. Thus identity output from an instance identity role does not establish that the application's workload role was obtained or that arbitrary S3/KMS access exists. No identity credential was inspected or used here. [Instance identity roles](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-roles-for-amazon-ec2.html#ec2-instance-identity-roles)

### Inferences

#### Concrete proof requirements for a separately authorized owned-canary review

This is a **proposed validation contract**, not an execution runbook. In this research-only assignment, all items remain requirements or possible owner-provided artifacts. No cloud call, session creation, credential handling, resource modification, metadata access, or remediation is authorized by this note. AWS's simulation/analysis limits explain why the evidence classes must remain separate. [Simulator limits](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_testing-policies.html); [Analyzer limits](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-concepts.html)

1. **Define the forbidden outcome and owned entities.** Identify the intended account/tenant/workload boundary, exact action, disposable canary resource/version, authorized owner identity and comparison identity, and expected denial. Intentional public content or approved cross-account collaboration is not a security defect merely because it creates an external finding. State who attests ownership and expected policy. [Sharing/intent basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html); [Zone-of-trust basis](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-findings.html)
2. **Obtain non-secret policy/configuration snapshots from the owner.** Relevant identity policies and selected managed-policy versions; boundary; available session-policy/attribute attestations; trust policy; organization hierarchy and applicable SCP/RCP; S3 effective BPA at all applicable levels; ownership/ACL mode; actual object/key identity; grants including new fields; endpoint route; resource-share state if relevant.
