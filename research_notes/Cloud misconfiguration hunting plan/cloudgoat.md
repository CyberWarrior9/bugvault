CloudGoat is an intentionally vulnerable cloud training environment generator, not a production-assessment engine. ## 2. What initial hints, priorities, prerequisites, and deep validation phases are useful?

### Takeaway

The strongest transferable pattern is **a principal can inspect or modify a lower-trust surface that a stronger identity later consumes**. Validate every transition separately: a visible resource, permissive-looking policy, retrieved credential, successful invocation, or changed browser page alone does not prove the terminal chain. Role-passing/service-trust and mutable-authority-attribute examples provide especially clear deterministic dependency tests. [Lambda route and trust distinction](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/lambda_privesc/README.md#walkthrough---iam-user-chris); [AgentCore trust source](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/agentcore_identity_confusion/terraform/iam.tf); [tag-conditioned management](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/iam_privesc_by_key_rotation/terraform/iam_manager.tf).

### Cited Findings

#### Boundary mechanics and prerequisite relationships

These are **source-derived lab relationships**, not copy-paste exploit procedures. Conjunctions matter: an isolated permission or clue does not establish the following edge.

1. **IAM policy history / authorization-state change.** The rollback lab requires both an older policy version with a stronger effect and authority to select that version as default; the initial state is deliberately limited. Reading historical versions is a discovery step, not escalation. In an adapted fixture, version A denies one canary object and version B permits only that object; proving that exact transition is sufficient without assigning global administrator access. [Scenario prerequisites](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/iam_privesc_by_rollback/README.md#route-walkthrough---iam-user-raynor).

2. **Trust and role passing / execution identity.** `lambda_privesc` allows Chris to assume the management role, whose policy grants `lambda:*` and `iam:PassRole` on `*`. The stronger debug role trusts the Lambda service, not Chris directly, and receives AdministratorAccess. The source-backed chain therefore needs management-role entry **AND** role-passing authority **AND** a compatible service-trust relationship **AND** a create/update-and-trigger path **AND** a useful downstream permission. A rejected direct assumption does not rule out a service-mediated path. [Starting principal and management trust](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/lambda_privesc/terraform/iam.tf#L15-L66); [management policy/debug trust](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/lambda_privesc/terraform/iam.tf#L68-L122).

3. **Mutable tags / credential and MFA ownership.** The key-rotation lab allows credential/MFA-management actions when a resource has `developer=true`, while another policy permits user/role/MFA tagging broadly. Its target secret role requires MFA; the admin user has authority to assume that role. The interesting defect is control over the attributes and enrollment state used to authorize privileged access, **not** cryptographic defeat of MFA. Verify the tag writer, target selector, credential ownership, enrollment owner, role condition, and secret access as distinct edges. [Tag-conditioned actions and unrestricted tag writer](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/iam_privesc_by_key_rotation/terraform/iam_manager.tf#L15-L81); [target identity, MFA trust, exact secret permission](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/iam_privesc_by_key_rotation/terraform/iam_admin.tf#L21-L86).

4. **Identity attributes / application privilege / identity-pool role.** Cognito Terraform explicitly makes `custom:access` mutable and writable by the application client. It also configures an authenticated identity-pool role with pool-audience and authenticated-method conditions, and broad downstream actions. The scenario README connects user-editable access state to a different application path and identity-pool credentials. Distinguish UI validation, identity-provider acceptance, token claim contents, application authorization, role mapping, and accepted canary API access. An exposed client ID or issuance of expected temporary credentials is not intrinsically a flaw. [Writable custom attribute](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/vulnerable_cognito/terraform/cognito.tf#L28-L32); [client writes](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/vulnerable_cognito/terraform/cognito.tf#L70-L104); [role trust and grants](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/vulnerable_cognito/terraform/cognito.tf#L108-L164); [intended route](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/vulnerable_cognito/README.md#walkthrough---vulnerable-cognito).

5. **Storage write / trusted consumption.** `static` turns off the bucket-level public-access-block flags and grants anonymous Get/List/Put subject to the configured source-IP allowlist plus the bot's IP. CORS permits GET/PUT/POST, but the bucket policy is the authorization mechanism shown here. The source is **not** unrestricted worldwide writing despite the README's broad “public” terminology. The damaging edge additionally requires that the actual trusted page/bot consumes the particular modified object. For owned validation, substitute a synthetic bot and inert run-marker receipt for credential collection. #### Deep validation-phase proposal

These phases have **no arbitrary conceptual-depth ceiling**. They separate reasoning depth from execution authority. Every additional real principal, account, tenant, service, write, secret, network segment, or resource requires its own current authorized permission state; a predecessor's success does not grant its successor.

| Phase | Required evidence / exit condition | What it must not be confused with |
|---|---|---|
| V0 — Authority and isolation | Written program/owner approval; exact accounts/subscriptions/tenants/regions/resource IDs; provider-policy review owner/date; permitted actions, identity changes, egress, request/cost budgets, retention, rollback, expiration. Research-only mode remains offline. | “Unlimited depth” is not unlimited budget, account access, credential use, or deployment permission. |
| V1 — Reproducible state census | Source SHA, scenario variant, intended weak edge, configuration hashes, caller/session identity, exact policies/trust and app revision; inventory labels distinguish lab fact from hypothesis. | Source/static match is not deployed state. |

| V3 — Effective permission and reachability | Trace caller → allowed action → resource → trust/conditions → runtime/network/data-plane path. Preserve deny/boundary/session/key/endpoint controls as explicit assessed or unknown facets. | A policy allow is not a successful accepted operation; a network path is not authorization. |
| V4 — One owned boundary crossing | Baseline denial plus one approved canary transition; exact accepted effect read back independently; distinct marker and context for control. | A successful API response without readback does not establish persisted effect or identity transfer. |
| V5 — Next-identity/use validation | Issuer and identity fingerprint, session constraints/expiry and redacted provenance; a single permitted canary action under that identity; deny control under initial identity. | Recovering a credential is not proof of its validity, scope, or authority. | V9 — Remediation/regression/cleanup | Revoke sessions/keys, restore changed policies/tags/revisions, remove all created and dependent resources, verify no residual access, reconcile inventory and cost observations; preserve receipts. | A teardown command's exit status or “destroyed” text is not independently verified cleanup. |

## 3. What cost/lifecycle risks matter, and what owned-lab acceptance should BugVault propose?

### Takeaway

Do not adopt CloudGoat's “create/reset/destroy” language as a deterministic safety guarantee. The pinned implementation and scenario-specific storage retention expose important gaps; acceptance should require independently verified state restoration and residual-resource cleanup, not merely a CLI success message. Begin with offline fixtures and a small paired-canary suite; any later cloud pilot is a separate human-authorized activity. [README lifecycle](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/README.md#usage-guide); [actual create implementation](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/core/python/commands.py#L388-L430); [actual destroy implementation](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/core/python/commands.py#L503-L569).

### Cited Findings

#### Cost, drift, credential exposure, and teardown hazards

1. **No verified price quote.** Scenarios include billable-resource candidates such as EC2, RDS, EFS, load balancers, public addresses, Glue jobs, audit/logging stacks, and an OpenSearch Serverless-backed knowledge base. This establishes a cost-review inventory, not current rates or a dollar estimate. Do not call these labs free, fixed-cost, or all equally cheap. [RCE resources](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/rce_web_app/README.md#scenario-resources); [ECS/EFS resources](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/ecs_efs_attack/README.md#scenario-resources); [AgentCore resources](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/agentcore_identity_confusion/README.md#scenario-resources); [OpenSearch collection](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/agentcore_identity_confusion/terraform/opensearch.tf#L83-L99).

2. **Waiting is part of the lab model, not proof of deterministic readiness.** `detection_evasion` describes a 30–60-minute post-deployment alert integration wait and possible 10–15-minute notification lag. Glue's README describes approximately one minute for the web page and three minutes for the ETL update. AgentCore Terraform sleeps 20 seconds for policy propagation and initiates ingestion through a local-exec command without an explicit completion wait in that resource. Record ready-state receipts and bounded deadlines; do not claim no alert or failed access before the relevant observation window. [Detection timing](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/detection_evasion/README.md#L33-L44); [Glue latency note](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/glue_privesc/README.md#L28-L34); [policy wait](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/agentcore_identity_confusion/terraform/bedrock.tf#L64-L67); [ingestion initiation](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/agentcore_identity_confusion/terraform/bedrock.tf#L119-L131).

3. **Reset documentation differs from the reviewed code.** README says creating an existing scenario destroys/recreates it. `_get_instance_path` instead reuses an existing instance directory, and `create_scenario` performs start script → init → plan → apply → outputs without an explicit destroy. Static review therefore does not establish a clean reset or deletion of out-of-state objects, mutated service state, or historical versions. [README promise](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/README.md#create); [directory reuse](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/core/python/commands.py#L128-L150); [create sequence](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/core/python/commands.py#L388-L430).

4. **Missing state can still yield a success message.** `destroy_scenario` runs Terraform destroy only if `terraform.tfstate` exists. When it does not, the function prints that destroy will not run, moves the instance folder to trash, prints “Successfully destroyed,” and returns `destroyed`. The success string is thus not sufficient cleanup evidence. A normal Terraform destroy error returns `failed` earlier. [Exact branch and success path](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/core/python/commands.py#L526-L569).

5. **One failed create invocation need not mean one underlying attempt.** Error-reporting arguments invoke `init`, `plan`, or `apply` again when the first call returns an error; in particular line 412 calls `self.terraform.apply()` inside reporting. Do not infer a bounded single-apply transaction or add an unreviewed outer retry loop around this implementation. ### Inferences

#### Owned-lab acceptance proposal — design only, nothing deployed

**Purpose:** accept the evidence model and causal chain reasoning, not the ability to obtain broad administrator access or finish every upstream CTF. Adapted canary fixtures are explicitly **not unchanged CloudGoat scenarios**; passing them must not be reported as upstream scenario success or real-cloud/provider coverage.

**Gate A — Offline deterministic acceptance (first milestone).**

- Use captured/synthetic Terraform, policy, resource graph, audit, configuration, task and receiver artifacts with expected labels. No cloud client, account credential, deployment hook, provider download, or external callback is needed.
- Test exact source-SHA provenance; policy/trust/config hashes; separation of identity, grant, accept, execute, data-read, consumer-effect and cleanup facts; AND-prerequisite handling; OR-branch separation; missing or tampered artifact rejection; provider/account/region/context mismatch rejection; stale permission-state reopening; redaction; replay/control distinction; unresolved cleanup blocks closure.
- Include hostile and ambiguous fixture cases: public-by-design client ID; read-only policy enumeration; canary callback without credential use; fetched configuration without downstream authority; CORS without authorization; allowed anonymous storage only from a specific IP; canary task identity confused with host identity; CLI “destroyed” without state; same marker reused as a supposed independent control; too-early detection observation; successful short branch that does not prove the intended long branch.
- Require **all declared offline assertions** to pass and make denominator/coverage explicit. Any emulator or loopback success remains `owned-simulation`, not `provider-validated`.

Design basis: [Cognito public client configuration](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/vulnerable_cognito/terraform/cognito.tf#L70-L93); [storage authorization/IP conditions](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/static/terraform/s3.tf#L14-L65); [destroy edge case](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/core/python/commands.py#L529-L569); [alert latency](https://github.com/RhinoSecurityLabs/cloudgoat/blob/63c65bd26edc6919499adfa20b176c450e35c33c/cloudgoat/scenarios/aws/detection_evasion/README.md#L33-L44).

Reuse the graph and evidence vocabulary, not the destructive goal, credential-capture payload, broad admin policy, alarm-evasion objective, or lab deployment configuration. Read-only authorized configuration review can identify a plausible path; without permission to cross the edge, report the exact supported configuration risk and untested consequence rather than pretending to have demonstrated it. A valid production finding still requires the engagement's reportability/evidence standard.

#### Deterministic lab design requirements

- Pin source and resolved dependencies, image digests, AMI IDs, runtime versions and fixture data. Archive a human-reviewed deployment manifest/plan only in a later authorized workflow. Disable blind retries and external surprise hooks in any adapted runner.
- Use per-run unique canary identities/objects and separate markers for baseline, test, replay and negative controls. Keep source fixture flags distinct from observed run markers; a hardcoded upstream flag alone cannot establish fresh execution.
- Represent permission state explicitly: config version, trust, tags, session issuer/expiry, app client/attribute policy, function alias/revision, container/node identity, exact receiver, and grant-review date. Reopen stale edges after changes.
- Keep account/tenant boundary and source context in every edge. A different authorized lab account is not automatically the same evidence context or permission scope.
- Prefer two nearly identical sibling environments/resources, weak and patched. Change one security-relevant edge while preserving application functionality; keep a legitimate reader/writer as positive control.
- Make readiness observable and bounded rather than relying only on fixed sleeps. Test timeouts, partial deployment, missing state, credential revocation and cleanup failure offline before cloud acceptance.
- Keep raw credentials, Terraform state, `start.txt`, personal data and real program details out of public/model-facing research notes; hashes/redacted labels are sufficient here.
- Track created resources independently of Terraform state, including manually created artifacts. Cleanup receipts need exact ownership, deletion/retention status, remaining-resource inventory, credential/session revocation and a named follow-up for retention that prevents immediate deletion.
- Budget by account/region/service, not by the number of scenario names. Select one scenario/fixture at a time, cap invocation/job/clone counts, review actual consumption, and halt on unexplained drift, service errors, lost receiver, unexpected third-party data, or cleanup failure.

These requirements are proposed responses to the reviewed source's drift, sensitive outputs, provisioning hooks, timing and cleanup limitations; they are not claims that upstream CloudGoat enforces them.
