# Evidence and readiness

First establish written authority, excluded assets, exact intended boundary,
principal/session and disposable test object. Then record operation, source ID,
current policy/context, artifact roles and independent observations. A scanner
PASS/FAIL, guessed bucket, response code, RUM ID or key-shaped string remains a
lead. Source hashes and selectors enable reconstruction but cannot certify
provider semantics. `canary-proved` is an operator-labelled stage requiring
baseline, test, replay and independent negative control. For a write it also
requires before, after and cleanup receipts. These do not prove a real cloud
service executed an operation; an independent validator still reviews causality.

`cloud.grants` in `scope.json` are *evidence-recording labels only* and can be
`read`, `write`, `discovery`, `chain`, `impact` or `burst`, each needing a dated
rules review and positive declared budget. No label changes scope, transport,
method approval, provider policy, current account ownership or the campaign's
HTTP limit. `recon send` enforces the URL/HTTP boundary; cloud SDK traffic is
not mediated. Burp traffic is declared manually and its approval workflow is
separate. A native event must cite actual matching stored request IDs. Neither
Burp refs nor content assessment automatically confirm an access-control bug.

Distinguish public-intended, private and unknown content. Use an owner-staged
synthetic canary or a permitted minimal proof; do not classify a genuine secret
as valid from its shape or send it to a receiver. Unclear ownership or intent
remains unknown, even if the response is 200. Stop on 429, 5xx, challenge,
unexpected effects, sensitive-data spill, absent observer or unresolved
cleanup; preserve historical evidence and the reason for later review.
