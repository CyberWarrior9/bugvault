# Dated provider confidence, not a claimability catalogue

This skill certifies **no provider as claimable today**. Its review date is the
workflow's edit date, not an independent review of every provider. Community status
can change with product, region, account tier, namespace, DNS-verification policy
and release/reuse protections. Local hardcoded suffix/body signatures remain leads.

## Keep independent evidence dimensions

| Dimension | Record | Stronger claim still needs |
|---|---|---|
| Provider identification | Exact matching CNAME suffix or response bytes; source file/version/hash | A match boundary and target-specific evidence, not a substring in unrelated text. |
| DNS/service failure | Exact DNS status or stored HTTP response with capture time | Distinguish collection failure, wildcard/parking, expired deployment and ordinary maintenance. |
| Catalogue status | Provider/product, source URL, pinned snapshot/hash when held, published status/date, review date | Current, specific review; community "vulnerable" is not target permission or a successful claim. |
| Namespace availability | Exact namespace, region/service, ownership prerequisites, observation time and approved source | A free-looking name may be reserved, account-bound or require DNS ownership verification. |
| Controlled ownership | Owned resource/account, scoped hostname marker proof, replay/control, authorization and cleanup | Validator review; not automatically a finding or downstream impact. |

Do not collapse these into one `confirmed` candidate state. Use the implementation's
actual candidate vocabulary and explain what it means; reserve finding `confirmed`
for the existing finding lifecycle. Preserve unknown/blocked/inconclusive dimensions
even when another dimension has strong evidence.

The current DNS classifier emits `candidate`, `potential`, `collection-gap` or
`provider-stale`. None means claimable. Inspect `basis`, `gaps`, `provider_info`,
`address`, `referral_state` and `wildcard_state` instead of treating one label as a
complete assessment.

## Provider-status wire records

`takeover.providers`, when supplied in `scope.json`, is a bounded list of records
with **exactly** `provider`, `status`, `source` and `checked`. The provider is a
lowercase hyphenated identifier; status is `unknown`, `vulnerable`, `patched` or
`edge-case`; source is an HTTPS URL without userinfo/fragment; checked is a
nonfuture `YYYY-MM-DD`. These are operator assertions. An HTTPS link is not proof
the source was fetched or its claim remains true.

`recon/takeover_dns.py` currently treats absent records or records older than
**90 days** as stale. The latest checked date is used; conflicting statuses on that
date become unknown/conflicting. Keep source snapshots and product/region details
in the dossier even where the compact config has no corresponding fields. Do not
set a new checked date without actually reviewing that provider claim.

## Date and source handling

- Keep **source publication/snapshot time**, **operator review time** and **target
  observation time** separate. Copying a 2023 source today does not make its provider
  claim current; a source URL without downloaded bytes is not a pinned snapshot.
- If a local freshness threshold exists, state its value and the observation window.
  Passing a threshold is a heuristic, not a guarantee. Unknown dates, historical
  data, patched/edge-case status or unresolved conflicts block stronger conclusions.
- Preserve stale positives as historical leads. They can still guide a high-priority
  review when a currently captured production trust reference remains, without
  making the claim branch ready. A recent negative may similarly be context-limited.
- Don't refresh catalogues, test provider availability, call APIs, allocate addresses,
  try registration or issue certificates automatically. Any future external review
  needs the existing approved path and must not leak private program hostnames.

## Provider-specific dossier questions

Name the exact product/region/namespace and whether reuse requires an owned account,
an unrelated DNS record/token, a paid plan, an ownership-verification step or a
cooldown. Record ambiguity instead of bypassing verification. Distinguish an
available resource name from a usable custom-domain association. DNS delegation,
resource allocation, serving an HTTP marker and serving trusted HTTPS are different
capabilities. An error page may be generated by a proxy, edge or default virtual
host instead of the claimed provider resource.

Treat can-i-take-over-xyz, dnsReaper, practitioner notes and scanner signatures as
dated research inputs, not grants or proof. `references/sources.md` lists the cited
URLs; they were not fetched or current-provider-verified when this skill was written.
